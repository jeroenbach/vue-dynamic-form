# Story: Rebuild the onboarding wizard components on `useFormWizard`

## Functional
### User story
As a docs reader studying the onboarding wizard example (an app-component author and a template author building on `DynamicForm`), I want `FormExampleClientOnboardingPlanner.vue`, `FormWizard.vue`, and `AdvancedFormTemplate.vue` rebuilt on `useFormWizard`, so the example teaches the composable-based pattern instead of `registerWizardPagePath`/`wizardPagePaths`/metadata-stored callbacks/`loadingResolve`, while the wizard behaves exactly as it does today.

### Acceptance criteria

1. **`FormExampleClientOnboardingPlanner.vue` drops the retired plumbing and calls `useFormWizard`.**
   Given the file after this story,
   When searched for `registerWizardPagePath`, `wizardPagePaths`, `validatePage`, `submitForm` (the metadata field), and `LoadingResolve`,
   Then none of those identifiers appear anywhere in the file, and `setup` calls `useFormWizard(wizardNode.children, { validateSection, onSubmit })` (using the shipped ST-01 API), where `onSubmit` wraps the existing `handleSubmit(...)` submit logic (the `removeNullValues(values)` call and `submitted.value = ...` assignment move into `onSubmit`, unchanged in behavior).

2. **Every other `computedProps` entry is preserved verbatim.**
   Given the six `computedProps` arrays across the five wizard pages and the summary page,
   When `registerWizardPagePath` is removed from each,
   Then every other entry (the industry/teamSize/migrationDeadline/trainingFormat conditional logic, and the summary page's `field.wizardSummary = wizardSummary.value`) is unchanged, verified by a diff against the pre-refactor file showing no line touched inside those closures beyond removing `registerWizardPagePath` from the array.

3. **`FormWizard.vue` reads and drives wizard state via the injected composable, not local refs.**
   Given `FormWizard.vue` after this story,
   When searched for `currentStepIndex = ref`, `createLoadingResolve`, and the `validatePage`/`submit` emits,
   Then none of those are present; the component calls `useFormWizardContext()` and reads `currentStepIndex`, `isFirst`, `isLast` and calls `next()`, `prev()`, `gotoStep()`, `submit()` directly from it. It remains a purely presentational component (Stepper, buttons, layout markup unchanged).

4. **`FormWizard.vue`'s `Stepper` uses `wizard.pages` as the single source of truth for step count and order; per-step display text (title/description) is read from `fieldMetadata.children` at the same index (finding 4's resolution, narrowed).**
   Given the injected wizard context and the wizard node's `fieldMetadata.children`,
   When `FormWizard.vue` builds the `Stepper`'s `steps` prop,
   Then it iterates `wizard.pages` (i.e. `wizard.pages.length`/order is authoritative, so `isLast` and the last rendered step can never desync), building each step as `{ title: toValue(fieldMetadata.children?.[i]?.fieldOptions?.label) ?? fieldMetadata.children?.[i]?.name, description: fieldMetadata.children?.[i]?.helpText }` for the matching index `i`, reproducing today's exact title/description strings.
   > DECIDED (research): the feature's AR-4 finding was specifically about step **count and order** desyncing `isLast` from the last rendered step, not about display text; that concern is fully addressed once `wizard.pages` (not `fieldMetadata.children`) governs iteration length and order. Display text still comes from `fieldMetadata.children` at the matching index, since `helpText`/`description` are docs-only `defineMetadata` extensions ST-01's core `FormWizardPage` type was never meant to carry (core only has `fieldOptions.label`, confirmed in `packages/core/src/types/FieldMetadata.ts`), and both arrays share the identical order and length by construction (both derive from the same wizard node's children), so index-matching is safe. This resolves the finding within this story's own scope; it requires no change to ST-01's published surface. (Superseded PROPOSED option (b), which would have touched ST-01's page shape and needed Jeroen: not necessary, since option (a) fully satisfies AR-4's actual concern.)

5. **`AdvancedFormTemplate.vue` drops the emit/slot-prop threading for step state, reading wizard state through a small dedicated child component instead of calling `useFormWizardContext()` at its own shared top level (finding 1's resolution).**
   Given `AdvancedFormTemplate.vue` after this story,
   When inspected,
   Then: the `validatePage`/`submitForm` fields and the `LoadingResolve` import are removed from the `defineMetadata` extended-properties generic; the `@validate-page`/`@submit` bindings and the `<slot :current-step-index :gotoStepIndex="gotoStep" />` threading are removed from the `#wizard` slot template; `currentStepIndex`/`gotoStepIndex` are removed from the `defineMetadata` SlotProperties generic; and the `wizardPage`, `wizardPage-array`, `wizardPage-array-item`, `wizardPage-choice`, `wizardPage-choice-array`, and `wizardSummaryPage` slots read `currentStepIndex`/`gotoStep` from a new small child component (working name `WizardStepGate.vue`) placed inside each of those slot templates, whose own `setup()` calls `useFormWizardContext()` and exposes `currentStepIndex`/`gotoStep` via its default scoped slot. `AdvancedFormTemplate.vue`'s own shared `<script setup>` (which every non-wizard example's `DynamicForm` also instantiates) never calls `useFormWizardContext()` directly.
   > DECIDED (research): option (b) from the review, not option (a). `AdvancedFormTemplate.vue` is a single component file reused recursively (`<AdvancedFormTemplate v-bind="_props" type="heading">` for every `wizardPage*` sub-render) and as the shared `:template` for every other docs example, so its one `<script setup>` runs identically regardless of which named slot ends up firing; a call there cannot be conditioned on "is this a wizard" before Vue has picked a slot. A genuinely separate child SFC that is only instantiated inside the wizard-specific slot templates sidesteps this entirely, since Vue only runs that child's `setup()` when it is actually mounted, i.e. only when a `wizardPage*`/`wizardSummaryPage`-typed node is being rendered, which today only happens inside the onboarding example's tree (confirmed by grep: no other example's metadata uses these types), where the wizard-providing ancestor always exists. This exactly mirrors the pattern `FormWizard.vue` itself already establishes (a separate component, mounted only for the `#wizard` slot, that owns wizard-context access) and needs no change to ST-01's published surface, so it stays a story-local decision rather than one that needs Jeroen.

6. **`docs/.vitepress/theme/utils/loadingResolve.ts` is deleted.**
   Given this story removes `loadingResolve`'s three real (compiled) callers (`AdvancedFormTemplate.vue`, `FormExampleClientOnboardingPlanner.vue`, `FormWizard.vue`),
   When this story ships,
   Then the file is deleted and `grep -rn "loadingResolve\|LoadingResolve\|createLoadingResolve" docs/.vitepress` returns no matches. (`docs/reference/use-validate-partial-form.md`'s mention of `LoadingResolve` is prose inside a Markdown fenced code block, not compiled/imported code; it does not block this deletion, and ST-03 separately rewrites that stale prose so the page stops teaching a pattern that no longer exists.)

7. **The wizard behaves identically to a reader, end to end.**
   Given the live onboarding example (`docs/examples/advanced.md`),
   When a reader steps through it: fill in company details (including the conditional migration-deadline field), add/remove project contacts, select and fill a launch-approach branch and switch between branches, add/remove systems, reach the summary page, use a summary row's edit link to jump back, then submit,
   Then every step behaves exactly as before the refactor: `next()` blocks on an invalid page and shows the same validation errors, `gotoStep` (stepper clicks and summary edit links) remains backward-only, the summary page's data and the post-submit timeline/JSON view are unchanged, verified via before/after Playwright screenshots (CLAUDE.md's "Before Every Push" step 4) and a manual walkthrough.

8. **The `launchApproach` choice page (an explicit choice, not a plain group) keeps validating and navigating correctly (Constraints section's named regression check).**
   Given the `launchApproach` page's root node is itself a `choice` (`explicitChoiceSelection`/`preserveOnSwitch`),
   When a reader selects a branch, fills its required fields, and clicks Next,
   Then page-path derivation and `next()`'s validation gating work exactly as for a plain group page, with no special-case code added for the fact that this page's root is a choice.

9. **The repeatable `projectContacts` page keeps validating correctly.**
   Given `projectContacts` (`minOccurs: 1, maxOccurs: 3`) as a wizard page,
   When the reader is on that page (with 1-3 contact occurrences filled to varying degrees) and clicks Next,
   Then `validateSection('projectContacts')` still validates all current occurrences by prefix match (`projectContacts[0].*`, `projectContacts[1].*`, ...), exactly as before, with no `field.path.includes('[')` guard needed anywhere in the refactored code.

### Edge cases
- Clicking "Next" is never exposed on the summary page in the UI (it shows "Submit" instead via `isLast`); no redundant bounds-guard needs to be added here beyond what `useFormWizard`'s own `next()` already provides (ST-01 AC9).
- The `migrationDeadline` conditional-required field (hidden/required based on `requiresMigration`) must still gate `next()` on the `company` page exactly as before; this is an existing `computedProps`/`xsd_required` interaction, unmodified by this story, and is a natural regression check for "every other `computedProps` entry preserved" (AC2).

### Out of scope
- Any visual redesign of the wizard UI; the docs example keeps its current look.
- `docs/examples/advanced.md` prose, `docs/reference/use-validate-partial-form.md`, and the new `docs/reference/use-form-wizard.md` page (ST-03).
- The `wizard`/`wizardPage`/`wizardSummaryPage` field-type concepts and other `AdvancedFormTemplate`-specific `defineMetadata` extensions (`choiceShowChoiceSelect`, `wizardSummary`, icon labels, etc.) beyond what is needed to wire the composable in; those stay exactly as they are.
- Any change to `packages/core/src/`; this story is docs-only.
