Section 1 — Narrative intro#page-intro

Inbox rules, where order is the whole point

Final slug / title / nav placement are Open question 4. Working title and slug /examples/inbox-rules used throughout. Page sets aside:false and a pageClass, widening the content column to 1100px, exactly like the checkout page.

Every mail client, every firewall, every router does the same thing: it walks an ordered list of rules top to bottom and stops at the first one that matches. Move a rule up, and it starts catching messages a rule below it used to handle. That is not a cosmetic detail. The order is the behavior.

The form below is a single repeatable ordered choice: one metadata tree, one template, no bespoke engine code. Each row is a rule, with genuinely different fields per condition type. Reorder the rules and the live test inbox on the right re-routes every message the instant a rule moves.

What you are looking at A fixed, fictional test inbox of six messages, routed entirely in your browser. No mail server, no account, no message is ever sent anywhere. The inbox is demo data authored for this page.

Intro copy borrows the conceptual model (Gmail filters / ACLs / routing tables) in words only. No email-client chrome is imitated, matching how the checkout page borrows Shopify's structure but not its branding.

Section 4 — Unreachable-rule surfacing#unreachable

The rule list, a repeatable ordered choice

Four condition branches, four shapes

Each branch is a genuinely different condition, not a cosmetic relabel: an email leaf with a pattern, a plain text leaf, a number-plus-unit pair, and a childless branch.

InboxRulesExample.vue
const fromSender = {
  name: 'fromSender', fieldOptions: { label: 'From sender' },
  children: [
    { name: 'email', type: 'email',
      restriction: { pattern: EMAIL_PATTERN }, validation: ['xsd_required'] },
    actionFields,                 // shared action block, spread into every branch
  ],
};

const largerThan = {
  name: 'largerThan', fieldOptions: { label: 'Larger than' },
  children: [
    { name: 'size', type: 'number', validation: ['xsd_required'] },
    { name: 'unit', type: 'select', fieldOptions: { options: ['KB', 'MB'] } },
    actionFields,
  ],
};

const hasAttachment = {
  name: 'hasAttachment', fieldOptions: { label: 'Has attachment' },
  // No filter field of its own, but not a childless leaf either: the shared
  // action block gives the branch children, so no marker value is needed
  // (unlike the checkout's express / home-delivery / PayPal leaves).
  // See Open question 1 and ADR-2.
  children: [ actionFields ],
};

Note for the architect: a truly childless branch disables preserveOrder for the whole choice (dev-mode warning). This prototype shows "Has attachment" carrying only the shared action block, so it is technically an object, but whether that counts as a filter-less branch for Open question 1 is Jeroen's call. The action block itself gives every branch children regardless.

The per-rule action

Every rule carries an action: move to folder, apply label, forward, or delete. Modeled as an action select with conditionally revealed fields via computedProps (the folder name, label, or forward address appears only for its action), mirroring the checkout's business/VAT toggle. A nested second-level choice is the alternative; that trade-off is an architecture decision.

The reorder control

The up/down buttons write the two affected occurrences' order values directly through the normal field-write path, exactly as SplitPaymentLedgerRow does. The engine's renderedChoiceOccurrences re-sorts with no remount.

The live routing module

A small, pure, synchronous TypeScript module (mirroring splitPaymentLedgerMath.ts) walks the rules in displayed order and returns, per sample email, the first matching rule and its action. A template-level computed reads the form's values through vee-validate's own context, not computedProps, and feeds the inbox panel.

inboxRoutingMath.ts
export function routeInbox(rules: Rule[], inbox: Mail[]): RoutedMail[] {
  return inbox.map((mail) => {
    for (const rule of rules) {          // already in displayed order
      if (matches(rule, mail))
        return { mail, caughtBy: rule, action: rule.action };
    }
    return { mail, caughtBy: null };     // stays in Inbox
  });
}

The unreachable-rule check

A derived check reads the live rule list and flags any rule an earlier rule already fully shadows, surfaced via the same hidden-field technique the checkout's splitPaymentCoverage uses. Open question 2 fixes the subsumption definition; Open question 3 fixes whether it blocks submit or only warns.

What It Demonstrates

  • A repeatable ordered choice (maxOccurs > 1 + explicitChoiceSelection + displayOrder: 'added') as the entire form, not a footnote.
  • Four condition branches with genuinely different fields, including a childless "Has attachment" branch.
  • A per-rule action with a conditionally revealed field via computedProps.
  • Position badges from globalIndex + 1, and up/down reordering that writes the affected order values directly.
  • A live side panel routing a fixed test inbox "first match wins", re-routing on every reorder.
  • A cross-row unreachable-rule check built on the checkout's hidden-field technique.

How It Works

The rule list is a choice with maxOccurs > 1 and explicitChoiceSelection. Each Add button pushes an occurrence into its branch's field array; reordering rewrites two order-equivalent values and the engine re-sorts renderedChoiceOccurrences with no remount. The inbox routing is a pure module read through vee-validate's useFormContext, not computedProps. Submit is gated on the form's aggregate meta.valid, trustworthy since FEAT-010 landed (ADR-5). No new engine primitive is involved.
