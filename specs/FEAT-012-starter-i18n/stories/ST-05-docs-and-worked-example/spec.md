# Story: Documentation, live example/story, components.md, README, and the Dutch worked example

## Functional
### User story
As a docs reader or library consumer evaluating this feature, I want a complete, runnable Dutch translation exercising every chrome string and validation message, a live pack-switching example, and documentation of how to select a pack, how precedence resolves, and how to author my own pack, so that I can adopt the mechanism (or build a non-English, non-Dutch pack) without reverse-engineering the source.

### Acceptance criteria
- AC1: Given `docs/guide/starter-template.md`, when the new section is read, then it covers: selecting a pack, the precedence rule (explicit > pack > built-in fallback, including the per-tier `password.strengthLabels` merge from ST-01), authoring a custom pack using the complete Dutch pack as the worked example, how the locale tag drives number formatting (ST-03), locale-aware display for the existing `date` field (canonical `YYYY-MM-DD`, its browser/OS-locale editing display unchanged by this feature, the new optional `date?: { min?, max? }` native bound, and the pack-locale read-only display via the exported util, ST-04), and the documented `xsd_minInclusive`/`xsd_maxInclusive` limitation for dates.
  - `DECIDED (Jeroen)`: corrected per adversarial review finding 1 (was a blocker). `date` already exists in `StarterValueTypes` (`packages/starter/src/metadata.ts`) and already renders as a native `<input type="date">` via `TextInput`/`default-input`; this was a factual error in the feature's own Problem section, carried through the original architecture, ST-04's first draft, and this story's first draft, not caught until this story's own adversarial review grepped the live source. ST-04 is rewritten to the accurate, much smaller scope: a `date?: { min?, max? }` group property and the exported read-only display util, no new value type, component, or slot. Docs describe an enhancement to a pre-existing type, never the introduction of one.
- AC2: Given `docs/guide/validation.md`, when the note is read, then it states the starter ships an opt-in English translated message set feeding `settings.messages` (ST-02), that a consumer's own per-rule override still wins, and that the Dutch worked example shows a full non-English set authored the same way.
- AC3: Given the complete Dutch worked example (a `StarterLanguagePack`-shaped chrome pack and message set, informally `nlStarterPack`), when its source is read in docs/examples, then it exercises every chrome string listed in the feature's Problem section and all 18 message keys, and is copy-pasteable, documented source (not a package export; it carries no changeset).
- AC4: Given at least one docs example page or Storybook story, when it is opened, then it demonstrates a live pack switch (English ↔ Dutch, no remount) end to end, matching the prototype's `#pack-english`/`#pack-dutch`/`#pack-dutch-success`/`#precedence` sections.
- AC5: Given `specs/components.md`, when the starter row is read, then it lists every new export/property added across ST-01/ST-02/ST-04 (`enStarterPack`, `StarterLanguagePack` type, `starterMessages`, the English message dictionary, `resolvePackText`, the exported date-display util, the active-pack selector field on `StarterSettingsProperties`, and the new `date?: { min?, max? }` group property on `StarterFieldProperties`) in one consolidated pass, with no stale or missing entries. The existing text-mode `date` sentence in components.md ("rendered through the existing `TextInput`/`default-input` with no new component or slot") stays correct and unchanged — `date` is still not a new value type, component, or slot — and gets one addition mirroring how `number?: { min?, max?, step? }` is already documented there: a sentence noting `date` also gained the optional `date?: { min?, max? }` group property, forwarded the same way.
  - `DECIDED (Jeroen)`: corrected per adversarial review finding 2 (was a should-fix) and the related finding 1 (blocker, resolved at the feature/ST-04 level, see below). The list above is the final, accurate eight-item consolidated pass. There is no `date-input` slot and no internal `DateInput` component to document, since neither exists; ST-04 was rewritten to add only the `date?` property and the exported display util.
- AC6: Given `packages/starter/README.md`, when it is read, then it documents pack selection and custom-pack authoring for a consumer reading the package directly from the npm tarball (no VitePress access assumed).
- AC7: Given the shared changeset file created in ST-01 and appended to by ST-02/ST-03/ST-04, when this story completes, then the changeset reads as one coherent user-facing entry for the whole i18n capability with sub-bullets, written business-purpose-first for someone skimming release notes, not as a per-story implementation log.

### Edge cases
- The Dutch worked example's consumer-authored field labels (not pack-owned content) are shown translated in the `#pack-dutch`/`#pack-dutch-success` prototype anchors on purpose (finding 8's resolution); this story's docs text must state that packs never translate consumer content, not imply the opposite.
- `docs/guide/validation.md`'s note must not claim the English message set is a "no observable change" extraction (unlike the chrome pack): it is genuinely new text relative to today's generic vee-validate fallback (finding 2), and must be stated as opt-in for that reason.

- RTL layout documentation (feature-level out of scope, OQ2).
- Translation of the VitePress site's own prose/navigation outside this feature's own pages (feature-level out of scope).
- Implementing any of ST-01 through ST-04's mechanism (this story only documents and demonstrates it).

### Edge cases to tests
- Consumer content is shown translated, un-outlined, in the `#pack-dutch`/`#pack-dutch-success` anchors on purpose (finding 8's resolution): the docs text accompanying the live demo must state plainly that a pack never translates consumer-authored labels, and that the Dutch demo's own field labels are translated separately by the example author, not by the pack. ### States from the feature's states policy covered by this slice
This slice only *demonstrates* states ST-01/ST-02/ST-03/ST-04 already implement and test; it adds no new component logic, so no new automated state assertions are owed here. What the worked example's demo page must visually reproduce (manual checklist, mirrors the prototype anchors):

- Light and dark mode: spot-check both for the new demo page (no new `sft-` class is introduced by this story, so this is a visual regression check only).

### Reactivity / render-count
This story introduces no new reactive wiring in `DynamicFormItem`/`computedProps`/`combinedValidation` (no `packages/core`/`packages/starter` source change), so no new `*.analytics.test.ts` file is owed. The one reactivity-adjacent risk is implementation, not a missing assertion: the new demo page's pack toggle must bind `settings.activePack` to a plain reactive `ref` consumed by the same mounted `DynamicForm`/`StarterFormTemplate` instance (per OQ3/ST-01 AC6, "no remount, no data loss"). A toggle implemented with `v-if`/a `:key` keyed to the active pack, or two separately-mounted forms swapped by `v-if`, would visually "work" but silently defeat the live-switch guarantee ST-01 already tested and would misrepresent the feature in its own worked example. Flagged as a specific implementation pitfall for the developer and a specific manual-checklist item (type into a field, switch the pack, confirm the typed value survives) rather than a new automated test, since the underlying mechanism is already covered by `StarterFormTemplate.languagePack.analytics.test.ts` in ST-01.

### Coverage
No `packages/core/src/` or `packages/starter/src/` file is added or changed, so `pnpm -r ci:test:coverage`'s statement/branch/function baseline is unaffected by this story; nothing to regress. The new pure `.ts` modules under `docs/.vitepress/theme/components/` (`nlStarterPack.ts`, `packSwitchReviewRows.ts`) are not codecov-tracked (per `CLAUDE.md`, `docs/` coverage is untracked), but must still be fully exercised by `pnpm docs:test` per the existing convention for every other extracted math/logic module in that folder (`inboxRoutingMath.ts`, `workoutPlanMath.ts`, `runOfShowMath.ts`, `splitPaymentLedgerMath.ts` all have a matching test file); no branch in either new module should be knowingly left uncovered.

### Time sensitivity
`packSwitchReviewRows.ts`'s date-formatting case calls the exported, already-timezone-independent date-display util (ST-04's AC5 requires `Intl.DateTimeFormat(locale, { timeZone: 'UTC' })`); this story's own test asserts the same calendar date renders identically regardless of process `TZ` by constructing its expected string the same UTC-anchored way, not by depending on the ambient `TZ`. `pnpm docs:test`'s plain `test` script does not set `TZ`; `ci:test` sets `TZ=Europe/Amsterdam`. The test must pass under both, since it asserts a timezone-independent property rather than a timezone-specific one. The prose docs' own date discussion (AC1's "canonical value / browser-locale editing / pack-locale read-only display" section) carries no runtime time dependency.
