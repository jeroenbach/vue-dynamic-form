# Story: Chrome-string language pack, resolver, and active-pack setting

## Functional
### User story
As a library consumer building a form for a non-English-speaking audience, I want to select one active chrome-string pack so every built-in wizard, array, choice, password, review, success, and optional-tag string in my form renders in that language without editing my metadata tree, so that I flip one setting instead of translating dozens of per-field strings by hand.

### Acceptance criteria
- AC1: Given a consumer selects no pack and sets no per-field chrome string override, when the starter template renders any chrome string it owns (wizard buttons/progress text, array add/remove/empty-state text, choice add/limit text, password toggle aria-labels, the optional tag, and the three inline template literals `'Ready to submit?'`, `` `New ${itemName}` ``, `` `New ${branchKey}` ``), then every rendered string matches today's hardcoded English default exactly. Verified by a test asserting each resolved string equals the shipped `enStarterPack` value, and that `enStarterPack`'s values equal today's component defaults.
  - `DECIDED (Jeroen)`: the review edit button and submission-success labels are removed from this AC's scope (and from AC2/AC4/AC6 below). Resolved per the feature-level amendment to the Functional overview and Design sections: `ReviewGroup`/`SubmissionSuccess` are not rendered inside `StarterFormTemplate` (`SubmissionSuccess` isn't rendered by it at all), so the template cannot auto-resolve their strings the way it does for every other chrome component. Instead, AC4 below is extended to require this story's resolver be **exported** (not internal) so a consumer wiring `ReviewGroup`/`SubmissionSuccess` on their own page can call it themselves. See the feature spec's amended Architecture > Public API impact.
- AC2: Given a consumer explicitly sets the active-pack setting to `enStarterPack`, when the form renders, then every chrome string still matches today's defaults exactly.
- AC3: Given a consumer has already set a per-field override (e.g. a field's own `wizardTexts.nextButtonText`) or a settings-level override (`optionalText`), when any pack is active (including a non-English one), then the explicit value renders unchanged, including when the explicit value is the empty string `''`.
- AC4: Given a consumer activates a non-English pack, supplied either as a `StarterLanguagePack`-shaped object or as a custom lookup function `(key) => string | undefined`, when a field has no explicit override, then the chrome string renders from that pack/function.
- AC5: Given `password.strengthLabels` is a per-tier object (`weak`/`fair`/`good`/`strong`, all tiers optional) and a consumer explicitly overrides only one tier while a pack is active, when the password strength bar renders, then the overridden tier shows the explicit value and the other three tiers show the pack's value (or the built-in fallback if the pack also leaves a tier undefined) — per-tier merge (`{ ...pack.strengthLabels, ...explicit.strengthLabels }`), never a whole-object replace.
- AC6: Given the active-pack setting changes while the form is mounted (no remount, no data loss), when the change is applied, then every chrome string across the rendered form re-resolves to the new pack's value without a reload.
- AC7: Given a consumer passes a custom lookup function as the active pack, when the function returns `undefined` for a given key, then resolution falls through to the built-in English fallback for that key (not to any other pack), consistent with `explicit ?? activePack(key) ?? fallback`.
- AC8: Given the active-pack setting lives on `StarterSettingsProperties` (`DynamicFormSettings`) and an optional `StarterFormTemplate`-level prop is also set, when both are present, then the template-level prop wins for chrome strings only; it has no effect on the validation-message channel (ST-02), which always keys off the form-level setting.
- AC9: Given `resolvePackText` is exported from `packages/starter/src/index.ts` (not internal), when a consumer imports it directly to build their own `ReviewGroup`/`SubmissionSuccess` usage (which `StarterFormTemplate` does not render), then calling it with the same `explicit`/`activePack`/`fallback` arguments produces the identical result the template uses internally, so a consumer can pack-resolve those two components' props themselves with no second mechanism to learn.

### Edge cases
- Placeholder tokens already used by existing strings (`{current}`/`{total}` in `stepText`, `{option}` in `choicePicker.addButtonText`/`limitReachedText`, `{number}` in `array.removeAriaLabel`) keep substituting correctly when the string's value comes from a pack instead of a hardcoded default or per-field override.
- A pack value explicitly set to `''` is honored as "set" (not treated as absent), matching the existing `??` semantics.
- ASSUMED (story prep): a custom lookup function that throws, or returns a non-string/non-`undefined` value, is not defensively caught; the resolver treats it as any other TypeScript-typed function call (consumer responsibility), matching how other injectable accessor functions in the codebase (e.g. `computedProps`) are not wrapped in try/catch. Alternative considered: wrap every lookup call in try/catch and fall back on error. Rejected for this story as unnecessary defensive scope beyond what the architecture asked for; trivially reversible later if a real consumer issue surfaces.

### Out of scope
- Translated validation messages (ST-02).
- Locale-aware number formatting (ST-03) and the new `date` field type (ST-04).
- Authoring the Dutch worked example's chrome strings, docs, README, and `specs/components.md`'s consolidated pass (ST-05); this story only ships the mechanism and the English pack.
- RTL layout (out of scope at feature level, OQ2).

## Design reference
- `../../prototype.html#pack-english` — full chrome in the English pack: wizard head + stepper, required/optional tags, password field with strength label and show/hide toggle, filled repeatable array with add/remove, repeatable-choice add bar including the disabled limit-reached state, wizard footer.
- `../../prototype.html#precedence` — Dutch pack active, two sibling repeatable sections: one reads `array.addButtonText` from the pack (indigo outline), the other declares its own value which wins (amber outline). This story implements the resolution mechanism the anchor visualizes; the Dutch pack content itself is authored in ST-05, so reproducing this anchor exactly requires ST-05's Dutch pack, but the precedence logic under test in this story is pack-agnostic (verifiable with any non-English pack, e.g. a small test fixture pack).
- No new design language: this story introduces no new `sft-` class or component.

## Architecture reference
- Builds: the `StarterLanguagePack` type (full shape, including a `messages` sub-shape declaration consumed by ST-02 — see dependency note below), the `enStarterPack` object's chrome-string portion (extracted verbatim from today's component `withDefaults`/template literals so it is observably identical to current behavior), the pure `resolvePackText`-style resolver supporting both a static pack object and a custom lookup function, and the active-pack selector on `StarterSettingsProperties` plus an optional `StarterFormTemplate` convenience prop that wins for chrome only (ADR 4 / OQ6).
- Modifies: `StarterFormTemplate.vue`'s ~25 chrome-string prop bindings (e.g. `:addButtonText="s.fieldMetadata.array?.addButtonText"`) plus the three inline template literals called out in the feature architecture, routing every one through the resolver; `metadata.ts` for the new `StarterSettingsProperties` field(s).
- Per-tier merge for `password.strengthLabels` (finding 6): implemented at the resolution site feeding `PasswordInput`/`PasswordStrengthBar`; confirm `PasswordStrengthBar`'s own `withDefaults` still backfills any tier left undefined by both the explicit value and the pack.
- Reused unchanged: every chrome component (`FormWizard`/`Stepper`, `ArrayField`/`ArraySectionCard`/`RepeaterCard`, `ChoiceField`/`ChoiceSectionCard`/`ChoiceArraySectionCard`, `PasswordInput`/`PasswordStrengthBar`, `OptionalRequiredTag`, `ReviewGroup`, `SubmissionSuccess`); their `withDefaults` stay as the lowest precedence tier.
- Public API surface (additive): new exports from `packages/starter/src/index.ts` — `enStarterPack`, `StarterLanguagePack` type, and the `resolvePackText` resolver itself (`DECIDED (Jeroen)`, amendment: exported, not internal, so a consumer can pack-resolve `ReviewGroup`/`SubmissionSuccess` props themselves per AC9); new optional field(s) on `StarterSettingsProperties`. No change to any chrome component's prop contract (internal, unexported); no change to `StarterFieldProperties`.
- No change to `packages/core/src/`.
- Dependencies: none on other stories; this is the first story and is purely additive. ST-02 depends on this story's `StarterLanguagePack` type definition (ASSUMED story-prep boundary: this story owns the type's full shape including its `messages` sub-shape, so ST-02 extends `enStarterPack.messages` using that shape instead of declaring a second type; alternative considered — ST-02 declares its own standalone messages type and the two are unified later — rejected as the same shape built twice, trivially reversible by moving the sub-shape declaration). ST-03 and ST-04 do not depend on this story but share the `StarterLanguagePack.locale` field this story's type also declares (OQ7).
- Changeset: this story creates the single shared changeset file (`.changeset/*.md`, **minor** bump, scoped to `@bach.software/vue-dynamic-form-starter`; no core changeset, `packages/core/src/` is untouched) with the lead-in text for the whole i18n capability (business purpose first, per CLAUDE.md's changeset-writing rule) and its own sub-bullet ("pack selection and precedence"). ST-02, ST-03, and ST-04 each append their own sub-bullet to this same file; ST-05 finalizes the wording. Do not create a second changeset file in a later story.
- `specs/components.md`: update the starter row for the exports this story adds (`enStarterPack`, `StarterLanguagePack`, the new `StarterSettingsProperties` field), per the standing CLAUDE.md rule that the developer updates this on every public-surface change. The full consolidated pass across the whole feature is ST-05's Documentation assignment.

### Reactivity / render-count plan

`resolvePackText` is specified as a pure function of `(explicit, pack, key)` reading only already-tracked reactive sources (`s.settings`, `s.fieldMetadata`), so it must add zero render passes per the architecture. `StarterFormTemplate.languagePack.analytics.test.ts` asserts this directly: switching `activePack` (AC6) must not bump the render count of a sibling field whose own text has no pack dependency, following the existing pattern in `StarterFormTemplate.wizard.analytics.test.ts`. This is the regression test that would catch a resolver accidentally introduced as a new reactive source (e.g. a fresh `computed` keyed oddly) causing an unrelated field to re-render.

### Coverage

New source this story adds, all of which needs direct test coverage: the `enStarterPack` object/module, the `StarterLanguagePack` type (type-only, covered by `expectTypeOf`, not runtime coverage), the `resolvePackText` resolver function (every branch: explicit hit including `''`, pack-object hit, pack-function hit, pack-function-returns-undefined, pack absent, per-tier object merge), and the modified lines in `StarterFormTemplate.vue` (every one of the ~25 bindings plus the 3 inline literals must be exercised at least once with a pack active and once with an explicit override active, which the mapping table above provides). Per the edge-case ASSUMED decision (no try/catch around a throwing/misbehaving custom lookup function), there is no defensive branch to cover; a throwing lookup function is expected to propagate, consistent with `computedProps`, and is not asserted against in a test (testing "it throws" would just pin an accidental behavior, not a designed one).

Run `pnpm -r ci:test:coverage` after implementation and confirm statement/branch/function coverage does not regress against the pre-story baseline; the new `resolvePackText` module in particular should read as fully branch-covered given the table above.

- **`StarterFormTemplate.vue`**: every existing chrome-string test that asserts "falls back to the built-in default" (`StarterFormTemplate.texts.logic.test.ts`, `.wizard.logic.test.ts`, `.array.logic.test.ts`, `.choice.logic.test.ts`, `.password.logic.test.ts`, `.wizard.overrides.logic.test.ts`) doubles as the regression guard for AC1/AC2: these must keep passing unmodified, since they exercise the "no pack selected" path that must stay byte-for-byte identical.

- **`index.ts` exports**: `publicApiSurface.test.ts` and `index.test.ts` both hardcode the full exported-name list (`Object.keys(api).sort()` / a literal array) and will fail the moment `enStarterPack`/`StarterLanguagePack` are exported without updating them. Same nature as the golden-metadata risk above: an intentional guard, not a false positive, but must be touched in the same change.
- **`PasswordStrengthBar.vue`**: untouched, but its own English-default backfill (`props.labels?.weak ?? 'Weak'`, etc.) is now load-bearing for AC5's per-tier fallback case; the existing tier-rendering tests in `StarterFormTemplate.password.logic.test.ts` must keep passing as the no-pack baseline.
- **Cross-story coupling**: ST-02 extends this story's `StarterLanguagePack.messages` sub-shape, and ST-03/ST-04 read `StarterLanguagePack.locale`. A shape change found during this story's own adversarial review ripples into those stories' architecture references; this QA plan does not attempt to pre-verify ST-02/ST-03/ST-04 against the type, only that the type exists with the fields the feature architecture specifies.
- **No `packages/core` change**: this story touches only `packages/starter`; the existing `packages/core` test suite is unaffected and is not part of this story's regression surface.

## Adversarial review
Reviewed lite (story level); blockers only, plus the QA plan's pre-flagged gap verified against source.

1. **(blocker) AC1 lists two chrome strings the approved feature Architecture gives this story no path to resolve. This is a gap in the FEATURE, not the story.** Verified against source:
   - `ReviewGroup.editButtonText` is a component prop with its own `withDefaults` of `'Edit'` (`packages/starter/src/ReviewGroup.vue:8,13`). In the template it is bound via `v-bind="group"`, where `group` iterates `s.fieldMetadata.wizardSummary?.groups ?? []` (`packages/starter/src/StarterFormTemplate.vue:594-599`). It is consumer-supplied per-group content, not one of the "~25 chrome-string prop bindings" the feature Architecture's Modified list routes through the resolver, and that list never describes defaulting a group's missing `editButtonText` from the pack.
   - `SubmissionSuccess` is never imported or rendered inside `StarterFormTemplate.vue` (confirmed: no import in the component's import block, no usage in the template). It is a standalone export (`packages/starter/src/index.ts:20`) that a consumer places outside `DynamicForm` in their own page (e.g. `docs/.vitepress/theme/components/FormExampleWizard.vue`, `playgrounds/storybook/components/StarterSuccessPreview.vue`), so it never receives `s.settings` and has no access to `activePack`. The feature Architecture lists it under "Reused unchanged".
   - Yet the feature's **Functional overview** (spec line 72: "the review screen's edit button, the submission-success screen's labels") and the feature **Design > Mapping to existing components** (spec line 120: "Review / success -> `ReviewGroup` / `SubmissionSuccess` (edit button, confirmation title, reference label, JSON toggle, reset button, timeline title)") both promise these are pack-covered chrome. The feature **Architecture** section provides no wiring for either. So the feature contradicts itself: its own design claims pack coverage that its architecture cannot deliver.
   - Because the story's AC1/AC2-AC4/AC6 ("every chrome string ... the review edit button, the submission-success labels") inherit that promise, the story cannot be implemented and verified as written. Per hard rule 4 a story may not silently narrow scope that contradicts the approved feature, and per `specs/RESEARCH-AND-DECIDE.md` this is case 3 (an approved feature has a real gap; every resolution option changes what ships in a way Jeroen would notice). The missing feature sections are: **Architecture > Modified (backward compatible)** (never specifies wiring the pack into the `wizardSummaryPage` block's per-group `editButtonText`), and **Architecture > Reused unchanged** together with **Design > Mapping to existing components** (both name `ReviewGroup`/`SubmissionSuccess` as pack-covered chrome while the architecture has no mechanism to reach either, and `SubmissionSuccess` is rendered outside the template entirely).
   - This confirmed, with source evidence, the gap the qa-planner already routed here (QA plan > Untestable / inconsistent acceptance criteria). `DECIDED (Jeroen)`: resolved by option (b)-adjacent, not (a): rather than wiring the template into components it cannot reach, the feature spec is amended (Functional overview, Design > Mapping to existing components, Architecture > Public API impact) to export `resolvePackText` (and, for ST-04, the date-display util) so a consumer can call the same resolver themselves when building their own `ReviewGroup`/`SubmissionSuccess` usage. AC1/AC2/AC4/AC6 are narrowed to the template-rendered string set; AC9 (new) covers the export guarantee. This is a public-API addition (one more named export), recorded in the feature's Public API impact and Changeset sub-bullet.

No other story-level blocker found: all nine ACs are mapped in the QA plan table, the per-tier `strengthLabels` merge (AC5), the custom-lookup-function fallthrough (AC7), the template-prop-wins-for-chrome-only rule (AC8), and the exported-resolver guarantee (AC9) are each consistent with the approved feature (AR-6, ADR 5/OQ1, ADR 4/OQ6), and the story's dependency note (none inbound; ST-02 depends on this story's `StarterLanguagePack` type) is explicit and matches the feature's Stories section.
