Repeatable choice occurrence ordering

Design surface for FEAT-002, an additive layer on top of FEAT-001's repeatable explicit choice (explicitChoiceSelection: true with maxOccurs > 1). It grows the docs example docs/examples/choices.md → "Add several, each one of several kinds" and its template components (RepeaterCard.vue, AdvancedFormTemplate.vue's default-choice-array-item slot, ChoiceArraySectionCard.vue) to demonstrate two things: a continuous cross-branch numbering badge, and an optional add-order (interleaved) display. Flip the toggle top-right to review every section in dark.

Domain data throughout is the live example's Integrations to add choice: two branches, CRM export and API endpoint. Shared budget is 5; each branch's own maxOccurs is 3.

Provisional API names used in annotations (final names are the architect's call). Decided: globalIndex (new -choice-array-item slot prop). Provisional: an ephemeral per-occurrence insertion counter shown here as insertionOrder, and an opt-in metadata flag shown here as preserveOrder: true that writes an order field into each occurrence's values.
1 · Continuous numbering (globalIndex)

Today each occurrence's badge is index + 1, its position inside its own branch. Mixing branches makes the numbers restart per kind (1, 2, 1, 2), which reads as a bug to a form filler. The new globalIndex slot prop is the loop index over the engine's existing activeChoiceOccurrences, so the template can show a single continuous 1..N sequence across all branches. It is always live-derived, never stored; removing an occurrence renumbers the survivors.

2 · Ordering modes (grouped vs add-order)

The engine's activeChoiceOccurrences stays grouped by branch (FEAT-001's Q8 guarantee), and that grouped order is the untouched default. A template can opt in to displaying occurrences in the order their Add buttons were pressed (interleaved) using a per-occurrence add-order value. Two tiers supply that value: a default ephemeral engine counter (resets on reload), and an opt-in preserveOrder metadata flag that persists an order field into the submitted values. The demo toolbar below lets a docs reader flip between them and watch both the cards and the submitted JSON react.

On page reload or when loading previously saved data the counter is gone, so this mode silently falls back to grouped order. To make add-order survive a reload, turn on preserveOrder (next section).

DOM order now equals visual order (the template physically reorders the cards, not a CSS order trick), so keyboard Tab traversal and screen-reader order follow the interleaved sequence. The CSS-only approach that would have split DOM and visual order was rejected (Q2 research finding).

5 · Docs & component impact

Docs example (docs/examples/choices.md, "Add several, each one of several kinds"): add the continuous-numbering before/after explanation, replace the flat "grouped, never click order" warning with the two-tier ordering explanation (grouped default, ephemeral add-order, persisted preserveOrder), and keep the live JSON dump so the order field is visible when persisted. The existing grouped-order guarantee statement stays, reframed as "the default, which the ordering layer sits on top of".

Template components: AdvancedFormTemplate.vue's default-choice-array-item slot binds the new globalIndex to RepeaterCard's badge (replacing :index for the badge value; index stays available for keys and remove wiring). ChoiceArraySectionCard.vue and the heading-choice-array slot gain the toolbar controls (display-order segmented control and the preserveOrder toggle) that FormExampleChoiceExplicitRepeatable.vue drives.

New metadata / slot surface (for specs/components.md, architect finalizes names): globalIndex on the -choice-array-item slot; a per-occurrence ephemeral insertion counter on the choice slot props; a preserveOrder metadata flag writing an order field into occurrence values. All additive and off by default: a FEAT-001 consumer who ignores them is byte-for-byte unaffected.

Live site check (2026-09-15): vue-dynamic-form.bach.software still shows the pre-FEAT-001 choices page (no "Add several" section deployed yet). The repo docs/ source is the authoritative target for these deltas; the deployed content will catch up on the next merge to main.
