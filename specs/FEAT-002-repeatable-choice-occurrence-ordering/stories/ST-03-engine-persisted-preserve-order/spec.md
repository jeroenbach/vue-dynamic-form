# Story: Persisted `preserveOrder` (`order` in occurrence values)

## Functional
### User story
As a template author, I want an opt-in mode where a repeatable explicit choice's add-order is written into each occurrence's own submitted values as an `order` field, so that the interleaved order survives a page reload or loading previously saved data, at the accepted price of `order` becoming part of the submitted shape.

### Acceptance criteria

1. **`preserveOrder: true` writes `order` on add.**
   Given a choice with `preserveOrder: true` on an object-shaped branch (its occurrence has `children`),
   When `addChoiceOccurrence(branchKey)` is called,
   Then the new occurrence is pushed with `order` already set to `activeCount + 1` (via `push({ order: n, ... })`, not a separate write after push, avoiding a null-to-object transition), where `activeCount` is the count of active occurrences across the whole choice before this add.

2. **Compaction on removal keeps `order` contiguous (Q6).**
   Given 4 occurrences across branches with `order` 1, 2, 3, 4,
   When the occurrence holding `order: 2` is removed,
   Then the 3 survivors' `order` values are rewritten to 1, 2, 3 (contiguous, no gap), each write using `setFieldValue(..., n, false)` (`shouldValidate: false`), and the next occurrence added afterward gets `order: 4`.

3. **Mount-time backfill for occurrences loaded without `order` (AR-2).**
   Given saved data is loaded where a choice has `preserveOrder: true` but some or all existing occurrences lack an `order` field,
   When the form mounts, before any add-press occurs,
   Then a one-time backfill pass assigns `order` to every occurrence missing it, based on its current grouped (`activeChoiceOccurrences`) position, so the counter and any subsequent sort always see a contiguous 1..N sequence.

4. **Render sort uses `order` (not `insertionOrder`) when `preserveOrder` is on.**
   Given `preserveOrder: true` and `displayOrder: 'added'` together,
   When `renderedChoiceOccurrences` is computed,
   Then the sort key is each occurrence's `order` value (not the ephemeral `insertionOrder`), and this holds correctly across a remount (unlike `insertionOrder`, `order` survives it, since it lives in the vee-validate `values` tree).

5. **Persistence is orthogonal to display (design decision 3).**
   Given `preserveOrder: true` but `displayOrder` absent/`'grouped'`,
   When occurrences are added and removed,
   Then `order` is still written on add and compacted on removal exactly as in AC1/AC2, even though the DOM/render order stays grouped (unaffected by `preserveOrder` alone).

6. **`order` is real submitted data (Q4).**
   Given `preserveOrder: true` with occurrences added,
   When the raw submitted `values` object is inspected (e.g. via `removeNullValues(values)` or directly at `handleSubmit`),
   Then each occurrence's `order` key is present with its numeric value; `removeNullValues` does not strip it (it is a non-nullish leaf, not special-cased).

7. **`xsd_choiceMinOccurs` and the shared budget are unaffected by `order` (the load-bearing validation analysis).**
   Given a choice at `minOccurs: 1` with `preserveOrder: true`, and one occurrence added but its own required child field left empty,
   When validation runs,
   Then `xsd_choiceMinOccurs` is already satisfied (the occurrence counts structurally, exactly as without `preserveOrder`), but the occurrence's own required child field still shows its own validation error; the shared per-branch occurrence budget (`canAddChoiceOccurrence`) is unaffected by whether `order` is present.

8. **Scalar-leaf branch is a no-op with a dev warning, not silent corruption (AR-4).**
   Given `preserveOrder: true` on a choice where one branch's occurrence is a scalar leaf (no `children`, e.g. `type: 'text'`) and another branch's is an object,
   When an occurrence of the scalar-leaf branch is added,
   Then no `order` write happens for that branch (the push stays a plain scalar/`null` placeholder as today) and a `console.warn` naming the branch fires in dev mode; the object-shaped branch in the same choice still gets `order` written normally.

   PROPOSED (adversarial review): pin the warn cadence so the developer does not guess (QA flag 2). The warning fires on **every** add-press of a scalar-leaf branch, with **no deduplication** for the component's lifetime (the stateless "fail loud" reading, consistent with ADR-3/feature finding 4's rationale; no dedup mechanism is named anywhere in the architecture). A dedup implementation would therefore be a deliberate deviation from this AC, not an implementation detail, and must be flagged as such rather than chosen silently. Tested by the "scalar-only choice" edge case, which adds the scalar branch several times and asserts a warn per add.

9. **`preserveOrder` is static, read once at setup.**
   Given `preserveOrder` is set in the initial metadata,
   When a `computedProps` function attempts to mutate `thisField.preserveOrder` at runtime,
   Then the change has no effect (excluded from `ComputedPropsFieldType`, mirroring its sibling static flags).

### Edge cases
- Removing the same occurrence a second time (already removed / index out of range): existing `removeChoiceOccurrence` no-op behaviour is preserved; compaction does not run for a no-op removal.
- All occurrences already carry contiguous `order` on mount: the backfill pass detects nothing missing and performs zero writes.
- A choice with two branches, one object-shaped and one scalar-shaped, where the scalar branch is the only one ever used: no `order` ever appears anywhere in that choice's values, and no crash occurs.
- `preserveOrder: true` on a `maxOccurs: 1` explicit choice: no effect (this story, like ST-02, is `maxOccurs > 1` only; `preserveOrder` has no meaning where there is no per-branch field array to push an `order`-bearing item into).
- **PROPOSED (adversarial review) - legacy occurrences carrying a non-contiguous or duplicate `order` (QA flag 3).** The mount-time backfill (AC3) only writes `order` for occurrences **missing** it; an occurrence that already carries a numeric `order` is trusted as-is and never renumbered on mount, even when that value is non-contiguous (e.g. `5, 10, 20`) or duplicated (e.g. `1, 1, 1`). Consequence to state and test: the contiguous 1..N invariant is guaranteed only for engine-produced data and for the all-missing legacy dataset AR-2 was written to migrate; a hand-authored non-contiguous/duplicate `order` set is trusted, only sorted (the ascending-`order` render sort and the two-key comparator both remain deterministic over any numeric set, ties broken by grouped position), and **self-heals to contiguous 1..N on the next removal**, because compaction re-ranks survivors by their current `order`. Known wart to document, not fix: with a non-contiguous legacy set the add-counter (`activeCount + 1`) can collide with or sort ahead of higher legacy values (e.g. loading `5, 10, 20` then adding gives `order: 4`, which sorts first) until a removal compacts. Test: seed `apiEndpoint[0].order = 5, apiEndpoint[1].order = 10, crmExport[0].order = 20`, `preserveOrder` on; assert backfill leaves all three untouched; assert `displayOrder: 'added'` sorts them ascending by `order`; then `removeChoiceOccurrence` one and assert survivors compact to contiguous `1, 2`. If Jeroen instead wants the contiguity invariant upheld for **all** legacy data (a full mount normalization pass that re-ranks pre-existing `order` too, not just backfills missing), that widens the decided scope of feature finding 2 ("onto any occurrence missing it") and must amend the feature spec first, not be added silently here.

### Out of scope
- Any `DynamicFormSettings` change: none ships (Q8 decided against that channel).
- Any docs/example UI exercising `preserveOrder` or the submitted-values JSON display: ST-05.
- Configuring the `order` key's name (e.g. via settings): explicitly rejected as YAGNI (ADR-3); the key is a fixed `order`.
- Any behaviour for a branch whose child is literally named `order` (documented collision, consumer's responsibility to rename or not opt in; not engine-enforced beyond what AR-4 already covers for the scalar case).

## Design reference
Feature prototype (`../../prototype.html`): `#ordering-preserve` (add-order display with `preserveOrder` on, `order` visible in fields), `#ordering-values` (submitted-values JSON compare, `order` key present vs absent), `#ordering-removal` (removal compacts `order` to 1..N), `#reload-behavior` (the persisted half: reconstructs exactly from `order`). This story delivers the engine mechanism only; the toolbar and live JSON dump a reader interacts with are ST-05's docs slice.

## Architecture reference
Builds on ST-02's `renderedChoiceOccurrences` sort infra (this story adds `order` as an alternative sort key alongside `insertionOrder`) and on FEAT-001/ST-05's static-flag pattern, against the feature architecture's Slice C, ADR-3, and the DECIDED (research) resolutions of adversarial findings 2, 3 (partially, shared with ST-02), and 4.

- **`packages/core/src/types/FieldMetadata.ts` (modified).** Add `preserveOrder?: boolean` (default `false`) next to `displayOrder`; add to the `ComputedPropsFieldType` `Omit` list.
- **`packages/core/src/components/DynamicFormItemChoice.vue` (modified).**
  - Static capture: `const preserveOrder = props.fieldMetadata?.preserveOrder === true`.
  - `addChoiceOccurrence`'s `maxOccurs > 1` branch: when `preserveOrder` is on and the target branch's occurrence shape is an object (the branch child declares `children`), push `{ order: activeCount + 1 }` instead of `null`; when the branch is scalar-leaf (no `children`), skip the `order` write for that branch and emit `console.warn` (dev-mode only, matching the Vue-ecosystem misconfiguration-warning convention) naming the branch.
  - `removeChoiceOccurrence`'s `maxOccurs > 1` branch: after `branchFieldArrays[...].remove(index)`, when `preserveOrder` is on, collect the surviving occurrences across all branches, compute each survivor's new contiguous rank, and for every survivor whose rank changed, call `formContext.setFieldValue(occurrencePath + '.order', newRank, false)` (mirroring the existing `clearBranch`/`restoreStashedBranch` `setFieldValue(..., false)` pattern).
    - PROPOSED (adversarial review): the survivor set for compaction must **exclude scalar-leaf occurrences** (branches with no `children`), for the same AR-4 reason the add-time write skips them: writing `occurrencePath + '.order'` onto a scalar placeholder would convert it into an object `{ order: n }`, the exact silent corruption AR-4 exists to prevent. Only object-shaped survivors are collected, ranked, and rewritten. Already pinned indirectly by the "scalar-only choice" edge case (which removes across scalar survivors and asserts no `order` key ever appears), but stated here so the exclusion is not left to inference in a mixed active set.
  - Setup-time (mount) pass, gated on `preserveOrder`: for every occurrence in `activeChoiceOccurrences` missing `order`, backfill it from that occurrence's current grouped position via `setFieldValue(..., n, false)`, once, before the first `addChoiceOccurrence` call can run (AR-2 mechanism).
  - `renderedChoiceOccurrences` (introduced in ST-02): when `displayOrder` is `'added'`, the sort key becomes each occurrence's `order` value when `preserveOrder` is on, falling back to `insertionOrder` (ST-02's ephemeral tier) otherwise; both use the same deterministic missing-value-first comparator shape.
- **No new slot prop for `order` itself.** Unlike `globalIndex`/`insertionOrder`, `order` is a real field inside the occurrence's own value object; a template reads it like any other child field (e.g. via `fieldContext.value` inside the occurrence's own fields), not through a dedicated `ChoiceArrayItemAttributes` property. No `DynamicFormTemplate.vue` type change is needed for this story.
- **Public API surface touched:** `FieldMetadata.preserveOrder?: boolean` (additive, `ComputedPropsFieldType`-excluded). No slot-prop or `DynamicFormSettings` change. **Changeset: `minor`**, this story's own entry.
- **Dependencies:** ST-02 (shares the `renderedChoiceOccurrences` computed and its two-key sort shape, which this story extends with the `order`-vs-`insertionOrder` key choice).
- **`specs/components.md`:** update the `DynamicFormItemChoice` row and the `FieldMetadata` list once implemented.

## QA plan

This story extends the FEAT-001/ST-01/ST-02 repeatable-explicit-choice fixtures already established in `DynamicFormItemChoice.logic.test.ts`/`.validation.test.ts`/`.analytics.test.ts` (the `apiEndpoint`/`crmExport` two-branch fixture, `apiEndpoint` declared before `crmExport`, per ST-02's adversarial-review correction). No new shared test-harness component is needed, and unlike ST-01/ST-02 **no `TestFormTemplate.vue` change is needed at all**: per the architecture, `order` gets no dedicated slot prop, it is a plain field inside the occurrence's own value object, read through `formValues(wrapper)`/`removeNullValues`, never through a testid. This keeps this story's fixture footprint smaller than ST-01/ST-02's.

Three fixture shapes are used, each a locally scoped `mount*` helper inside the new describe block (mirroring the file's existing per-`describe` fixture-function convention, e.g. `mountExplicitRepeatableChoice`, `mountPreserveOnSwitchChoice`):

- **Object branches, both branches** (`mountExplicitRepeatableChoiceObjectBranches`): `apiEndpoint` (`children: [{ name: 'url' }]`) declared before `crmExport` (`children: [{ name: 'system' }]`), choice `maxOccurs: 5`, each branch `maxOccurs: 3`. Used for AC1, AC2, AC3 (backfill), AC4, AC5, AC6, AC7, AC9, and the compaction/backfill analytics tests, since `preserveOrder` needs an object-shaped occurrence to attach `order` to.
- **Mixed branches** (`mountExplicitRepeatableChoiceMixedBranches`): `apiEndpoint` scalar (`type: 'text'`, no `children`, matching today's FEAT-001 fixture shape) declared before `crmExport` object (`children: [{ name: 'system' }]`). Used for AC8 (scalar-leaf no-op + warn) and the "scalar-only choice, no `order` ever appears" edge case.
- **Scalar branches, both branches** (reuses the existing `mountExplicitRepeatableChoice` from the `explicit selection — maxOccurs>1` describe block, unmodified): used for the "no visual/DOM footprint" byte-identical regression check and the maxOccurs:1 no-op check (reusing `mountExplicitSingleChoice`, ST-01's fixture).

### Acceptance criteria → test mapping

1. **`preserveOrder: true` writes `order` on add.**
   Using `mountExplicitRepeatableChoiceObjectBranches` with `enablePreserveOrder(metadata, 'pick')`: `addChoiceOccurrence('apiEndpoint')` then assert `formValues(wrapper).pick.apiEndpoint[0].order === 1` immediately after the first `flushPromises()` (no second tick needed to "settle"). Then `addChoiceOccurrence('crmExport')` → `pick.crmExport[0].order === 2`; then `addChoiceOccurrence('apiEndpoint')` again → `pick.apiEndpoint[1].order === 3`. This proves the counter is the shared, cross-branch `activeChoiceOccurrences.length` (not a per-branch counter): `crmExport[0]` gets `2`, not `1`, because `apiEndpoint[0]` already existed. `DynamicFormItemChoice.logic.test.ts`.

   The "not a separate write after push... avoiding a null-to-object transition" clause is tested at the outcome level only (see Flags for reviewer): the value is correct immediately, and stays stable (unchanged) across a second `flushPromises()` with no further mutation, which is the observable consequence a consumer could rely on; Vue's synchronous-mutation batching makes "one `push({order})` call" and "a `push(null)` immediately followed by a same-tick `setFieldValue`" behaviourally indistinguishable by render count, so no test enforces the single-call mechanism directly.

2. **Compaction on removal keeps `order` contiguous (Q6).**
   Continuing from AC1's sequence, add `addChoiceOccurrence('crmExport')` once more so four occurrences exist: `apiEndpoint[0].order=1, crmExport[0].order=2, apiEndpoint[1].order=3, crmExport[1].order=4` (matching the story's own literal example). Remove the occurrence holding `order: 2` (`crmExport[0]`, via `removeChoiceOccurrence('crmExport', 0)`). Assert the three survivors now read `order` `1, 2, 3` respectively (`apiEndpoint[0]=1` unchanged, `apiEndpoint[1]=2`, `crmExport[1]=3`, re-ranked by their prior `order`), with no gap. Then `addChoiceOccurrence('crmExport')` once more and assert its `order === 4` (`count + 1`, `count` being the 3 survivors). `DynamicFormItemChoice.logic.test.ts`.

   `shouldValidate: false` is asserted indirectly, mirroring the project's existing `restoreStashedBranch` precedent (no test spies on `formContext.setFieldValue` directly): after the removal above, assert that a still-empty required child field inside a re-ranked survivor (e.g. `apiEndpoint[1].url`, left empty throughout) does **not** show its own error message immediately after the compaction write, i.e. the write that changed its `order` did not also flip it into a validated/touched state.

3. **Mount-time backfill for occurrences loaded without `order` (AR-2).**
   Three variants, all on `mountExplicitRepeatableChoiceObjectBranches` with `preserveOrder` enabled and `initialValues` seeded (no `addChoiceOccurrence` call this session, so any write is attributable only to the backfill pass):
   - **All missing:** seed `apiEndpoint[0]={url:'a'}, apiEndpoint[1]={url:'b'}, crmExport[0]={system:'c'}` (no `order` anywhere). Assert immediately after mount (before any add-press) `pick.apiEndpoint[0].order===1, pick.apiEndpoint[1].order===2, pick.crmExport[0].order===3` (grouped position, `apiEndpoint` first). Then `addChoiceOccurrence('crmExport')` and assert the new occurrence's `order === 4`, proving the counter and the sort see the backfilled values as the baseline.
   - **Selectively missing:** seed `apiEndpoint[0]={url:'a', order:1}` (already has one), `apiEndpoint[1]={url:'b'}` (missing), `crmExport[0]={system:'c'}` (missing). Assert `apiEndpoint[0].order` is untouched (`1`), and the two missing ones are backfilled from grouped position (`apiEndpoint[1].order===2`, `crmExport[0].order===3`), proving only missing occurrences are written, not a blanket renumber.
   - **Zero missing (edge case, restated below):** all three already carry contiguous `order` (`1,2,3`); assert values are byte-identical before/after mount and (analytics) each occurrence's render count is exactly the baseline mount count with no extra write-triggered render, proving the backfill pass performs zero writes.
   `DynamicFormItemChoice.logic.test.ts` for the value assertions; the render-count halves of variants 1-3 are cross-checked in `.analytics.test.ts`.

4. **Render sort uses `order` (not `insertionOrder`) when `preserveOrder` is on.**
   The differentiating test against ST-02: mount `mountExplicitRepeatableChoiceObjectBranches` with both `enablePreserveOrder(metadata, 'pick')` and `enableDisplayOrder(metadata, 'pick', 'added')` (ST-02's helper, reused). Press in a deliberately non-grouped order: `crmExport`, `apiEndpoint`, `crmExport` → `order` `1, 2, 3` respectively (`crmExport[0]=1, apiEndpoint[0]=2, crmExport[1]=3`); assert `renderedChoiceOccurrences(wrapper,'pick')` equals `[{branchKey:'crmExport',index:0},{branchKey:'apiEndpoint',index:0},{branchKey:'crmExport',index:1}]` (interleaved, driven by `order`). Then **remount a fresh wrapper** with `initialValues: formValues(firstWrapper)` and no add-press this session (so every occurrence's ephemeral `insertionOrder` is `undefined` in the new instance — the exact condition under which ST-02's own sort would fall back to grouped order). Assert `renderedChoiceOccurrences` on the remounted wrapper is the **same interleaved sequence**, not the grouped one, proving the sort key genuinely switched to the persisted `order` and survives the remount ST-02's `insertionOrder` cannot survive. `DynamicFormItemChoice.logic.test.ts`.

5. **Persistence is orthogonal to display (design decision 3).**
   Same object-branch fixture, `preserveOrder` on, `displayOrder` **absent**. Press `crmExport`, `apiEndpoint`, `crmExport` (the same non-grouped sequence as AC4). Assert `order` values are still written exactly as in AC1/AC2 (`1, 2, 3`), but `renderedChoiceOccurrences(wrapper,'pick')` equals `activeChoiceOccurrences(wrapper,'pick')` (grouped: `apiEndpoint[0], crmExport[0], crmExport[1]`), **not** the press-order sequence — directly proving persistence and display are independent knobs. `DynamicFormItemChoice.logic.test.ts`.

6. **`order` is real submitted data (Q4).**
   Add two occurrences across both branches on the object-branch fixture, then: (a) `Object.keys(formValues(wrapper).pick.apiEndpoint[0])` contains `order` alongside the declared child (`url`), the inverse assertion of ST-01/ST-02's "no injected key" checks; (b) `removeNullValues(formValues(wrapper)).pick.apiEndpoint[0].order` is present and equals the same numeric value, proving it is not stripped; (c) a submit-capture round-trip (`click submit`, re-read `formValues`) shows `order` still present, mirroring the existing `removeNullValues` test pattern at `DynamicFormItemChoice.logic.test.ts:1194-1220`. `DynamicFormItemChoice.logic.test.ts`.

7. **`xsd_choiceMinOccurs` and the shared budget are unaffected by `order` (the load-bearing validation analysis).**
   Extends the existing "the occurrence's own required fields still validate independently once the occurrence holds some data" test (`DynamicFormItemChoice.validation.test.ts:707-749`) with `preserveOrder: true` added to the choice metadata: add one `apiEndpoint` occurrence (its `order` gets written automatically), fill only `token`-equivalent sibling child, leave `url` empty, submit. Assert the choice-level `pick-error-message` is absent (already satisfied structurally, `order`-only or not) while `pick.apiEndpoint[0].url-error-message` is present (the occurrence's own required field still enforces independently). A second, byte-identical-outcome test: run an identical add/remove-to-budget-exhaustion sequence on two wrappers, `preserveOrder` on and off, and assert `canAddChoiceOccurrence(wrapper,'pick',branchKey)` and `pick-error-message` presence are identical at every step, directly pinning "changes no validation outcome and no occurrence-budget outcome". `DynamicFormItemChoice.validation.test.ts`.

   A companion **byte-identical rendered HTML** regression test belongs here too (see Regression risk): since `order` has no slot prop, `wrapper.html()` for the choice/occurrence DOM should be identical whether `preserveOrder` is on or off, proving the persisted tier has zero visual footprint, exactly as the architecture states.

8. **Scalar-leaf branch is a no-op with a dev warning, not silent corruption (AR-4).**
   Using `mountExplicitRepeatableChoiceMixedBranches` (`apiEndpoint` scalar, `crmExport` object) with `preserveOrder` enabled: spy on `console.warn` (`vi.spyOn(console, 'warn').mockImplementation(() => {})`, restored in an `afterEach`/local `try/finally`, no existing precedent for this in the suite so this is a new pattern introduced by this story). `addChoiceOccurrence('apiEndpoint')`: assert `formValues(wrapper).pick.apiEndpoint[0]` is `null` (unchanged, no `order` key, byte-identical to today's plain placeholder), and `console.warn` was called with a message naming `'apiEndpoint'`. Then `addChoiceOccurrence('crmExport')`: assert `pick.crmExport[0].order === 2` (**not** `1`) — the shared counter still counts the scalar placeholder structurally (`activeChoiceOccurrences.length` before this push is `1`), even though that placeholder itself never received an `order` value; this is the sharpest test of "the object-shaped branch in the same choice still gets `order` written normally" against the correct arithmetic. `DynamicFormItemChoice.logic.test.ts`.

9. **`preserveOrder` is static, read once at setup.**
   Two tests, mirroring ST-02 AC8 / FEAT-001's `explicitChoiceSelection is static metadata, not computed` line for line. (a) Runtime: mount the object-branch fixture with `preserveOrder: true` and a `computedProps: [(thisField: any) => { thisField.preserveOrder = false; }]` on the choice; add an occurrence; assert `order` is still written (the mutation has no effect). (b) Type-level: `@ts-expect-error preserveOrder is excluded from ComputedPropsFieldType` inside a `ComputedPropsFieldOf<Metadata>`-typed function, checked by `pnpm typecheck`. `DynamicFormItemChoice.logic.test.ts`.

**Edge cases** (same new describe block):
- **Removing the same occurrence a second time (already removed / index out of range).** Extends the existing no-op removal test (`DynamicFormItemChoice.logic.test.ts:1821-1834`, `removeChoiceOccurrence('apiEndpoint', 99)`) with `preserveOrder: true`: assert the existing no-op behaviour is unchanged (array length/`activeChoiceOccurrences` untouched) **and** that no other occurrence's `order` value changed as a side effect (compaction did not run for the no-op removal).
- **All occurrences already carry contiguous `order` on mount.** Covered as AC3's third variant above (zero writes, render count at baseline).
- **Scalar-only choice, scalar branch the only one ever used.** On the existing plain scalar `mountExplicitRepeatableChoice` fixture (both branches scalar) with `preserveOrder: true`: add and remove occurrences across both branches several times; assert no occurrence ever holds an `order` key anywhere (`pick.apiEndpoint`/`pick.crmExport` stay arrays of plain strings/`null`, never objects), `console.warn` fires for every add (naming the correct branch each time), and nothing throws.
- **`preserveOrder: true` on a `maxOccurs: 1` explicit choice: no effect.** Reuses `mountExplicitSingleChoice` (ST-01's fixture) with `preserveOrder: true` added. Assert `wrapper.html()` after a selection is byte-identical to the same fixture with `preserveOrder` absent (mirrors ST-02 AC10's technique), and `formValues(wrapper).pick.selfServe` is the plain scalar value, never an object with an injected `order` key.

### States policy (this slice)

Per the feature's states policy, this slice ships no visible output of its own (no slot prop, no DOM change; see architecture's "No `DynamicFormTemplate.vue` type change is needed for this story"). The relevant states to confirm at the data level:
- **Default** (`preserveOrder` absent/false): byte-identical to today, confirmed by the AC7 companion HTML-identity regression test and by the full existing FEAT-001/ST-01/ST-02 suites remaining green, unmodified.
- **Populated** (1+ occurrences, `order` present): AC1, AC2, AC4, AC5.
- **Loaded/legacy data missing `order`:** AC3 (backfill), all three variants.

### Flags for reviewer

- **AC1's "not a separate write after push... avoiding a null-to-object transition" is tested at the outcome level only, not the mechanism level.** Vue's synchronous-mutation batching means "one `push({order})` call" and "a same-tick `push(null)` followed by `setFieldValue`" are indistinguishable by render count or by any test in this suite's existing toolkit; the plan proves the outcome (`order` correct immediately, stable across a second tick) instead. Flagging for confirmation this is sufficient, consistent with the ST-01 AC2 / ST-02 AC4 precedent of testing a negative/mechanism claim through its observable consequences.
- **The `console.warn` dedup semantics are unspecified by the AC.** AC8 says a warning "fires" when an occurrence of the scalar-leaf branch is added; it does not say whether a second add of the same scalar branch warns again or is deduplicated for the component's lifetime. The plan tests "warns on every add-press of a misconfigured branch" (the simpler, stateless reading, and the one consistent with "fail loud" per finding 4's rationale), since no dedup mechanism is named anywhere in the architecture. Flagging so the developer does not need to guess, and so a dedup implementation (if chosen instead) is recognized as a deliberate deviation from this plan's assumption, not a test bug.
- **AC3's backfill is tested as "only missing occurrences are written, pre-existing `order` values are never touched or renumbered even if non-contiguous."** This is the plan's reading of "assigns `order` to every occurrence missing it" (Data flow section), but the spec does not explicitly state what happens to a pre-existing, non-contiguous `order` value on a legacy occurrence that already has one (e.g. `order: 99` sitting next to freshly backfilled `1, 2, 3`). The plan does not test that scenario's long-term consequences (e.g. whether a later removal's compaction pass would then produce a genuinely non-contiguous result, since compaction re-ranks by current `order` value, not by position). This is flagged as an untested combination rather than a defect: it falls outside every stated AC and edge case, and "migrate cleanly from a feature-predating dataset" (all occurrences uniformly missing `order`) is the scenario AR-2 was actually written to solve.
- **The compaction analytics bound (item 2 above) is contingent on `setFieldValue` writes being individually observable as per-occurrence render deltas**, the same indirect-proof style ST-01/ST-02 used for their own negative/bound claims. If the implementation batches multiple survivors' writes into a single reactive flush in a way that changes this render-count arithmetic, the bound's *number* (`+1` per changed survivor) may need adjusting, though the qualitative claim (bounded, no remount, unaffected survivors get zero extra renders) would still hold either way.
- **Item 5 of the analytics plan (recompute-count parity for `_analytics_renderedChoiceOccurrencesCalculatedCount`) is contingent on ST-02 shipping that counter**, which is itself a `PROPOSED (adversarial review, finding 3)` edit on ST-02's own spec, not yet implemented.
