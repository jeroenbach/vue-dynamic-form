# Story: Ephemeral `insertionOrder` and the `displayOrder` render-order channel

## Functional
### User story
As a template author rendering a repeatable explicit choice, I want an opt-in, instance-local record of the order in which occurrences were added (across branches), and a static per-choice flag that makes the engine actually render occurrences in that add-order instead of grouped-by-branch order, so that I can build an interleaved display without writing anything into form `values`.

### Acceptance criteria

1. **Default is byte-identical to today (flag absent/`'grouped'`).**
   Given a repeatable explicit choice with `displayOrder` absent or `'grouped'`,
   When occurrences are added, removed, and re-rendered,
   Then the engine's `renderedChoiceOccurrences` (the new internal render-list computed) is identical, in both membership and order, to `activeChoiceOccurrences`; DOM order and every `globalIndex` value are byte-identical to ST-01's behaviour.

2. **`insertionOrder` is assigned at add-press time, in press order, across branches.**
   Given `addChoiceOccurrence('crmExport')`, then `addChoiceOccurrence('apiEndpoint')`, then `addChoiceOccurrence('crmExport')` again,
   When each occurrence's `-choice-array-item` slot is read,
   Then the three occurrences report `insertionOrder` `1`, `2`, `3` respectively, matching click order, independent of their grouped (branch-then-index) position.

3. **`insertionOrder` is `undefined` for occurrences never added this session.**
   Given a choice mounted with pre-existing (loaded) occurrences already in the value tree,
   When their `-choice-array-item` slots render, with no add-press having occurred yet this session,
   Then their `insertionOrder` is `undefined`.

4. **`insertionOrder` never reaches form `values`.**
   Given any mix of added occurrences,
   When the raw submitted `values` object is inspected (e.g. at `handleSubmit`),
   Then no `insertionOrder`-shaped key appears anywhere in it; the counter lives only in an instance-local ref, exposed solely as slot-prop data.

5. **`displayOrder: 'added'` sorts the render list with a deterministic two-key comparator (AR-3).**
   Given a choice with `displayOrder: 'added'`, mounted with pre-existing occurrences (no `insertionOrder`) and then one new occurrence added this session,
   When `renderedChoiceOccurrences` is computed,
   Then occurrences with no `insertionOrder` come first, ordered by their grouped (branch-then-index) position, followed by occurrences that do have an `insertionOrder`, ordered ascending by that value; no `NaN`/implementation-defined ordering ever occurs for the mixed case.

6. **`globalIndex` reflects the displayed sequence, not the grouped one, when interleaved.**
   Given `displayOrder: 'added'` and the mixed set from AC5,
   When each occurrence's `-choice-array-item` slot renders,
   Then `globalIndex` is that occurrence's position within `renderedChoiceOccurrences` (the sequence actually shown), so `globalIndex + 1` still reads a clean 1..N of what the reader sees, per design decision 2.

7. **Interleaved reorder preserves component/field state (no remount).**
   Given occurrences already rendered in grouped order with some field data entered,
   When an add-press changes the sort so `renderedChoiceOccurrences`'s order changes,
   Then existing occurrences' `DynamicFormItem` instances are reused (same Vue keyed `v-for` instance, since keys are the stable `occurrenceKey`, unaffected by display order), preserving entered field values, touched/validation state, and focus, not remounting them.

   PROPOSED (adversarial review, finding 2): reword the When clause. Under the decided AR-3 append-only stable comparator, a newly-added occurrence always appends at the end of the numbered group and never demotes an already-rendered occurrence's position, and the missing-`insertionOrder` group's relative order never changes on an add either, so "an add-press changes the sort so order changes" for an already-rendered occurrence is unreachable within a session (verified against the comparator: every add is an append to the displayed sequence). Replace with: "When an add or remove changes `renderedChoiceOccurrences`'s composition (an add appends a new entry; a remove drops one and shifts the rest)". This makes the AC describe the actually-reachable, load-bearing property (a keyed `v-for` composition change is remount-free) that the QA plan already tests, rather than a scenario that cannot occur.

8. **`displayOrder` is static, read once at setup.**
   Given `displayOrder` is set in the initial metadata,
   When a `computedProps` function attempts to mutate `thisField.displayOrder` at runtime,
   Then the change has no effect on rendering (the property is excluded from `ComputedPropsFieldType`, mirroring `explicitChoiceSelection`/`preserveOnSwitch`/the sibling static flags), so the render mode cannot flip mid-form.

9. **Removal renumbers `globalIndex` live in interleaved mode too.**
   Given `displayOrder: 'added'` with 4 displayed occurrences,
   When one is removed,
   Then the 3 survivors' `globalIndex` re-derive to 0, 1, 2 within the remaining displayed sequence, extending ST-01 AC2 to the sorted list.

10. **No effect on `maxOccurs: 1` explicit choices.**
    Given a `maxOccurs: 1` explicit choice with `displayOrder` set (a no-op location for this flag),
    When it renders,
    Then behaviour is unchanged from FEAT-001/ST-05 (this story's scope is `maxOccurs > 1` only; `insertionOrder`/`displayOrder` have no observable effect there).

### Edge cases
- All occurrences loaded, none added this session, `displayOrder: 'added'`: every occurrence has `insertionOrder === undefined`, so the two-key comparator's "missing group" covers everyone and the result equals grouped order exactly (documented fallback made concrete).
- An occurrence added, then removed, then a different one added: the `insertionCounter` does not reuse the removed occurrence's number; it keeps incrementing (no compaction in this ephemeral tier, unlike ST-03's persisted `order`).
- A repeatable explicit choice nested inside a reindexing array: `insertionOrder` keys off the stable `occurrenceKey` (unchanged by ancestor reindex), so per-instance isolation holds the same way ST-01 AC6 holds for `globalIndex`.

### Out of scope
- Any persisted `order` value in `values`, mount-time backfill, or compaction on removal: ST-03.
- Any `DynamicFormSettings` change: explicitly rejected (Q8, decided Jeroen); this story ships no settings surface.
- Any docs/example UI exercising `displayOrder` or a visible toolbar: ST-05.
- A reactive/runtime toggle for `displayOrder`: it is static by design (ADR-5); any UI that flips it does so by remounting the form, which is ST-05's concern, not this story's.

## Design reference
Feature prototype (`../../prototype.html`): `#ordering-interleaved` (the ephemeral tier's visual outcome: DOM order equals visual order per design decision 5, ADR-4; the amber reload-fallback caveat callout), `#reload-behavior` (the ephemeral half of the side-by-side: instance-local counter, gone on remount, falls back to grouped order). This story delivers the engine mechanism only; the toolbar control that lets a reader flip `displayOrder` live is docs-demo chrome built in ST-05, not shipped here.

## Architecture reference
Builds directly on ST-01's `globalIndex` (this story makes the list `globalIndex` loops over sortable) and on FEAT-001/ST-05's static-flag-plus-`ComputedPropsFieldType`-exclusion pattern (`explicitChoiceSelection`, `preserveOnSwitch`), against the feature architecture's Slice B, ADR-2, ADR-3 (render-loop reorder is engine-side, ADR-4), ADR-5, and the "deterministic two-key sort" resolution of adversarial finding 3.

- **`packages/core/src/types/FieldMetadata.ts` (modified).** Add `displayOrder?: 'grouped' | 'added'` (default `'grouped'`) next to `preserveOnSwitch`; add it to the `ComputedPropsFieldType` `Omit` list for the same reason as its siblings (a `computedProps` mutation must not flip render order mid-form).
- **`packages/core/src/components/DynamicFormItemChoice.vue` (modified).**
  - Static capture: `const displayOrder = props.fieldMetadata?.displayOrder === 'added'`, mirroring the existing `explicitChoiceSelection`/`preserveOnSwitch` captures.
  - New instance-local refs: `insertionOrders = ref<Map<string, number>>(new Map())` (keyed by `occurrenceKey`) and a plain (non-reactive, analytics-style) `insertionCounter` variable, incremented on each add-press.
  - In `addChoiceOccurrence`'s `maxOccurs > 1` branch, immediately after `branchFieldArrays[index]?.push(...)`, resolve the just-created occurrence's `occurrenceKey` (branch length before push, per ADR-2: assignment happens at add-press time, not lazily while iterating the grouped list) and call `insertionOrders.value.set(occurrenceKey, ++insertionCounter)`.
  - New computed `renderedChoiceOccurrences`, deterministic two-key sort: equal to `activeChoiceOccurrences` when `displayOrder` is falsy; otherwise a stable sort where occurrences with no `insertionOrders` entry sort first (in their original grouped/`activeChoiceOccurrences` order) followed by occurrences that do have one, ascending by that value.
    - PROPOSED (adversarial review, finding 3): add a `_analytics_renderedChoiceOccurrencesCalculatedCount` plain-variable counter incremented at the top of this computed, mirroring the existing `_analytics_activeChoiceOccurrencesCalculatedCount`/`_analytics_occurrencesCalculatedCount` counters (`DynamicFormItemChoice.vue:50-51,181,277`). This story adds a genuinely new reactive `computed` (unlike ST-01, which added zero new computeds and for which an indirect DOM-identity proof was sufficient), so the direct recompute-count guard the component gives every other computed is the right, cheaper-to-maintain render-discipline test here. Wire it into the `.analytics.test.ts` plan item 5 below (making that test unconditional rather than placeholder).
  - The `-choice-array-item` `v-for` (the `explicitChoiceSelection && maxOccurs > 1` template branch) switches its source list from `activeChoiceOccurrences` to `renderedChoiceOccurrences`; `globalIndex` (ST-01) becomes the loop index over this now-possibly-sorted list, satisfying AC6 without any change to ST-01's own binding.
  - `activeChoiceOccurrences` itself, the choice-level slot prop, is untouched (per the feature's hard constraint and finding 5).
- **`packages/core/src/components/DynamicFormTemplate.vue` (modified, types only).** Add `insertionOrder?: number` to `ChoiceArrayItemAttributes`. `ChoiceOccurrence` stays unchanged (DECIDED research, finding 5: it is dropped from that type entirely, since `activeChoiceOccurrences` never carries it).
- **`packages/core/src/types/DynamicFormItemProps.ts` / `DynamicFormItem.vue` (modified).** Add and forward `insertionOrder?: number`, alongside `globalIndex` (ST-01) and `branchKey`.
- **Public API surface touched:** `FieldMetadata.displayOrder?: 'grouped' | 'added'` (additive, `ComputedPropsFieldType`-excluded) and `ChoiceArrayItemAttributes.insertionOrder?: number` (additive, optional). No `DynamicFormSettings` change ships (Q8 decided against that channel). **Changeset: `minor`**, this story's own entry.
- **Dependencies:** ST-01 (the loop index `globalIndex` must already exist as the render-loop index before this story makes that loop's source list sortable, per the feature architecture: "Depends on A (globalIndex becomes the loop index over the now-sortable render list)").
- **`specs/components.md`:** update the `DynamicFormItemChoice` row (`renderedChoiceOccurrences`, `displayOrder`), the `FieldMetadata` list, and the `ChoiceArrayItemAttributes` type entry once implemented.

## QA plan

This story extends ST-01's `globalIndex` suite and the FEAT-001 `maxOccurs > 1` repeatable-explicit-choice fixtures already established in `DynamicFormItemChoice.logic.test.ts`/`.analytics.test.ts` (the `apiEndpoint`/`crmExport` two-branch fixture). No new fixture component is needed. The same two fixture shapes ST-01 used are reused:

- **Scalar-leaf branches** (`type: 'text'`), matching the existing `maxOccurs > 1` analytics fixture, for tests where occurrence content is not the point. `insertionOrder` never writes into occurrence values (it is purely ephemeral slot-prop data, unlike ST-03's persisted `order`), so unlike ST-03 there is no scalar-branch restriction here: scalar fixtures are safe for every test in this plan, including AC4's "never reaches `values`" assertion in its render-count/structural form.
- **Object branches** (a `children` array, one text child each), named `crmExport`/`apiEndpoint`, used specifically for AC4's `Object.keys()` subset assertion, mirroring ST-01 AC2's pattern for proving no extra key appears inside an occurrence's own object.

This story's dependency on ST-01 means every test below assumes ST-01's `-global-index` testid, `occurrenceGlobalIndex` helper, and `findDynamicFormItemByPath` are already in place and green; this plan does not re-litigate ST-01's own acceptance criteria beyond the specific regression checks called out below.

   Reuses AC5's exact mixed-set fixture and sequence. 7. **Interleaved reorder preserves component/field state (no remount).**
   Under the decided AR-3 comparator (stable two-key sort, missing-`insertionOrder` group first in grouped order, numbered group appended after), a newly-added occurrence always appends at the end of the displayed sequence and never demotes an already-rendered occurrence's position, and the missing-`insertionOrder` group's own relative order never changes from an add-press either. So a literal in-place reorder of an *already-rendered* occurrence cannot be produced purely by `addChoiceOccurrence` within a single session; what actually changes `renderedChoiceOccurrences` mid-session is a composition change (an add appends a new entry, a remove drops one and shifts the rest). The test below validates the real, load-bearing engine property (a keyed `v-for` reorder/composition change is remount-free) via a composition-change scenario rather than a literal position swap, since that is the only scenario the decided comparator actually permits: seed `initialValues` with three occurrences (`apiEndpoint[0]`, `crmExport[0]`, `crmExport[1]`, grouped order, all `insertionOrder === undefined`), enter a value into `crmExport[0]`'s field and capture its DOM element reference, render count, and field value; then `addChoiceOccurrence('apiEndpoint')` (new occurrence, `insertionOrder === 1`, appended at the end of the displayed sequence, changing `renderedChoiceOccurrences`'s composition without touching the three existing entries' relative order). Assert `crmExport[0]`'s DOM element is the same reference, its render count is bounded (`+1` at most, the same bound ST-01 established), and its entered field value survived. A second variant repeats the check for a `removeChoiceOccurrence` call instead of an add, since removal is the other composition-changing operation. `DynamicFormItemChoice.analytics.test.ts`, cross-checked with a `.logic.test.ts` companion asserting the entered field value specifically.

   Flagged below (Flags for reviewer): AC7's own wording ("an add-press changes the sort so `renderedChoiceOccurrences`'s order changes") describes a scenario that cannot actually occur for an already-rendered occurrence under the decided AR-3 comparator; the test above proves the equivalent, actually-reachable property (composition change is remount-free) instead. See Flags for reviewer for the proposed rewrite.

(b) Type-level: `@ts-expect-error displayOrder is excluded from ComputedPropsFieldType` inside a `ComputedPropsFieldOf<Metadata>`-typed function, checked by `pnpm typecheck`/`vue-tsc`, mirroring the existing `explicitChoiceSelection` type-check test line for line. `DynamicFormItemChoice.logic.test.ts`.

    Reuses `mountExplicitSingleChoice` (ST-01 AC4's fixture) with `displayOrder: 'added'` added to the metadata. **Edge cases** (same new describe block):
- **All loaded, none added, `displayOrder: 'added'`.** Mount with `initialValues` seeding 3+ occurrences across both branches, no `addChoiceOccurrence` call.
