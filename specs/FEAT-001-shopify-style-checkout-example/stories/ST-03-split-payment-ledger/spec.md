## Functional
### User story
As a docs reader evaluating the library's more advanced capabilities, I want an opt-in "split your payment" section where I can add multiple payment sources, see each row's applied and remaining amount recompute live, reorder rows, and be blocked from submitting until the rows cover the order total, so that I can see the repeatable ordered choice shape (`maxOccurs > 1` combined with `choice`) working as a real, functional interaction.

### Acceptance criteria

1. Given the payment section's default single-choice picker, When "Split your payment across multiple methods" is clicked, Then the split-payment section expands and the single-choice payment selection is not required to be concurrently filled.
2. Given the split-payment section is empty, When no source has been added, Then a dashed empty-state slot with guidance text is shown and the place-order button stays disabled.
3. Given a gift card source (fixed amount) is added followed by a voucher (fixed amount) and a card (covers the remainder), When all three are present in that order, Then each row displays its own applied amount and a "remaining after this row" amount computed as the order total minus every row above it, and the card row's applied amount equals the order total minus the sum of the fixed rows above it.
4. Given at least two rows exist, When the down arrow on the first row (or the up arrow on the last row) is clicked, Then the clicked row and its display-neighbor swap their persisted `order` values, the rows visually reorder to match, and every row's applied/remaining amounts recompute to match the new order.
5. Given a remainder-covering row (card or PayPal) is moved above a fixed-amount row, When the new order causes the running total to exceed the order total, Then every displayed applied and remaining amount clamps at 0, the amber "still unassigned" readout becomes a rose "overshoot" banner naming the exact amount over the total, and the place-order button stays disabled.
6. Given the rows do not yet sum to the order total, When the place-order button is shown, Then it is disabled, the readout shows the amber "still unassigned" amount, and a rose banner names the exact shortfall; When the rows are added or reordered so the sum equals the order total exactly, Then the readout turns to the "ok" state showing 0.00 and the button becomes enabled (assuming the rest of the form is otherwise valid).
7. Given the up control on the first row and the down control on the last row, When rendered, Then those two controls are disabled regardless of how many rows exist, including the case of exactly one row, where that row is both first and last and both controls are disabled simultaneously.
   - DECIDED (research): the PROPOSED one-row boundary clause (the QA plan's own rewrite, endorsed by the adversarial review) is adopted into the Then clause above.
8. Given the split-payment section is active and its rows do not cover the order total, When `handleSubmit`'s validation runs, Then it surfaces a validation error at the `coverage` field's path and submission does not proceed, regardless of whether the live `remainingToAssign` computed has already re-run. (Checkable by inspecting `meta.errors` after a forced submit, manually, or automatically if the deferred docs test runner is ever added.)
   - DECIDED (research): the PROPOSED rewrite (the QA plan's own independently-checkable form, endorsed by the adversarial review) replaces the original wording, which asserted an internal two-gates-agree guarantee a manual click cannot force apart.

### Edge cases
- Removing a row re-triggers the coverage validation and the remaining-amount recompute for every remaining row.
- Reaching the configured `maxOccurs` cap disables adding further sources; re-ordering remains available up to the cap.
- A source branch that is already present behaves per the existing repeatable-choice add/remove mechanics already demonstrated on `/examples/choices`; this story does not change that mechanic, only the ledger chrome built on top of it.

### Out of scope
- The baseline (non-split) checkout sections (ST-02).
- The docs page's warning callout prose about ordering being UI-level, not XSD (ST-04 owns the exact copy; this story only needs the behavior it describes to be true).
- Nav/sidebar changes (ST-05).

## Design reference
Implements the prototype's `#split-payment` section (`../../prototype.html`), all four states: entry point collapsed, empty, covered with reordering controls, and short/blocked. The overshoot-on-reorder state is a delta the feature's adversarial review resolved (DECIDED, Jeroen, finding 3: clamp at 0, show a clearly messaged blocked state, no pinning) and is not drawn as its own prototype snapshot; this story is where it is first built and must be verified by test or manual check even though no static mockup shows it directly.

## Architecture reference
Builds, from the feature architecture's component plan:

  PROPOSED (adversarial review): define the "active split" state this story turns on, which neither the feature Data flow nor this reference currently names. The opt-in entry point (per DECIDED Open question 2, split payment is an escalation behind a link, default is the single payment `choice`) must drive three pieces of `computedProps` wiring, all of which this story owns because they only exist once the ledger exists:
  1. **Reveal:** activating split payment un-hides the `splitPayment` section and the hidden `coverage` leaf (the same `hide`/`minOccurs: 0` conditional pattern used for the business/VAT and billing toggles).
  2. **Relax the single payment choice** (AC1): while split is active, the single `payment` choice created in ST-02 must drop its `xsd_choiceMinOccurs` requirement via `computedProps`, so the two payment paths do not both demand a selection.   DECIDED (research): Resolved at the feature level, where the gap lives: the feature's Data flow now has a "Split activation scopes the gate" clause. All three wiring pieces above stand as this story's work. The activation model is a boolean split-payment leaf written by the entry point and read via `computedProps` (the same toggle-reveal pattern as the business/VAT and billing sections); deriving "active" from the occurrence count was rejected because the revealed-but-empty state ("No payment sources yet") must exist before any occurrence is added. The gate scoping follows from decisions already approved (Open questions 2 and 7, the prototype's enabled place-order state with a single payment method), so nothing approved changes; the cross-seam touch on ST-02's `payment` node stays declared here.
  Sources: feature spec Data flow ("Split activation scopes the gate", with its own DECIDED entry and sources), prototype `#split-payment` empty state

### States to assert (feature states policy, this slice's instances)

Per the feature's States policy, this slice must show:
- **Empty**: dashed sunken slot with guidance text, no sources added (AC2).
- **Disabled**: capped "Add" button once `maxOccurs` is reached (edge case), and both `not-allowed` up/down arrows at the row boundaries (AC7).
- **Error (form-level)**: the amber "still unassigned" readout plus the rose shortfall banner (AC6), and the rose overshoot banner (AC5). These are the two rose-banner variants this slice is responsible for; both must read the exact amount, not a generic message.
- **Default/pristine**: a freshly added row before any reorder, numbers matching the simple top-to-bottom sum.
- **Loading**: not applicable to this slice directly (submit's spinner state belongs to ST-02's submit bar); state explicitly to avoid the omission reading as missed rather than out of scope.

### Reactivity / render-count

`SplitPaymentLedgerRow` sits on top of `DynamicFormItemChoice`'s `splitPayment-choice-array-item` slot and reads `values` via `useFormContext()` rather than through the engine's own `computedProps` re-render path, so the `analytics` setting's `data-testid="<path>-analytics-render-count"` elements (a `packages/core` engine feature) do not directly instrument this new docs-level component. There is nothing in `packages/core/src/` for this story to add an `*.analytics.test.ts` against. The regression risk that matters here is upstream: `DynamicFormItemChoice.analytics.test.ts` already guards that writing one occurrence's `order` does not cause unrelated sibling occurrences to re-render; rerun it as part of `pnpm ci` and treat a new failure there as a signal that this story's reorder writes are over-triggering recomputation outside what reordering should touch. If the test-runner recommendation above is accepted, a manual-inspection substitute is reasonable in the meantime: watch the Vue devtools component inspector while clicking reorder and confirm only the ledger container and the two swapped rows re-render, not the rest of the checkout form.

### Coverage

No `packages/core/src/` change, so `pnpm -r ci:test:coverage`'s tracked baseline is mechanically unaffected by this story in either direction; nothing under `docs/` is included in that measurement. This is called out rather than left silent because it means the story's riskiest code (arithmetic, clamping, the hidden validation closure) ships with no coverage number at all, automated or otherwise, reinforcing the test infrastructure finding above.

### Time sensitivity

Nothing in this slice is date or time dependent; order totals, amounts, and ordering are all synchronous arithmetic over form values. `TZ=Europe/Amsterdam` has no bearing here. Stated explicitly so the silence is not mistaken for an omission.

## Adversarial review

Lite (STORY) mode: blockers to acceptance-criteria testability and to consistency with the approved feature design/architecture. The QA plan's factual load-bearing claims were spot-checked against the repo and hold: the cited regression suites exist with matching names (`DynamicFormItemChoice.formApi.test.ts` "validateField at the choice anchor path surfaces the error by default"; `DynamicFormItemChoice.logic.test.ts` `preserveOrder` and "displayOrder is reactive through the metadata prop ... without a remount"; `DynamicFormItem.formApi.test.ts` "validateField validates only the targeted field"; `DynamicFormItem.logic.test.ts` `computedProps > childFields`); the fixture arithmetic (gift card 50.00 + voucher 25.00 + card 173.50 = 248.50) matches both the prototype's covered-state numbers and the feature; and the empty / covered / short states and the amber-readout-plus-rose-banner arrangement match `prototype.html`'s `#split-payment` section.

1. **(blocker) The coverage gate as specified blocks the DEFAULT single-payment checkout from submitting, and the "active split" semantics AC1 depends on are defined nowhere.** The feature Data flow sets `remainingToAssign = orderTotal - sum(all applied amounts)`, the live button-disable fires on `remainingToAssign !== 0`, and a hidden `coverage` field enforces the same for `handleSubmit`. With zero split rows (the default single-payment path, per DECIDED Open question 2), the sum is 0, so `remainingToAssign` is the full 248.50 and both gates would permanently block the most common checkout path. Symmetrically, AC1 requires activating split payment to relax the single `payment` choice's `xsd_choiceMinOccurs`, but neither the story's Architecture reference nor the feature's metadata mapping defines the entry-point toggle / active-split state that both of these hinge on (the feature's `#payment` node is just "choice (single), four branches"; ST-02's scope lists only "single payment choice"). ### Metadata contract for ST-04

- `splitPaymentActive` (`checkbox`, sibling of `paymentMethod` under `manual`): the entry-point toggle. ST-04's walkthrough can anchor on this path (`checkoutMethod.manual.splitPaymentActive`) for the "split your payment" entry point excerpt.

### Coverage gate reconciliation with ST-02's `canSubmit` gate (ADR-5)

ST-02's Implementation notes flagged that `onSubmit` no longer calls vee-validate's own `handleSubmit` at all (it gates the actual submission directly on the local `canSubmit` computed), specifically because a fresh `handleSubmit`-triggered `validate()` call surfaces a stale validation registration on an unmounted nested choice. ADR-5 assumes `handleSubmit`'s own validation pass is what authoritatively checks the hidden coverage field at submit time; that assumption no longer holds given ST-02's fix.

Resolution: the coverage check is folded directly into the same `formIsComplete`/`canSubmit` gate `onSubmit` already trusts, not left to a `handleSubmit` call that never happens. `formIsComplete` now includes `if (!splitPaymentCovered.value) return false;`, where `splitPaymentCovered` is a `computed` built from the exact same pure `computeSplitPaymentLedger`/`collectSplitPaymentOccurrences` functions the ledger UI and the coverage field's own validation message use, so the "two gates" (button-disable and submit-decision) cannot read different numbers. The hidden `splitPaymentCoverage` field's `validation` closure is still registered and still the one **visible** error source (its message is what the rose banner shows, and it is what a forced submit's `errors` map would surface per AC8), but the **block** on a real click is enforced independently by `canSubmit`, consistent with how ST-02 already made the same call for the childless-branch and stale-registration issues. This is the concrete answer to AC8: `canSubmit` reads `false` and the place-order click never proceeds whenever `splitPaymentRemainingToAssign !== 0`, verified below with a forced-submission (Enter key, not the disabled button) attempt while short.

### Deviations

- **The ledger components take plain data (`splitPaymentPath: string`, `branches: SplitPaymentBranchShape[]`, `path: string`), not the raw `FieldMetadata` object**, even though `FieldMetadata` is a public export. Tried first with the raw object; `vue-tsc` rejected it (`ComputedPropsFieldType<string, object>` is not assignable to `ComputedPropsFieldType<SpecificUnion, SpecificProps>`, a contravariance mismatch in `computedProps`'s function-parameter position between the generic default-typed `FieldMetadata` and `CheckoutFormTemplate`'s own union-typed `Metadata`). - **`label` props on both new components are typed `MaybeRefOrGetter<string | undefined>`, not plain `string`,** matching `SectionCard`/`RepeaterCard`'s existing convention (`fieldContext.label` is a `MaybeRefOrGetter`, and passing it into a plain-`string`-typed prop is exactly the pre-existing `ChoiceSectionCard.vue` baseline type error already on record from ST-01/ST-02). `SplitPaymentLedgerRow.vue` resolves it once via `toValue()` into a `labelText` computed used everywhere it needs the string; `SplitPaymentLedger.vue` only forwards `label` untouched into `ChoiceArraySectionCard`, so no resolution was needed there.

- **`SplitPaymentLedgerRow`'s layout uses `flex-wrap` with `shrink-0` on the badge/arrows column, the amounts column, and the remove button, plus a `min-w-[180px]` floor on the content column**, not a plain `flex items-center` row. ### Fix round 1: single-payment path permanently blocked

Root cause confirmed directly, same as diagnosed in the Verification report below: `paymentMethod`'s own required check runs once, at the moment a branch is picked, against a value still necessarily empty (no field underneath typed in yet), and nothing re-runs that check afterward except on the `splitPaymentActive` transition. For the default, non-split path, that transition never fires, so the stale required error sits in `errors.value` forever once any branch (card, iDEAL, PayPal, Klarna) is selected, and `canSubmit`'s `Object.keys(errors.value).length === 0` term then blocks that branch's checkout permanently, regardless of how completely its fields are filled in.

Fix: extended `paymentMethod`'s existing `computedProps` re-trigger with a second transition to watch, alongside the already-present `splitPaymentActive` one. A `hasSelection` boolean (whether any branch key is present under `paymentMethod`) is tracked across runs the same way `paymentMethodRelaxWasActive` already is; whenever it flips, `validateField` is called on `paymentMethod`'s own path. This clears the stale required error the moment a branch is chosen, independent of how long it then takes the shopper to fill in that branch's own fields.

Rejected alternatives, and why:
- Dropping the `errors.value` term from `canSubmit` entirely (the quick fix the verifier proved works) was rejected because `formIsComplete` only checks presence, not format: an active, invalid VAT number, email, postal code, or over-length gift message would then stop blocking submit, since nothing else in `canSubmit` reads the per-field pattern-validation result. Confirmed this would be a regression by testing: an active, invalid VAT number must keep blocking submit, and still does after this fix.
- Scoping `canSubmit`'s error check to exclude "choice-anchor" errors generically was rejected in favor of fixing the one anchor actually affected: direct testing showed `checkoutMethod`'s and `shippingMethod`'s own choice-level required checks do **not** get stuck the same way (both revalidate cleanly once their branch is picked and filled in), so a generic exclusion would have been broader than the actual bug and harder to reason about later. Only `paymentMethod` needed the re-trigger.

### Fix round 3: split payment never mounted on the production build, `useFormContext()` injected against the wrong symbol

On the production build only (`pnpm docs:build` + `vitepress preview`), `SplitPaymentLedger.vue` and `SplitPaymentLedgerRow.vue` threw `Cannot destructure property 'values' of 'useFormContext(...)' as it is undefined` on every load of `/examples/checkout`, pristine or not, and the split-payment section never mounted. `pnpm docs:dev` never reproduced it.

Root cause, confirmed by instrumenting both sides with a temporary debug build (`minify: false`, no `NODE_ENV` override, reverted before finishing): the component ancestry and the `provide()`/`inject()` prototype chain were both completely correct, and `CheckoutFormExample`'s own `instance.provides` genuinely held a `Symbol(vee-validate-form-context)` entry at the moment `SplitPaymentLedger` mounted. The two symbols were simply not the same object. `packages/core` resolves its own `vee-validate` import from `packages/core/node_modules` (a pnpm store entry keyed `vee-validate@4.15.1_vue@3.5.44_typescript@5.9.2_`, via the root workspace install), while `docs/` resolves its own direct `import { useFormContext } from 'vee-validate'` from `docs/node_modules` (a separate pnpm store entry keyed `vee-validate@4.15.1_vue@3.5.44`, installed independently since `docs/` sits outside the pnpm workspace). Same version, two physically different files, so Vite's production build (Rollup) bundled both, each executing its own top-level `Symbol('vee-validate-form-context')` call. `useDynamicForm()`'s `provide()` (reached through the library's copy) and the ledger's own `useFormContext()` (reached through the docs copy) therefore never agreed on which key to look up. `pnpm docs:dev` never showed this because Vite's dev-server dependency pre-bundler collapses every `'vee-validate'` specifier it encounters into one dev chunk regardless of which physical file it would otherwise resolve from, masking the duplication; only Rollup's production build keeps the two resolutions separate. This is not a hydration-specific defect: it is a module-identity mismatch baked into the bundle, which happens to only ever get exercised through the ledger components because they are the only docs-level code in this feature calling `useFormContext()` directly instead of only ever reading the return value of the host's own `useDynamicForm()` call. `<ClientOnly>` and lifecycle-timing fixes in the ledger components were both considered and rejected: neither changes which physical `vee-validate` module a given import resolves to, so both would leave the symbol mismatch, and therefore the broken injection, fully intact regardless of when the component mounts.

Fix: `docs/.vitepress/config.ts`'s Vite config now sets `resolve.dedupe: ['vee-validate']`, the standard Vite remedy for "duplicated copies of the same dependency... likely because of hoisting or linked monorepos" (Vite's own wording for this exact option). This forces every `'vee-validate'` import reached while building the docs site, regardless of which physical file it would otherwise resolve to, onto the one copy actually installed at `docs/node_modules/vee-validate`. Confirmed in the built bundle: `vee-validate-form-context` now appears exactly once across every output chunk, where it previously appeared twice (once under a Rollup-disambiguated `PublicFormContextKey$1` alias).

Verified on the production build (`pnpm docs:build` + `vitepress preview`) with Playwright (local cached Chromium, `args: ['--no-proxy-server']`): a pristine load of `/examples/checkout` shows zero console errors; activating split payment, adding gift card (50.00) + voucher (25.00) + card in that order shows the exact fixture amounts (`-50.00/198.50`, `-25.00/173.50`, `-173.50/0.00`); moving a row up/down reorders and recomputes correctly; moving the card row to the front produces the exact overshoot banner ("exceed the order total of 248.50 by 75.00"); restoring the order returns to "Remaining to assign 0.00"; and a real submit click reaches the success banner. Also re-checked: a pristine load with no interaction stays clean (the pre-existing, unrelated "Hydration completed but contains mismatches" console message and a 404 resource warning are present on every docs example page, including ones with no form at all, so they are out of scope here and were not touched); `pnpm docs:dev` still behaves exactly as before, including the split-payment flow; and the single-payment card path (no split) still reaches the success banner. `pnpm run ci:test`, `ci:lint`, `ci:typecheck`, and `pnpm -r ci:test:coverage` are all unchanged from the recorded baseline (97.8% stmts / 93.12% branch / 98.26% funcs / 97.8% lines on `packages/core`); `git diff --stat -- packages/` is empty, so this remains docs-only with no changeset. `pnpm docs:build` passes, and `vue-tsc --noEmit -p docs/tsconfig.json` shows only the same two pre-existing baseline errors (`BasicFormExample.vue`, `ChoiceSectionCard.vue`).

### Blocking finding

**(blocker) The single, non-split payment path can never be submitted: `canSubmit` permanently reads `false` for every non-split payment method (card, iDEAL, PayPal; Klarna not separately tested but shares the same mechanism), even with the form otherwise fully and correctly filled in.**

Reproduced with `checkoutMethod.manual.paymentMethod.payPal = true` (and separately with a fully filled card, and with iDEAL) and every other required field filled: `formIsComplete` evaluates `true` by its own hand-rolled checks, but `errors.value` (vee-validate's own map) retains a stale entry, `{"checkoutMethod.manual.paymentMethod": "How would you like to pay? is required"}`, that never clears. `canSubmit = formIsComplete.value && Object.keys(errors.value).length === 0` (added in this story's "Coverage gate reconciliation") therefore stays `false` forever once that branch is picked, for every payment branch, regardless of how completely the form is filled in. Confirmed root cause directly: temporarily changing `canSubmit` to `formIsComplete.value` alone (no `errors.value` check) made every single-payment submit path work immediately, with no other regression, because `formIsComplete` already independently encodes every check `errors.value` was meant to catch, including the coverage gate (`splitPaymentCovered.value`). The temporary change was reverted before finishing; the working tree is unchanged from what the developer handed off.

This is exactly the failure mode the feature's own Risks section already documents and warns against ("an `explicitChoiceSelection` choice's own aggregate ... is only ever checked once, at activation time, while it is still necessarily empty... so ST-03 and ST-04 do not rely on `meta.valid`" and the related `handleSubmit`-staleness note): the `paymentMethod` choice's own `xsd_choiceMinOccurs` check runs once at branch-activation time, before the childless-branch marker value (for PayPal) or the first keystroke (for card/iDEAL) lands, and nothing re-runs it afterward because no `computedProps` on `paymentMethod` calls `validateField` except when `splitPaymentActive` itself flips (the "relax while split is active" wiring), not when a branch is freshly selected while split stays inactive. `errors.value` is therefore stuck with the stale required error for the entire lifetime of the single-payment path, and this story's new `Object.keys(errors.value).length === 0` term surfaces it as a hard, permanent submit block.

Because this blocks every non-split checkout, which is the feature's documented default path (Open question 2: "Default is a single payment method choice"), and the QA plan's own AC1 mapping explicitly calls for confirming "submit with full coverage and confirm the single-choice `choiceMinOccurs` error never blocks it," this is squarely the kind of regression that mapping was meant to catch. The Implementation notes' own AC1 evidence only exercises a real submit click on the **split** path, never the single-payment path, which is why this slipped through.

**Required fix**: `canSubmit` must not depend on vee-validate's own `errors` map (consistent with the already-documented reason `meta.valid` is avoided elsewhere in this feature); `formIsComplete`'s own hand-rolled checks are already sufficient and already include the coverage gate. Alternatively, if keeping an `errors.value` check is wanted for defense in depth, the `paymentMethod` choice's `computedProps` needs to re-run `validateField` on its own path whenever a branch is freshly selected (not only when `splitPaymentActive` flips), the same pattern already used elsewhere in this file for toggle-revealed fields.
