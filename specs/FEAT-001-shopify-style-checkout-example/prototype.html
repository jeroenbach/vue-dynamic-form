#page-intro

A complete webshop checkout, Shopify-style

One typed metadata tree, one template component, and the most consequential form on the web. This example rebuilds the structure of a modern one-page checkout, not its branding, and ends with a split-payment finale that no other page here demonstrates.

Years ago, a usability team at a major retailer studied why so many shoppers filled a cart and never bought. The culprit was a single button next to the sign-in form that read "Register". First-time buyers assumed they had to create an account to purchase, so they abandoned. The team replaced it with a "Continue" button and a quiet line of text: you can check out as a guest. Purchases rose 45% in the first month, an extra 300 million dollars in the first year. Jared Spool told this story for years and never named the retailer, so neither will we.

The lesson is not about one button. It is that checkout is the highest-stakes form on the web, and small structural choices move real money. Baymard Institute finds the average checkout asks for 11.3 fields across 5.1 steps, while an optimized checkout needs only about 8 fields, and that 17% of shoppers have abandoned a purchase purely because checkout was too long or complicated.

Few companies obsess over this more publicly than Shopify. According to a study Shopify commissioned from one of the Big Three consulting firms, its checkout converts about 15% better on average, and up to 36% better than comparable checkouts, with Shop Pay lifting conversion by up to 50% against guest checkout. Those are vendor-published figures from an unnamed study, so treat them as Shopify's own claim rather than independent fact. Either way, this is the checkout we rebuild below, as the benchmark worth matching.

What you are looking at

Everything in the live form is rendered by the library from one metadata tree through one neutrally styled template. We rebuild the checkout's structure, not Shopify's visual design or logo. Payment inputs are inert demo fields (details below).

Intro uses the VitePress prose column (max 860px) and the default theme's tip container. No dark-specific styling needed: text and borders come from --vp-c-* equivalents, which both themes supply.

#split-payment

Split your payment, the finale

Here is the shape no other page here covers: a repeatable ordered choice (maxOccurs > 1 combined with choice). Split payment is opt-in, so it never inflates the default field count (DECIDED, Q2). #metadata-walkthrough

It is one metadata tree and one template

Everything above is declarative. The engine walks the tree, classifies each node by its shape, and renders it through the neutral template. Below, the same walkthrough style as the other advanced examples.

What it demonstrates

  • A top-level choice for express vs manual checkout, shown with minimal inert UI
  • Email xsd_pattern, and a country xsd_enumeration that drives per-country postal validation through computedProps
  • Conditional visibility and validation: the business / VAT toggle and the billing "same as shipping" toggle
  • A shipping choice with a field nested only on the pickup branch
  • A payment choice with four branch flavours: card inputs, a bank select, an empty branch, an enumeration select
  • The finale: a repeatable ordered choice (maxOccurs > 1) for split payment, with a computed per-row remaining amount, template-driven reordering, and a hard cross-field rule that the rows cover the total
  • A gift message with xsd_maxLength and a character counter

How it works: the split-payment shape

The split-payment list is a choice with maxOccurs > 1 and explicitChoiceSelection. Each source is a branch; adding one pushes an occurrence. The per-row remaining amount is a computedProps read over the sibling occurrences above it, and reordering writes the two affected occurrences' order values directly, exactly as the choices page already demonstrates.

checkout.metadata.ts
// Split payment: a repeatable, ordered choice of payment sources.
{
  name: 'splitPayment',
  type: 'heading',
  maxOccurs: 6,
  explicitChoiceSelection: true,
  displayOrder: 'added',
  preserveOrder: true, // order is real, reorderable data
  choice: [
    { name: 'giftCard', children: [ /* code, applied amount */ ] },
    { name: 'voucher',  children: [ /* code, applied amount */ ] },
    { name: 'card',     children: [ /* inert demo inputs */ ] },
    { name: 'payPal',   children: [ /* applied amount */ ] },
  ],
}
Illustrative excerpt for the design brief. The architect owns the exact field set, validation wiring and computedProps signatures; this only fixes the shape and the camelCase, no-em-dash house style.
