Explicit choice selection

Design surface for FEAT-001. A framework-native way to select (and, for repeatable choices, add / remove) a choice branch before any field inside it holds a value, exposed as slot props on the -choice slot mirroring the array addItem / removeItem pattern. The widgets below are all built by the template author on top of the same low-level primitives (decision 2); the engine ships no prescribed UI. Flip the toggle top-right to review every section in dark.

Provisional slot-prop names used in annotations, final names are the architect's call: addChoiceOccurrence(branchKey), removeChoiceOccurrence(branchKey, index?), canAddChoiceOccurrence(branchKey), activeChoiceOccurrences.

2 · Repeatable choice (maxOccurs > 1)

Add affordances respect both each branch's own maxOccurs and the choice's shared occurrence budget (the existing occurrences math in DynamicFormItemChoice). Two widget styles below prove the primitives are widget-agnostic; both are template-author code.

3 · Choice inside an array occurrence

A hard requirement (decision 6). A repeatable array where each occurrence contains its own maxOccurs: 1 choice. Each array item tracks its own active branch independently, addressed through the item's pathOverride. Here: project contacts, each with a preferred contact method.

4 · Onboarding planner: today vs after

The Launch approach step looks the same to the user in both worlds. The change is what the template author has to write. Below, identical rendered output with the mechanism annotated on each side.

Today (userland workaround)

Launch approach

Pick one. You can switch later.

  • Invented changeChoice extended property the engine ignores
  • Selection kept in a local ref outside the form values
  • Every branch has computedProps that hide + thisValue = {} to clear
  • Every branch has a hidden phantom child faking a truthy value so counting works
  • Starts hard-defaulted to Self-serve; a true empty start is awkward

After (framework-native)

Launch approach

Pick one. You can switch later.

  • ChoiceSectionCard calls addChoiceOccurrence(key) from a slot prop
  • Selection is engine state, never in the submitted values (decision 4)
  • Clearing on switch handled by the engine (decision 3), no per-branch clear code
  • No phantom child: branch reads as active from explicit selection
  • Can start unselected; pre-selecting a default stays possible via one call on mount

Docs impact: docs/examples/choices.md gains a "Select first, then fill in" section covering both the maxOccurs: 1 and maxOccurs > 1 patterns, using this same visual language. AdvancedFormTemplate.vue's #heading-choice slot and ChoiceSectionCard.vue are updated to consume the new slot props; the changeChoice extended property and both phantom-field blocks are deleted from FormExampleClientOnboardingPlanner.vue.

No visual redesign of ChoiceCard / ChoiceSectionCard beyond the new "kind" badge and repeatable-mode add affordances (in scope). The maxOccurs:1 rendering is pixel-identical to today.
