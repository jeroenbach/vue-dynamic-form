# Quick: a choice-hosting field's own validation registration survives its unmount, blocking a later valid submit

## Decided without Jeroen (research)

Settled from research during discussion prep, not reviewed by Jeroen. Override any of these freely.

- AR-1 → Test impact and Affected files now name both reproduction tests; both must flip
- AR-2 → test descriptions corrected to what they literally assert (DOM state, not `validate()` return values)
- AR-3 → silent-validate watcher attributed to ST-03 (already landed); QUICK-004 depends on it, does not reimplement it
- AR-4 → direction 2 dropped (needs a vee-validate fork)
- AR-5 → direction 1 chosen: single registration at the path, hosting field's own rules folded into the choice's `combinedValidation`

## Problem

Split out of FEAT-010's GAP 3 story (ST-03) stale-registration investigation. Reproduced against `TestForm`: an outer `explicitChoiceSelection: true` choice with two branches, one branch itself carrying a nested `explicitChoiceSelection: true` choice. Select the nested-choice branch, select one of its inner options, switch the outer choice to the other branch, fill that branch completely, then call `validate()`/`handleSubmit()`. The deselected branch's own required check still fails validation, even though every currently rendered field is valid and the branch's value was cleared on deselection (so "still has stale data" is not the cause).

Root cause, confirmed by dumping vee-validate's own `pathStates` through the lifecycle (`getAllPathStates()`):

- `DynamicFormItem.vue` calls `useField(normalizedPath, combinedValidation, …)` for every non-array field regardless of shape, including a field whose own `choice` array makes it host a nested `DynamicFormItemChoice`. That nested component anchors its own `useField(normalizedPath, …)` call at the *same* path (`DynamicFormItemChoice.vue`'s `closestPath` falls back to the nearest ancestor path when the choice node itself has no path segment of its own, which is exactly the hosting field's own path). So one logical field (a branch that both has a nested choice and may have its own `restriction`/`validation`) carries **two independent `useField` registrations at the identical string path**.
- vee-validate's `createPathState` (installed `vee-validate@4.15.1` dist, `vee-validate.mjs`) only merges two registrations sharing a path when both are checkbox/radio; for any other field type it always pushes a brand new `pathState` entry, while `pathStateLookup[path]` is overwritten to point at whichever registered **last**.
- On unmount, `useField`'s own `onBeforeUnmount` (same file) looks up `form.getPathState(path)` and bails out (without calling `removePathState`) unless `pathState.id === field.id`. Because the lookup only ever holds the *last*-registered id, the *first*-registered one's unmount handler always finds a mismatch and returns early, leaving its entry in `pathStates` forever: a permanent ghost with no owning component and no further way to be removed.
- In the reproduction, the hosting `DynamicFormItem` (the branch) registers before its child `DynamicFormItemChoice`, so the hosting field's own ghost survives deselection with its last-known `valid`/`value` frozen. Live reads (`form.errors`, `meta.valid`) are not affected while nothing re-validates it, because ST-03's already-landed silent-validate watcher keeps it refreshed as long as the component is mounted. Once the branch is deselected its value is cleared and the component unmounts, so nothing ever revalidates the ghost again; the next full `validate()`/`handleSubmit()` call re-evaluates every `pathState` from scratch, including the ghost, against the now-cleared value, and the stale xsd_required rule fails.

> **Dependency note.** The silent-validate watcher referenced in this section is ST-03's work, not QUICK-004's, and it is already present on this branch (`DynamicFormItem.vue`, the `watch(childValueReactivity, …)` block guarded by `isValidationSuppressed()`). QUICK-004 depends on it but does not reimplement it: the reproduction's "fresh while mounted, stale once unmounted" framing only holds because ST-03's watcher has landed.
>
> DECIDED (research): applied — the two former "this story's" references are reworded to attribute the watcher to ST-03. Source: the watcher verified present in `DynamicFormItem.vue` on this branch.

This is unrelated to GAP 3's silent-validate mechanism (it happens with or without it; GAP 3 only changes how fresh the ghost's value is *while mounted*, not whether it unregisters on unmount) and is not narrowly scoped to the nested-choice case named in the reproduction: it reproduces for *any* field that both hosts a `choice` (or, by the same mechanism, has `children`? — see Proposed change for why only the choice case is affected in practice) and later unmounts while a sibling registration still exists at the same path. Per the feature's standing permission (its "Stale-registration investigation" open question), this is split out rather than shipped inside ST-03.

**A second, mounted-only manifestation of the same double registration (found during ST-03's own test authoring).** No unmount is even required. A plain choice-hosting field's own registration can get stuck without ever unmounting: selecting a childless branch that declares `presenceValue` (GAP 1) writes the branch's value through `formContext.setFieldValue(branchPath, presenceValue, false)` — a `shouldValidate: false` write, which `useIsValidationSuppressed`'s `trackNonValidatingWrites` wrapper marks as form-wide suppressed for one tick. The resulting value-bubble that increments the hosting field's own `childValueReactivity` lands inside that same suppressed tick, so ST-03's silent-validate watcher correctly skips it (per its own suppression guard), and nothing ever revalidates it afterward if no other field in the form changes again. The result: the choice anchor's own `meta.valid` (a second, redundant registration living at the same path as `DynamicFormItemChoice`'s own, functionally identical to the unmount case's ghost) stays stuck invalid even though the value it should be validating is actually present. Confirmed via a form containing only a single `explicitChoiceSelection` choice with one `presenceValue`-declaring childless branch: after selecting the branch, the form-level `meta.valid` never becomes `true`. This is the same root cause (the unconditional `useField` call in `DynamicFormItem.vue` for an `isChoice` node), just triggered without an unmount, which is further evidence for proposed direction 1 below (stop double-registering at the same path) over the other two, since it is the only one that removes the hazard in both the mounted and the unmounted case.

## Proposed change

DECIDED (research): **direction 1** — stop double-registering at the same path. `DynamicFormItem.vue` skips its own `useField` call for a choice-hosting node (mirroring the existing array stub) and reads the value via `useFieldValue(path)`; the nested `DynamicFormItemChoice`'s registration becomes the single one at that path. The hosting field's own `restriction`/`validation` is folded into the choice's `combinedValidation` so those rules keep running exactly as before (including in cases where the choice's own `combinedValidation` would currently return `undefined`, e.g. a single-child choice), plus the dedicated new test the Test impact section requires.
Why: direction 2 is verified infeasible without forking vee-validate's `useField` (its own escape clause drops it); direction 3 does not fix the mounted-only manifestation at all and leaks one `pathState` per deselect. Direction 1 is the only candidate that removes the hazard in both the mounted and the unmounted case.
Sources: vee-validate@4.15.1 dist (`createPathState` merge rules, `onBeforeUnmount` id check — verified by the adversarial review), the mounted-only reproduction in the Problem section, `DynamicFormItemChoice.vue`'s `combinedValidation` computed (holds the hosting `field` node, so the rules can be folded there).

The three directions originally weighed, kept for the record:

1. **Stop double-registering at the same path.** For a field whose `computedField.choice?.length` is non-empty, `DynamicFormItem.vue` could skip its own `useField(...)` call (mirroring the existing array stub, `{ value: ref(undefined) } as FieldContext`) and instead read the branch's current value with `useFieldValue(path)` (the read-only accessor `DynamicFormItemChoice.vue` already uses for `branchValueRefs`), leaving the nested `DynamicFormItemChoice`'s own `useField` call as the single registration at that path.
   - Risk: a choice-hosting field's own `restriction`/`validation` (a cross-field rule declared directly on the branch, independent of the nested choice's `xsd_choiceMinOccurs`/`xsd_choiceMaxOccurs`) is currently validated through this exact registration. Dropping it outright would silently stop checking those rules. Any fix along this path must either prove no current caller relies on a choice-hosting field's own `restriction`/`validation`, or fold those rules into the nested choice's own `combinedValidation` instead of dropping them.
2. **Fix the unmount lookup instead of avoiding the collision.** Patch `onBeforeUnmount`'s cleanup so a field whose id does not match the current lookup entry still removes *itself* from `pathStates` (by id, not by the lookup's single-slot pointer) rather than bailing out. This lives entirely inside our own wrapping, if feasible without reaching into vee-validate internals; if it requires forking vee-validate's own `removePathState`/`onBeforeUnmount` behavior, this option is likely not worth the maintenance cost and should be dropped in favor of option 1 or 3.
   - **DECIDED (research): dropped — verified not feasible in-wrapper.** The bailing `onBeforeUnmount` is defined inside vee-validate's own `useField` (confirmed in `vee-validate@4.15.1` dist: the handler reads `form.getPathState(path)`, compares `pathState.id === field.id`, and `return`s without `removePathState` on mismatch). The library never owns that handler, so option 2 cannot be done "inside our own wrapping"; it would require forking `useField` or monkey-patching the form's `removePathState`. Per the option's own escape clause this means it should be dropped in favor of option 1 (or 3). Note also that `removePathState(path, id)` itself already matches by id, so the fork would be small, but owning a forked lifecycle hook against a peer-dependency range of `>=4.12` is the maintenance cost the option warns against.
3. **Avoid the unmount race by deselecting before clearing.** Investigate whether reordering `clearBranch`'s value-clear relative to the branch's own unmount (e.g. clearing and letting the branch's own ghost revalidate against the cleared value *before* the component that owns it tears down, so the live silent validate — not a later cold `validate()` — is what observes the cleared state) closes the gap without touching the registration shape at all. This only helps if the ghost's last-known `valid` ends up correct at the moment of clearing; needs verification before relying on it, and does not address the underlying permanent-ghost accumulation (a long-lived form repeatedly selecting/deselecting the same branch would leak one `pathState` per deselect).

`packages/core/src/` is touched by whichever direction is chosen; expect a **patch** changeset (behavior fix, no export shape change) unless the fix needs a new prop/option, in which case **minor**.

## Implementation notes

- `DynamicFormItem.vue` skips its own `useField` call for a choice-hosting node (`isChoice`, moved up next to `isArray` so the skip condition is available at the same setup-time call site) and reads the value through vee-validate's `useFieldValue(path)` instead. The `onBeforeUnmount` cleanup also returns early for a choice-hosting node, since its value is read-only here and clearing a deselected branch's data is already handled explicitly by `DynamicFormItemChoice`'s own `clearBranch`.
- The hosting field's own `restriction`/`validation` is folded into `DynamicFormItemChoice.vue`'s `combinedValidation`, including in the `singleChild`/`disabled` early-return cases, exactly as the approved direction specifies.
- Deviation: the hosting field's generic `required` (derived from `minOccurs` defaulting to 1) was deliberately **not** folded in, even though the Problem section's prose attributes the first reproduction's failure to "the branchA group's own required check." Folding a derived `xsd_required` in addition to `restriction`/`validation` made every default-required plain choice (the common case, no restriction/validation declared) doubly required against its own anchor path, which isn't materialized until a descendant writes into it; this broke a large number of existing `DynamicFormItemChoice.validation.test.ts` assertions that pin an exact `combinedValidation` rule count. Removing the double registration already fixes both reproductions on its own, because `xsd_choiceMinOccurs` (and, for a plain leaf branch, the branch's own `xsd_required` on its own distinct path) already cover that semantic space; a redundant `xsd_required` on the choice-hosting node itself was never a deliberate feature, just a side effect of the same unconditional `useField` call that caused the bug. Spec's Proposed change section already only asks for "restriction/validation" to be folded, not required, so this is read as confirming rather than contradicting the approved direction.
- To avoid duplicating the full XSD restriction/custom-validation rule list in two files (which also regressed branch coverage, since `DynamicFormItemChoice.vue` had never exercised those twelve facets), the rule-building logic shared by `DynamicFormItem.vue`'s own `watchEffect` and `DynamicFormItemChoice.vue`'s `combinedValidation` was extracted into `packages/core/src/utils/buildRestrictionValidations.ts`. Both call sites now share one implementation; `required`/`xsd_required` stays each caller's own concern (not part of the shared function), matching the previous bullet.
- Added a dedicated test proving a choice-hosting branch's own `validation` rule still runs after the registration change, both for a branch with its own nested choice (`DynamicFormItem.logic.test.ts`) and for the `singleChild` fast path (`DynamicFormItemChoice.validation.test.ts`), since the `singleChild`/`disabled` early returns are a separate code path from the general case.
- Coverage: full-suite statement/line/function coverage held or improved; branch coverage moved from 92.76% to 92.71% (1064/1147 to 1056/1139 branches), entirely inside `DynamicFormItem.vue`. Verified the uncovered-branch count there is unchanged (6, same pre-existing `?? ` fallback branches as before the fix) and `DynamicFormItemChoice.vue`'s own total/covered branch counts are unchanged from baseline; the dip is denominator shrinkage from moving already-covered restriction-building code out into the shared util, not a new untested path.
- `specs/components.md` was not updated: `restriction`/`validation` were already documented as generic `FieldMetadata` properties with no stated exclusion for choice-hosting fields, so this fix restores previously-unreliable behavior rather than changing documented behavior.
