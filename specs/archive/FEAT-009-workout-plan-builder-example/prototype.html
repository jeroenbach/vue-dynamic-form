Section 1 — Narrative intro#page-intro

Workout Plan Builder

Working slug /examples/workout-plan, working title "Workout Plan Builder" (Open question 1; nav placement relative to Choices / Checkout / FEAT-006 / FEAT-008 still Jeroen's). Page sets aside:false and a pageClass, widening the content column to ~1100px, exactly like the checkout page.

A good session is not just a bag of exercises, it is an order. You warm up before you lift. You train the big compound movements while you are freshest, then the smaller isolation work. You finish with a cooldown. Shuffle those blocks and you have not just rearranged a list, you have changed the workout. The order is the plan.

The builder below is a single repeatable ordered choice: one metadata tree, one template, no bespoke engine code. Each row is a block, with genuinely different fields per block type. Move a block up or down and the live summary on the right recomputes, and the convention checks below flag or clear a violation, from the reorder alone, with no field edit.

Where these rules come from The ordering conventions this page checks (warm up first, compound movements before isolation movements, do the most demanding work while freshest, cool down last) are common published coaching guidance, cited below the way the checkout cites Baymard and Shopify. One deliberate, published exception, pre-exhaustion training, is called out honestly next to the compound-before-isolation rule.
Not training advice This is a library demo, not a coach. The conventions reflect common convention, not a guarantee of a correct or safe program for any individual. Nothing you build here is saved anywhere: no account, no storage, no history. It lives only in the form's own in-memory values.

Two VitePress callouts: an info block sourcing the rules (mirrors checkout's Baymard/Shopify sourcing) and a warning block carrying the medical + no-persistence disclaimers from the spec's Disclaimers paragraph.

Section 4 — Convention-violation surfacing#violations

The five order-only rules surface in two coordinated places: the summary rail's "Convention checks" list (names the rule and the offending block by displayed position) and an amber badge on each offending row. Open question 2 decides blocking vs warning; the working assumption below is non-blocking (a plan is not "invalid data"), with the blocking alternative shown for reference.

The five conventions checked

  • Warm-up first — a Warm-up block must be the first block (boundary rule).
  • Cooldown last — a Cooldown / stretch block must be the last block (boundary rule).
  • Compound before isolation — no compound strength exercise may appear after any isolation strength exercise, anywhere in the list (position-class rule over the whole list).
  • No back-to-back same muscle group — two consecutive strength exercises must not target the same muscle group.
  • No adjacent high-intensity cardio — two cardio blocks that are both high intensity must not be adjacent.
One honest exception The compound-before-isolation rule has a well-known, deliberate exception: pre-exhaustion training intentionally isolates a muscle first, then hits it with a compound movement. The page names this exception in copy, the same candour the checkout uses for its "ordering is UI-level, not XSD" caveat, so the rule reads as convention with a known override, not an absolute law.

Variant A — non-blocking warnings (working assumption)

An out-of-convention plan is dead-lifting-in-the-wrong-order, not corrupt data, so a warning reads better than a hard error. Submit stays enabled. Only derived display flags are needed, no real validation rules. This is the working assumption pending Open question 2.

The plan, a repeatable ordered choice

The whole form is one node: maxOccurs > 1 combined with a choice, in explicit selection mode, rendered in add-order with a persisted order the reorder control can write.

WorkoutPlanExample.vue
{
  name: 'plan',
  minOccurs: 0,                  // an empty plan is a valid, mandatory empty state (Q3)
  maxOccurs: 12,                 // a reasonable ceiling (Q3)
  explicitChoiceSelection: true,
  displayOrder: 'added',         // render in session add-order
  preserveOrder: true,           // every branch has children, so order is persisted data
  fieldOptions: { label: 'Your plan' },
  choice: [ warmUp, strength, cardio, cooldown ],
}

Four block types, four shapes

Each branch is a genuinely different block, not a cosmetic relabel: two single-duration branches, a five-field strength branch, and a three-field cardio branch. All four declare children, so preserveOrder stays on for the whole choice.

Note for the architect: no branch field is named order, so there is no collision with preserveOrder's written order child (the dev-mode warning never fires). Units are minutes only (Open question 4). Per-type caps (maxOccursTotal: 1 on Warm-up and Cooldown) are the working assumption for Open question 3.

The reorder control

The up/down buttons write the two affected occurrences' order values directly through useFormContext().setFieldValue, exactly as SplitPaymentLedgerRow does. The engine's renderedChoiceOccurrences re-sorts with no remount.

The live summary module

A small, pure, synchronous TypeScript module (model: splitPaymentLedgerMath.ts) takes the blocks in displayed order and returns the summary figures and the violations. A template-level computed reads the form's values through vee-validate's own context, not computedProps, and feeds the summary rail.

workoutPlanMath.ts
export function summarizePlan(blocks: Block[]): PlanSummary {
  return {
    totalDuration: blocks.reduce((m, b) => m + (b.duration ?? 0), 0),
    profile:       countByTypeAndIntensity(blocks),
    muscleGroups:  distinctMuscles(blocks),   // strength blocks only
    violations:    checkConventions(blocks),  // order-only rules, see below
  };
}

export function checkConventions(blocks: Block[]): Violation[] {
  const v: Violation[] = [];
  if (blocks.length && blocks[0].kind !== 'warmUp')
    v.push({ rule: 'warmUpFirst', atIndex: 0 });
  // ...cooldownLast, compoundBeforeIsolation (scan for first isolation,
  //    flag any later compound), noBackToBackMuscle, noAdjacentHighCardio
  return v;
}

The convention checks

Five order-only checks, each reorder-fixable. Under the working assumption (Open question 2) they are derived display flags surfaced in the summary rail and on the offending rows; they do not block submit. If a rule must block, it becomes a hidden-leaf validation rule re-triggered the way the checkout's splitPaymentCoverage is (its createTransitionTracker helper is gone since FEAT-010, so avoid validating an empty required field at mount). Submit itself is gated only on the form's aggregate meta.valid (field-level validity), trustworthy since FEAT-010.

What It Demonstrates

  • A repeatable ordered choice (maxOccurs > 1 + explicitChoiceSelection + displayOrder: 'added' + preserveOrder) as the entire form, not a footnote.
  • Four block types with genuinely different field shapes, all childful.
  • Per-type caps via maxOccursTotal (one Warm-up, one Cooldown) alongside the shared choice budget.
  • Position badges from globalIndex + 1, and up/down reordering that writes the affected order values directly.
  • A live summary rail (duration, intensity profile, muscle coverage, violations) that recomputes on every reorder.
  • Five cross-row, order-only convention checks that a reorder alone satisfies or violates.

How It Works

The plan is a choice with maxOccurs > 1 and explicitChoiceSelection. Each Add button pushes an occurrence into its branch's field array; reordering rewrites two order values and the engine re-sorts renderedChoiceOccurrences with no remount. The summary and the violations come from a pure module read through vee-validate's useFormContext, not computedProps. Submit is gated on the form's aggregate meta.valid, trustworthy since FEAT-010. No new engine primitive is involved.
