# Story: Reorder controls and the live summary rail (the payoff)

## Decided without Jeroen (research)

Settled from research during story prep, not reviewed by Jeroen. Override any of these freely.

- Default fixture → conformed to the approved seven-block shape (decided in ST-01); AC3/AC4 totals and counts updated accordingly
- Intensity profile cardio row → the feature's DECIDED wording restored ("Cardio 2 blocks · high"); cardio occurrences with differing intensities fall back to count-only, dots carry the detail
- Review blocker 1 → explicit numeric `order` seeds (1..7) plus `preserveOrder: true` moved into ST-01, since the engine renders keyless seeded occurrences branch-grouped (verified in `DynamicFormItemChoice.vue`); this story keeps only the chevron wiring

## Functional

### User story
As a docs reader exploring the workout plan builder example, I want to reorder blocks with up/down buttons and watch a live side panel of total duration, intensity profile, and muscle coverage recompute in real time, so that I can see that reordering is a real, data-affecting action, not cosmetic.

### Acceptance criteria

1. Given `preserveOrder: true` is enabled on the `plan` choice (in place since ST-01) and at least two occurrences exist, When the down arrow on a block (or the up arrow on its display-neighbor) is clicked, Then the clicked block and its display-neighbor swap their persisted `order` values via two `setFieldValue` order writes (one targeting the row's own occurrence path, one the neighbor's), byte-for-byte the `SplitPaymentLedgerRow` technique, and the engine's `renderedChoiceOccurrences` re-sorts with no remount.
2. Given the up control on the first displayed block and the down control on the last displayed block, When rendered, Then both are disabled (30% opacity, never hidden) regardless of block count, including the boundary case of exactly one block, where both controls on that single row are disabled simultaneously.
3. Given the seeded seven-block default plan from ST-01 (warm-up 10, three strength blocks with no duration, cardio 15/12, cooldown 8), When the summary rail renders, Then "Total duration" shows "45 min timed · 7 blocks", computed as `collectBlocks(values.plan, BRANCHES)` summed over only the blocks that carry a duration (warm-up, cardio, cooldown), with a note that strength blocks are counted in the block total but not timed.
4. Given the same default plan, When the "Intensity profile" section renders, Then it shows count-only rows for Warm-up, Strength, and Cooldown ("Warm-up 1 block", "Strength 3 blocks", "Cooldown 1 block") with no invented intensity word on any of them (correcting the stale prototype's "Warm-up 1 · low" / "Cooldown 1 · low" rows, which have no `intensity` field behind them per the feature's own review finding 3), while the Cardio row carries its intensity word per the feature's DECIDED finding 3 ("Cardio 2 blocks · high" in the default, since both cardio occurrences are high; when cardio intensities differ the row falls back to the count only and the dot sequence carries the per-occurrence detail), plus a low/moderate/high colored dot sequence of exactly the cardio occurrences in their current displayed order (default: rose, rose for rowing-high, jump rope-high), reusing the existing state palette.
5. Given the same default plan, When "Muscle coverage" renders, Then it shows the distinct muscle groups across strength blocks as slate chips ("Legs", "Chest"; two chips, not three, since "Legs" appears on two occurrences), with no duplicate chip.
6. Given zero strength blocks exist, When "Muscle coverage" renders, Then it shows a single italic empty chip reading "No strength blocks yet".
7. Given any add, edit, remove, or reorder of a block, When the change commits to the form's `values`, Then the rail recomputes live with no manual refresh, because the host computed (`summary = summarizePlan(collectBlocks(values.plan, BRANCHES))`) reads `values` directly and never registers a `computedProps` closure.
8. Given a numeric leaf (`duration`, `sets`, `reps`), When read by `collectBlocks`, Then it is coerced with `Number(...)` before any arithmetic, mirroring the checkout's `parseAmount`; the form model and the submitted values JSON both keep every numeric leaf as a string (e.g. `"duration": "10"`), per the feature's DECIDED resolution of its own review finding 1. No number-input slot performs its own coercion.
9. Given the add-toolbar budget is exhausted (12 of 12, or a per-branch cap reached), When a block is reordered near either boundary, Then the reorder still succeeds; the budget cap and the reorder control are independent gates.
10. Given the zero-block empty state (inherited from ST-01), When the rail renders, Then "Total duration" reads "0 min timed · 0 blocks", "Intensity profile" shows no rows, and "Muscle coverage" shows the empty chip from AC6.
11. Given the whole form, When `html.dark` is toggled, Then the reorder boundary-disabled state and every rail section resolve through the existing CSS custom properties with no page-specific dark markup.

### Edge cases
- Removing every strength block returns "Muscle coverage" to the empty chip (AC6) with no stale chip left behind.
- Removing every timed block (warm-up, cardio, cooldown) drops "Total duration" to "0 min timed · N blocks" where N is whatever non-timed (strength) blocks remain.
- With exactly two blocks, both boundary disables (first block's up, second block's down) are exercised from each row's own perspective, not only from one row.
- Reordering a cardio block changes the dot sequence's order immediately (the dots track display order, not insertion order).

### Out of scope
- The five convention checks, the "Convention checks" rail section, the row amber badge/border, and `#reorder-payoff` (ST-03; this story's rail has only three sections: Total duration, Intensity profile, Muscle coverage).
- Narrative prose, the metadata walkthrough, cross-links, and nav/sidebar discoverability (ST-04).
- Any change to the condition fields, validation, or add/remove behavior ST-01 already built.

## Design reference

Implements the reorder chevrons and the summary rail's first three sections from `../../prototype.html#live-form` and `../../prototype.html#plan-summary`, plus the reorder-boundary chevron-disabled states in `#block-states` that ST-01 left visually present but unwired. The fourth rail section shown in the prototype ("Convention checks") is explicitly out of scope here; this story's `WorkoutPlanSummary.vue` renders only the first three sections, matching the feature's seam split (seam 2 lists "total duration + intensity profile + muscle coverage" only, not the conventions).

Two corrections to the prototype's still-stale rail markup:
- Per the feature's DECIDED resolution of review finding 3, the warm-up / strength / cooldown rows are count-only with no invented intensity word (the prototype's "Warm-up 1 · low" / "Cooldown 1 · low" are stale and must not be built); only the cardio row carries an intensity word, since cardio is the single branch that declares an `intensity` field.
- DECIDED (research): the story prep draft had generalized the cardio row to count-only (written against a since-dropped three-cardio fixture); with the approved seven-block default's two cardio occurrences (both high), the cardio row follows the feature's DECIDED finding 3 literally and reads "Cardio 2 blocks · high". The one case the feature left unspecified, cardio occurrences with differing intensities, falls back to the count-only row and lets the dot sequence (one dot per cardio occurrence, in display order) carry the per-occurrence detail; that fallback adds no new copy or UI surface (smallest scope). Source: the approved FEAT-009 spec, DECIDED on review finding 3 and Open question 5.

## Architecture reference

Builds, extending ST-01's files:
- `workoutPlanMath.ts` (new, pure, framework-free, mirroring `splitPaymentLedgerMath.ts`): `collectBlocks(planValues, branches)` flattens the `plan` choice's four branch arrays into one `Block[]`, ordered by each occurrence's persisted `order`, coercing `duration` / `sets` / `reps` with `Number(...)` as it reads them (AC8); `summarizePlan(blocks)` returns `{ totalDuration, profile, muscleGroups }` in this story (no `violations` field yet; ST-03 extends both the return shape and the function body to add `violations: checkConventions(blocks)`). `checkConventions` itself is not declared in this story.
- `WorkoutPlanSummary.vue` (new, the sticky rail, a 5th presentational file per ADR-4): takes the host-computed `summary` prop and renders the three sections from the acceptance criteria above (Total duration, Intensity profile with the dot sequence, Muscle coverage). The "Convention checks" section does not exist in this story's version of the file; ST-03 extends it in place.
- `WorkoutPlanExample.vue` (extends ST-01's file): `preserveOrder: true` and the explicit numeric `order` seeds (1..7) are already in place from ST-01 (see the DECIDED note below); this story adds the `summary = summarizePlan(collectBlocks(values.plan, BRANCHES))` computed reading `useDynamicForm().values` directly (ADR-3, never `computedProps`) and renders `<WorkoutPlanSummary :summary="summary">` beside `<DynamicForm>` in the two-column layout.

  DECIDED (research), resolving review finding 1: the engine does **not** auto-produce the authored interleaved order. `normalizeOrder` seeds a keyless occurrence's `order` from its branch-grouped position (`DynamicFormItemChoice.vue:852-860`), and without `preserveOrder` the display sort key is the session-local `insertionOrders` map, under which seeded (never-added) occurrences are keyless and render branch-grouped too (`renderedChoiceOccurrences`, `:341-369`). So the fix is two-part and lives in ST-01, not here: ST-01's `initialValues` seed an explicit numeric `order` (1..7, authored interleaved sequence; `normalizeOrder` preserves an existing contiguous `order`), **and** `preserveOrder: true` moves up from this story into ST-01's metadata, because without it the explicit `order` values would be ignored and ST-01's own AC1 display order would collapse to branch-grouped. `order` is engine-managed and numeric (unlike the string-seeded user numerics of DECIDED finding 1). This story's remaining reorder scope is unchanged: wiring the chevrons and the boundary disables. Why this is not a feature contradiction: the approved design requires the interleaved clean default on the page; which story flips one metadata flag is internal slicing staging (the feature's seam list is "input for the scrum-master", not design surface). Sources: `DynamicFormItemChoice.vue` (verified), approved FEAT-009 Design `#live-form`.
- `WorkoutBlockRow.vue` (extends ST-01's file): wires the up/down chevrons already present but unwired from ST-01, each writing the two affected occurrences' `order` values via `useFormContext().setFieldValue(path.order, n, false)`, and the boundary-disable logic (first/last displayed occurrence), both byte-for-byte the `SplitPaymentLedgerRow` technique. The row-level violation badge does not exist yet (ST-03).

No `packages/core/src/` change and no changeset: `preserveOrder`, `renderedChoiceOccurrences`, `globalIndex`, and `useFormContext().setFieldValue` are all already exported and already proven end to end by the checkout's split-payment ledger, per the feature architecture's verification.

**Documentation:** none assigned to this story; no `docs/reference/*` or `docs/guide/*` page changes (no public API change). The page itself stays the minimal, unlinked scaffold ST-01 created; ST-04 writes the prose that describes this story's reorder and summary behavior.

Dependencies: depends on ST-01 (extends `WorkoutPlanExample.vue`, `WorkoutPlanTemplate.vue`'s slots via `WorkoutBlockRow.vue`). ST-03's `checkConventions` and row badge depend on this story's `collectBlocks` / `summarizePlan` / `WorkoutPlanSummary.vue`; ST-04's region excerpts depend on this story's finished reorder/summary source to describe accurately.

## QA plan

### Test infrastructure constraint

Same constraint as ST-01 (see its "Test infrastructure constraint, read this first"): `docs/` has no vitest/`@vue/test-utils`/jsdom, no `test` script, and is excluded from `pnpm-workspace.yaml`. Not re-litigating that decision here (already raised in FEAT-001/ST-03's QA plan, declined, and restated by ST-01). The consequence carries forward unchanged: every criterion for the new docs-local code (`WorkoutPlanSummary.vue`, `workoutPlanMath.ts`, the extensions to `WorkoutPlanExample.vue` and `WorkoutBlockRow.vue`) is manual-only, and the plan instead cites the existing `packages/core` suites that guard the engine mechanisms this story leans on.

**`workoutPlanMath.ts` specifically.** The feature architecture calls it out as "the one non-trivial, independently testable unit" because it is pure, synchronous, and framework-free, exactly like the checkout's `splitPaymentLedgerMath.ts`. Checked the precedent directly: `docs/.vitepress/theme/components/splitPaymentLedgerMath.ts` has zero test file anywhere in the tree (confirmed by glob; no `__tests__` or `*.test.ts` next to it, and no cross-package import of it from `packages/core`'s suites either). It ships covered only by manual verification, same as every other docs component. This story follows that exact precedent for `workoutPlanMath.ts`: no automated test is added for `collectBlocks` / `summarizePlan`, even though the module's purity would make it trivial to unit test if a runner existed. Reasons against bending the rule for just this file:
- Importing it from `packages/core`'s vitest via a relative cross-package path would blur the published package's test boundary (the file lives outside the workspace specifically so `docs/` changes carry no changeset and no coverage-gate exposure) and would need to survive `docs/`'s own build/lint independent of `packages/core`'s tsconfig include globs, which is not guaranteed.
- Adding a bespoke, one-off vitest config just for this file is a cross-feature tooling decision (the same one ST-01 and FEAT-001/ST-03 already declined to re-open per-story), not something ST-02 should decide unilaterally.

Consequence: AC3, AC4, AC5, AC8, and AC10's arithmetic are verified manually by reading the rendered figures against hand-computed expectations, not by calling `collectBlocks`/`summarizePlan` directly in a test. If a docs test runner is ever added (cross-feature decision for Jeroen), `workoutPlanMath.ts` is the first and best candidate to retrofit, since it needs no DOM and no form context.

### Reactivity / render-count

This slice is the one in the feature that most directly needs the render-count discipline `*.analytics.test.ts` exists for, but the instrumentation itself (`analytics` setting, `data-testid="<path>-analytics-render-count"`) is a `packages/core` engine feature with no docs-level equivalent, and this story adds no `packages/core/src/` code. So no new `*.analytics.test.ts` file is added by this story; instead:
- **Regression guard (cited, not new)**: `DynamicFormItemChoice.analytics.test.ts` already guards that a `setFieldValue` write on one occurrence's field does not cause unrelated sibling occurrences to re-render, which is exactly the shape of this story's reorder write (two `setFieldValue` calls on two occurrences' `order` fields). Re-running it via `pnpm run ci:test` is this story's automated signal that the reorder write pattern has not regressed at the engine level.
- **Manual reactivity check**: because the host's `summary` computed reads `useDynamicForm().values` directly (ADR-3) rather than `computedProps`, there is no risk of the infinite-loop guard (`assertNoComputeLoop`) firing; confirm during manual testing that no console warning or error appears on any add/edit/remove/reorder action (a `computedProps` misuse would surface there).
- **Why this matters here specifically**: this is the first story in the feature where `WorkoutBlockRow.vue` calls `useFormContext()` at all (ST-01's row only received props/slots). A sloppy reorder implementation (e.g. reading `values` inside a `watch` without `flush: 'sync'` consideration, or writing both `order` values in two separate ticks) could cause a visible double-render or a flash of incorrect order; the manual check above ("no remount", perform rapid successive reorders) is this story's closest substitute for a render-count assertion given the infra constraint.

### Coverage

No `packages/core/src/` change, so `pnpm -r ci:test:coverage`'s tracked baseline is unaffected in either direction; confirm with `git diff --stat -- packages/` showing empty before closing out the story. `workoutPlanMath.ts`, `WorkoutPlanSummary.vue`, and the extensions to `WorkoutPlanExample.vue`/`WorkoutBlockRow.vue` all ship with no automated coverage number, consistent with every other docs component and explicitly not a regression this story introduces (see Test infrastructure constraint above).

### Compliance findings

1. **(blocker) AC8 fails under normal use: `number`-typed fields silently become JS numbers in the model on any edit, not strings.** `WorkoutPlanTemplate.vue`'s `#default-input` slot binds `@input="handleChange"` directly to vee-validate's `useField` handler on a native `<input type="number">`. vee-validate's own `handleChange` → `normalizeEventValue` → `parseInputValue` (`docs/node_modules/vee-validate/dist/vee-validate.mjs:619-627`) special-cases `el.type === 'number'` and returns `el.valueAsNumber` (a real number), not `el.value` (a string), whenever the bound handler receives a native `Event`.
