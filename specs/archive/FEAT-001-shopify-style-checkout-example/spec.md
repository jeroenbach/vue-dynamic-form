## Problem & goal

Docs readers evaluating `@bach.software/vue-dynamic-form` (developers and technical decision makers comparing schema-driven form libraries, and template authors learning advanced patterns) currently see every metadata shape demonstrated in isolation: a basic form, arrays and groups, choices, dynamic fields, validation, a wizard, and an advanced client-onboarding wizard. None of these pulls everything together into one realistic, famous, benchmarked flow, and none demonstrates the repeatable ordered choice shape (`maxOccurs > 1` combined with `choice`), one of the engine's richest and least obvious capabilities.

This feature adds one flagship docs page that rebuilds a Shopify-style one-page checkout: the structure, not the branding. It opens with the most famous checkout UX anecdote on the web (a major retailer's guest-checkout change, per Jared Spool, never naming the retailer) and Baymard Institute's independently verified checkout benchmarks, states Shopify's own published conversion claims as the attributed benchmark being rebuilt, shows the live form, then reveals it is one typed metadata tree plus one template component. It culminates in a split-payment section: a repeatable, ordered list of payment sources where each row shows a computed remaining amount depending on the rows above it, and reordering redistributes that remainder live, the one shape (repeatable ordered choice) no existing docs page covers.

Success looks like: a published, linked docs page that tells this narrative accurately and with correct attribution, embeds a live interactive checkout that stays near Baymard's ideal of 8 visible fields through their own reduction tactics, walks through the metadata tree below the form the same way the other advanced docs pages do, and ends with a working split-payment demo that proves the repeatable ordered choice shape, built entirely on the library's existing public surface.

## Functional overview

**Page structure.** One docs page, live form on top, metadata walkthrough below, matching the pattern already used by `docs/examples/wizard.md` and `docs/examples/advanced.md`. The live form area is two columns on wide screens: form sections left, a sticky order-summary cart right (line items and totals, reacting live to the form), stacking above the form on narrow screens. The page sets `aside: false` and widens the doc column for itself, so the walkthrough opens with a short inline TOC in place of the "On this page" outline (per DECIDED under Design decisions, sticky cart). The opening copy carries the narrative arc: the $300M-button anecdote and Baymard's numbers establish the stakes, the Shopify benchmark states what is being rebuilt and why it is credible, the form is shown live, and a short reveal states that everything above is one typed metadata tree rendered through one template component, exactly as the rest of the docs demonstrate elsewhere.

**Baseline checkout flow.** A shopper moves through: express checkout vs manual entry (a `choice`), contact details, a delivery address group (country enumeration driving per-country postal code validation through `computedProps`, mirroring the conditional `minOccurs`/`hide`/`options` `computedProps` pattern already used in `FormExampleClientOnboardingPlanner.vue`), an optional business toggle that reveals a VAT field, a shipping method `choice` whose pickup branch nests a pickup-point field, a payment method `choice`, an optional "bill to a different address" toggle that reuses the same address subtree, and an optional gift message with a `maxLength` limit and a character counter, added as new template chrome on top of the existing field components (the counter lives in the template, not the engine). Baymard's five reduction tactics keep the default visible field count near their ideal of 8: one full name field, no address line 2 by default, discount/gift codes tucked behind a link rather than shown inline, billing fields hidden until the toggle is used, and no account-creation step.

**Payment and the split-payment finale.** The payment section is where the feature's flagship shape lives. The straightforward path is a single payment method `choice` (card / iDEAL / PayPal / Klarna with an installment-plan selector), each branch with its own fields and validation, so a visitor immediately sees branch switching work. An explicit "split your payment across multiple methods" entry point then reveals the advanced case: a repeatable ordered choice (`maxOccurs > 1` + `choice`, in explicit-selection mode) of payment sources (gift card, voucher, card, PayPal), added top to bottom. Each row computes and displays a "remaining amount" derived from the order total minus everything applied in the rows above it. Reordering rows changes which rows count as "above" a given row, so the remaining amounts recompute and redistribute live. See Constraints for how this is achievable without any new engine capability. The opt-in escalation described here is confirmed (per DECIDED under Open question 2), protecting the field-count target while giving the simple choice its own moment.

**Disclaimers.** The page states plainly, near the payment fields, that card and iDEAL inputs are inert demo fields collecting no real payment data, and in the intro that the page rebuilds Shopify's checkout *structure*, not its visual design.

### Design decisions

- **Two layers, one house style.** The page is two visual registers: VitePress prose (the narrative, the walkthrough, the callouts) in the default-theme doc column (max 860px), and the live form rendered through the docs' existing `AdvancedFormTemplate` look (slate neutrals, indigo for choice selection, sky for primary actions and toggles, rose errors, emerald success, amber warnings). The prototype reuses that exact palette and the existing component shapes rather than inventing new chrome, so the built page drops into the site without a restyle.
- **Neutral, explicitly not Shopify.** The form has its own neutral card styling. Nothing copies Shopify's colors, type, or logo. The intro callout states plainly that we rebuild the structure, not the brand.
- **Narrative order is fixed** (matches Problem & goal and the research report): the $300M-button anecdote (retailer never named, "a major retailer", +45% / +$300M), then Baymard's verified numbers (11.3 fields, 5.1 steps, ideal of 8, 17% abandon), then the attributed Shopify benchmark ("a study Shopify commissioned from one of the Big Three consulting firms", 15% average / up to 36% / Shop Pay up to +50%, flagged as vendor-published), then the live form, then the "one metadata tree, one template" reveal. Every externally sourced claim carries its binding attribution inline; the Baymard link is live.
- **Baymard reduction tactics are visible in the layout, not just claimed:** single full-name field, address line 2 behind a link, discount/gift codes behind links, billing hidden behind the "same as shipping" toggle (on by default), no account step. Annotations in the prototype call out each tactic where it appears so the architect keeps them.
- **Payment leads, split payment is the finale.** Default payment is a single four-branch `choice` (card / iDEAL / PayPal / Klarna), shown first because branch switching is the most immediate proof of the metadata-driven approach. The four branches are deliberately four different flavours: card inputs, a bank `<select>`, an empty redirect branch, and Klarna's installment enumeration (3 / 6 / 12 months). Split payment is a separate opt-in escalation behind a link, so it never inflates the default field count.
- **Sticky cart right of the form, where the VitePress aside normally sits.** DECIDED (Jeroen): the live form area is two columns on wide screens, form sections left and a sticky order-summary cart right (line items, subtotal, shipping, VAT included, total), matching Shopify's own form-left/cart-right layout. ### States policy (applied consistently across every section)

- **Default / pristine:** clean fields, Required/Optional tag only, no color beyond neutral.
- **Focus:** sky ring (`box-shadow` with `--primary-ring`); annotated where a static snapshot cannot show it.
- **Invalid:** rose border on the control plus a rose message below it (mirrors `ErrorMessage.vue`). Shown at least once per input kind (email, postal, VAT, gift-message length).
- **Valid:** subtle emerald border only, no checkmark noise (shown on email and NL postal).
- **Disabled:** muted surface, `not-allowed` cursor (phone, capped split-payment Add button, blocked submit, edge ▲/▼).

## Architecture (feature level)

### Public API impact and changeset conclusion

**None. Docs-only. No changeset.** Nothing under `packages/core/src/` changes. Every capability this feature needs is already exported and was verified against the installed code, not just `specs/components.md`:

- **Repeatable ordered choice** (split payment): `explicitChoiceSelection` + `maxOccurs > 1` + `displayOrder: 'added'` + `preserveOrder: true`, with the persisted `order` child written through the normal field-write path. Confirmed present on `FieldMetadata` and demonstrated live by `FormExampleChoiceExplicitRepeatable.vue` on `/examples/choices`.
- **Reordering** by writing the two affected occurrences' `order` values directly. Confirmed achievable: `DynamicForm.vue` itself reads the active form through vee-validate's `useFormContext()` (line 8, 40), so any docs component rendered inside the form tree can call `useFormContext()` to obtain `setFieldValue` and write a sibling occurrence's `order`. No `moveItem`/`swapItems` engine primitive is needed, matching the Constraints note. vee-validate is pinned at `>=4.12` (`pnpm-workspace.yaml` catalog), where `useFormContext` is available.
- **Per-country postal validation** via `computedProps`: confirmed by the existing conditional-field pattern in `FormExampleClientOnboardingPlanner.vue` (a `computedProps` fn reads a sibling value and flips `minOccurs`/`hide`/`options`). For the reused address subtree, `ComputedPropsFieldType` exposes readonly `path` and `parent` (`FieldMetadata.ts:362-367`), so the postal field's `computedProps` can derive its own country sibling path from `thisField.parent.path` instead of a hard-coded absolute path, letting one address fragment serve both delivery and billing.
- **Cross-field "rows must cover the total"**: confirmed by the existing cross-field pattern in `FormExampleValidation.vue` (`endDate`/`confirmPassword`): a `validation` closure reads the sibling value(s) and a `computedProps` fn calls `validateField(path)` to re-trigger when the dependency changes. The same two-part pattern gates submit on split-payment coverage.

Because the public surface is untouched, no `defineMetadata` generics, props, slots, settings, or validation rules change, and no consumer is affected.

### Data flow: split-payment remaining computation and reorder

State lives entirely in the vee-validate form (`values`), provided by `useDynamicForm` in `CheckoutFormExample.vue`. Each split-payment occurrence sits under its branch array (for example `splitPayment.giftCard[0]`) and carries a persisted numeric `order` child (via `preserveOrder`) plus its amount/code/inert fields.

- **Display order** is owned by the engine: `DynamicFormItemChoice.renderedChoiceOccurrences` sorts by each occurrence's persisted `order` (the `preserveOrder` tier), so the `splitPayment-choice-array-item` slot iterates rows already in display order and exposes `globalIndex` (the display index).
- **Per-row remaining** is derived, not stored. The order total is a module/example constant. A row's "remaining after" = `orderTotal - sum(amount of every occurrence whose order < this row's order)`. Each `SplitPaymentLedgerRow` computes this from `values` (read via `useFormContext`) plus its own `order` value, so it needs no cross-row plumbing. Remainder-covering sources (card / PayPal) display `max(0, remainingBefore)` as their applied amount.

- **Overshoot on reorder** (a remainder-covering source moved above a fixed source): every displayed applied and "remaining after" amount clamps at 0, and the ledger flips to a clearly messaged over-the-total state: the amber "still unassigned" readout becomes a rose banner naming the exact overshoot amount. The coverage gate already keeps submit blocked whenever `remainingToAssign !== 0`, in either direction, so no extra gating is needed. Reordering itself stays unrestricted; remainder-covering sources are never pinned. (Per DECIDED under Adversarial review finding 3.)
- **Reordering**: the up/down control swaps this occurrence's `order` with the adjacent display-neighbor's `order` (found by scanning occurrences in `values` for `order === myOrder ± 1`) through two `setFieldValue(path.order, n, false)` writes. That value change propagates two ways automatically: the engine re-sorts `renderedChoiceOccurrences` (rows visually reorder) and every row's remaining computed re-runs (amounts redistribute). No remount, no new primitive.
- **Coverage gate**: a `remainingToAssign` computed in `CheckoutFormExample.vue` = `orderTotal - sum(all applied amounts)`. Deactivating split restores the single choice's requirement.

  DECIDED (research): This clarification was recorded post-approval after ST-03's adversarial review showed the formula above, read literally, evaluates to the full order total with zero split rows and would block the default single-payment checkout from ever submitting. The scoping follows from what is already approved (Open question 2's opt-in decision, Open question 7's "rows cover the total" wording, and the prototype's enabled place-order state with a single payment method selected), so no approved behaviour changes. The boolean-leaf activation model follows the existing toggle-reveal pattern; deriving "active" from the occurrence count was rejected because the prototype's revealed-but-empty state ("No payment sources yet") must exist before any occurrence is added.

### ADR notes

- **ADR-1 Separate `CheckoutFormTemplate` instead of extending `AdvancedFormTemplate`.** Context: the split payment needs a bespoke ledger rendering for its `-choice-array` family, unlike the onboarding wizard's `RepeaterCard`. Decision: new template with its own `FieldValueTypes` union and a dedicated `splitPayment` type. Alternative: add ledger slots to `AdvancedFormTemplate` behind a flag. Rejected: it widens a shared template's type surface and risks the onboarding examples, for no narrative gain (the page sells "one template" for the checkout, which a dedicated file delivers).
- **ADR-2 Reorder through `useFormContext().setFieldValue`, row-local.** Context: reorder must write two occurrences' `order` and no engine move helper exists. Decision: the row component obtains `setFieldValue` from vee-validate's own context (the same channel `DynamicForm` uses) and swaps `order` with its display-neighbor. Alternative: lift reorder into `CheckoutFormExample` and inject per-row callbacks into the slot. Rejected: slot plumbing is awkward and the row already has everything it needs via context, keeping the ledger self-contained.
- **ADR-3 Remaining amounts derived, not stored; `order` is the only persisted ordering data.** Context: the running remainder must redistribute on reorder. Decision: compute remaining per row from `values` + `order`; persist only `order`. Alternative: write computed remaining into each occurrence. Rejected: redundant state that can desync; `order` changing already drives the recompute reactively.
- **ADR-4 Reused address subtree via relative `thisField.parent.path`.** Context: delivery and billing must share one address fragment including the per-country postal rule. Decision: the postal `computedProps` derives its country sibling path from `thisField.parent.path`. Alternative: two copies of the address metadata with absolute paths. Rejected: duplication defeats the "same subtree reused" point the page makes, and absolute paths cannot serve two mount points.
- **ADR-5 Coverage gate: live local computed for UX, hidden-field cross-field rule for the hard block.** Context: cross-field revalidation in vee-validate does not fire automatically when a sibling occurrence changes. Decision: disable the button on a local `remainingToAssign` computed (instant), and enforce the block authoritatively with a hidden coverage field carrying the `validation` + `validateField` re-trigger pattern checked by `handleSubmit`. Alternative: rely solely on the validation rule. Rejected: its live feedback can lag a tick; the belt-and-suspenders keeps the demo honest and the hard block correct.

### Risks

- Seam 3 is the only genuinely non-trivial build: self-computing per-row remainders plus `order`-swap reordering plus a hidden cross-field coverage gate, all on the template side. It is achievable on the existing surface (verified above) but is the slice most likely to surface an engine gap; if it does, that is a feature-level amendment per the Constraints rule, not a story workaround.
- Open question 8 (the misnamed existing page) is resolved: the nav slice relabels the existing page "Client Onboarding Wizard" (DECIDED under Open question 8).
- **Flagged by ST-02's implementation**: an `explicitChoiceSelection` choice's own aggregate `meta.valid` never recovers after its first branch activation, even once every field underneath is individually valid and `errors` is empty. Root-caused to `DynamicFormItem.vue` only calling `fieldContext.validate()` for leaf nodes on value change, by design, so a choice/group node's own validity is only ever checked once, at activation time, while it is still necessarily empty. This does not block any story: ADR-5 already specifies gating the split-payment submit state on a local computed (`remainingToAssign`) rather than `meta.valid`, and ST-02 independently confirmed that same shape is required for its own place-order button (a local `canSubmit` computed, not `meta.valid`). No `packages/core/src/` change was made or is proposed; this is recorded here so ST-03 and ST-04 do not rely on `meta.valid` anywhere in this feature, and so a future engine-level fix (outside this feature's scope) has a starting point if one is ever pursued. See ST-02's Implementation notes for the full repro and trace.
- **Flagged by ST-02's second fix round**: a nested `choice` field's own validation registration can outlive its component's unmount. Reproduced by mounting a `choice`-containing branch (e.g. selecting "manual", which contains its own `shippingMethod`/`paymentMethod` choices), then switching to a sibling branch that unmounts it (e.g. "express"): a real submit click afterwards still fails full-form `validate()` on the unmounted choices' paths as "required", even though neither section exists in the DOM any more and the live `errors` map reads empty. Same category as the `meta.valid` finding above (a fresh full-form `validate()` surfacing a failure the live `errors`/`canSubmit` reads do not catch), but a distinct mechanism (a stale registration surviving unmount, not a stuck aggregate on a still-mounted node). ST-02 worked around it by no longer calling vee-validate's own `handleSubmit` at all: the actual submit decision is gated directly on the same local `canSubmit` computed that already drives the button's disabled state, bypassing the fresh `validate()` that surfaces the stale registration. No `packages/core/src/` change was made or is proposed; recorded here so ST-03 and ST-04 do not assume `handleSubmit`'s own validation pass is safe to rely on wherever a `choice` can be mounted and later unmounted in this feature, and so a future engine-level fix has a starting point. See ST-02's Implementation notes, Fix round 2, for the full repro and trace.

## Constraints & assumptions

- **The repeatable ordered choice shape already exists and is already demonstrated.** `DynamicFormItemChoice` supports `explicitChoiceSelection` + `maxOccurs > 1` today, with `displayOrder: 'added'` (session add-order, in-memory) and `preserveOrder: true` (a persisted `order` field written into each occurrence's own values) as opt-in flags; see `specs/components.md` and the live demo at `docs/examples/choices.md` (`FormExampleChoiceExplicitRepeatable.vue`). This feature reuses that mechanism for split payment; it is not introducing it.
- **No built-in reorder/move helper exists.** Neither the array slot props nor the choice-array-item slot props expose a `moveItem`/`swapItems` action. `DynamicFormItemChoice`'s render order reads each occurrence's persisted `order` value reactively (`renderedChoiceOccurrences`'s sort key), so a template can implement "move up"/"move down" (or drag) by writing the two affected occurrences' `order` values directly through the normal field-write path, the same way any other field is written. This is expected to be sufficient for the "reordering redistributes the remainder live" behavior without any new engine primitive. If architecture work finds this insufficient, that is a feature-level gap: it must be raised back into this spec (amended and re-approved), never patched around silently in a story, per the project's hard rule on story-level overrides.
- **Ordering is UI-level, not XSD occurrence semantics.** Per this project's XSD-fidelity convention, the order in which split-payment rows are displayed and the `order` value written into each occurrence's data are both library-level, `computedProps`/template-driven behavior layered on top of the shape; they have no equivalent in `<xs:choice>` and must not be described as XSD semantics in the page copy.
- **No public API or core change is expected.** Everything described above (choice, array, `computedProps`, the existing validation rules, and reading/writing a sibling occurrence's own field) is already exported per `specs/components.md`. No changeset is expected under `packages/core/src/`; confirm this holds once architecture is done.
- **`docs/` is a separate workspace.** It is excluded from the pnpm workspace and has its own `node_modules` (install separately per `CLAUDE.md`).
- **A nav collision exists today.** `docs/.vitepress/config.ts` already has an "Examples" nav entry and an "Advanced example" sidebar link pointing at `/examples/advanced`, which is `docs/examples/advanced.md`, the existing Client Onboarding Wizard (`FormExampleClientOnboardingPlanner.vue`), a multi-step onboarding wizard with its own narrative and metadata tree. This feature needs its own page and nav entry distinct from that one; see Open questions 1 and 8.
- **Citation rules are binding** (from `research/checkout-example/raw/verification.md`, carried over from `research/checkout-example/final-report.md`):
  - The 15% average / up to 36% / Shop Pay +50% conversion figures are vendor-published and must always be attributed to "a study Shopify commissioned from one of the Big Three consulting firms," never stated as independent fact.
  - The $300M-button retailer must never be named. Say "a major retailer," Jared Spool's own wording; the Best Buy identification is unverified rumor.
  - Baymard's figures (11.3 average fields, 5.1 average steps, an ideal of 8 fields, 17% of users abandoning a purchase due to checkout complexity) were verified directly and can be cited as fact.
- **Writing rules from `CLAUDE.md` apply to every word this feature produces:** no em dashes anywhere in the page copy, Vue code always camelCase, and no references to spec, story, or finding identifiers in any code or comments the feature adds.

**Fix round 2 (this audit), addressed:**

- **Production-only split-payment mount failure, fixed.** Root cause was not hydration timing: the throw happens on every load (pristine, no interaction needed) because `packages/core` resolves `vee-validate` from its own, separately pnpm-installed copy (`packages/core/node_modules`, keyed `vee-validate@4.15.1_vue@3.5.44_typescript@5.9.2_`), while `docs/` resolves its own direct `useFormContext()` import from a different physical copy of the same version (`docs/node_modules`, keyed `vee-validate@4.15.1_vue@3.5.44`, since `docs/` sits outside the pnpm workspace). Vite's production build (Rollup) bundles both as separate modules, each with its own `Symbol('vee-validate-form-context')`, so `useDynamicForm()`'s `provide()` (reached through the library's copy) and the ledger's own `useFormContext()` (reached through the docs copy) inject against different symbols. Confirmed by instrumenting both sides: the component ancestry and the `provide()`/`inject()` prototype chain were completely correct throughout, and `CheckoutFormExample`'s own `instance.provides` genuinely held the key, just under a different symbol object than the one the ledger looked up. `pnpm docs:dev` never reproduced it because Vite's dev dependency pre-bundler collapses every `'vee-validate'` specifier into one shared dev chunk regardless of which physical file it would otherwise resolve from, masking the duplication; only Rollup's production build keeps the two resolutions separate. `<ClientOnly>` and lifecycle-timing fixes in the ledger components were both considered and rejected: neither changes which physical module a given import resolves to, so both would leave the underlying mismatch, and the broken injection, fully intact. Fix: `docs/.vitepress/config.ts` now sets `resolve.dedupe: ['vee-validate']`, Vite's documented remedy for duplicated dependency copies in linked monorepos, forcing every resolution onto the one copy actually installed under `docs/node_modules`. Re-verified on the production build with Playwright: a pristine load is clean, the full split-payment flow (add gift card/voucher/card, see the exact fixture amounts, reorder, overshoot with the exact banner, cover the total, submit to the success banner) and the single-payment card path both work; `pnpm docs:dev` is unchanged. Pipeline checks (`ci:test`, `ci:lint`, `ci:typecheck`, `ci:test:coverage`, `docs:build`) all pass at the recorded baseline; no `packages/core/src/` change, no changeset. Details in ST-03's Implementation notes, Fix round 3.
