# Story: Reorder controls and the hard-blocking curfew rule (the payoff)

## Decided without Jeroen (research)

Settled from research during story prep (post-approval ladder), not reviewed by Jeroen. Override any of these freely.

- Review finding 1 (blocker) → the Architecture reference states both flags: `displayOrder: 'added'` and `preserveOrder: true` (the engine never re-sorts without both)
- Review finding 2 (blocker) → `collectProgramOccurrences` swaps its ordering key to the persisted `order` child, stated explicitly
- Review finding 3 → the seeded default data carries an explicit `order` child per occurrence so `normalizeOrder()` cannot re-sequence it
- Review finding 4 → AC5's "unit test" becomes a worked example in the PR description (docs/ has no test runner); the feature's ADR-7 wording reconciled to match, promotion path recorded

## Functional

### User story
As a docs reader exploring the run-of-show builder example, I want to reorder program items with up/down buttons and watch a hard-blocking curfew check react live, so that I can see that the order of the program causally decides whether it is valid, not merely how it displays.

### Acceptance criteria

1. Given `preserveOrder: true` is now enabled on the `program` choice (every branch already has `children`, so no metadata reshape is needed) and at least two occurrences exist, When the down arrow on an item (or the up arrow on its display-neighbor) is clicked, Then the two occurrences swap their persisted `order` values via two `setFieldValue(path.order, n, false)` calls, and the engine's `renderedChoiceOccurrences` re-sorts with no remount.
2. Given the up control on the first displayed item and the down control on the last displayed item, When rendered, Then both are disabled (reduced opacity, never hidden) regardless of item count, including the boundary case of exactly one item, where both controls on that single row are disabled simultaneously.
3. Given the hidden `curfew` vehicle leaf (`minOccurs: 0`, so it never fails on occurrence count) with a `validation` closure that reads the host's reactive `curfewBreaches` computed, When any amplified item (a band/DJ set, an open dance floor, or a speech with its `onMic` toggle on) ends after the curfew anchor, Then the vehicle fails validation naming the offending position(s) by number, `meta.valid` becomes false, and the submit button disables with a rose helper line ("Resolve the curfew violation on position N before saving").
4. Given a curfew breach, When the breaching item is reordered to a position where its computed end no longer exceeds the curfew, Then the breach clears live with no field value edited, matching the design's resolved finding 3: the default/documented program ships with exactly one breaching amplified item and one obvious single up-move that clears it, and no second amplified item in the default data breaches on its own. Exact durations are tuned at implementation time against `runOfShowMath`, within the per-kind increment lists ST-01 shipped.
5. Given the amplified-music curfew anchor is moved past midnight (for example from `23:00` to `00:30`), When the breach check runs, Then `findCurfewBreaches` compares entirely in one minutes-since-event-start frame (ADR-7, resolving finding 2), verified by a worked example covering a past-midnight curfew (start `20:00`, curfew `00:30`), documented in the PR description; promoted to an automated unit test if and when a `docs/` vitest setup is added (ST-01 QA plan finding 1, recorded for Jeroen, not a gate). DECIDED (research), resolving finding 4: reworded from "with a unit test" because `docs/` has no vitest runner to execute one; the feature's ADR-7 wording carries the matching reconciliation note.
6. Given any item whose own computed end exceeds the curfew, When it renders, Then it shows the rose card border, an inline rose message with an alert icon, and a rose clock-time chip, derived from the same `runOfShowMath` module as a display flag (not a per-occurrence validation leaf).
7. Given the computed clock crossing the curfew time between two adjacent rows, When the timeline renders, Then the dashed curfew marker line renders as a trailing element of the earlier of the two rows (the design's resolved finding 1: the container's single passthrough slot has no insertion point between specific rows), and the marker's position moves live as durations above it change.
8. Given a speech item, When its `onMic` toggle is switched off, Then that speech item is excluded from the amplified set and cannot by itself trigger a curfew breach; switching it back on re-includes it live.
9. Given the submit button, When `meta.valid` is true (no curfew violation), Then it is enabled; When clicked while valid, Then it shows the loading-spinner state and then the success state naming the item count and the program's start-to-end span, matching `#submit-bar`.

### Edge cases
- Moving a non-breaching item never introduces a new spurious breach; the shipped default data must not reproduce the "breach jumps to a different item" failure mode the design's finding 3 called out.
- Reordering works independently of the add-toolbar budget being exhausted (20 occurrences).
- With exactly two items, both boundary disables are exercised from each row's own perspective, not only from one row.
- A curfew anchor set earlier than the event start wraps to the next day exactly like the venue-close anchor already does (ADR-7).
- Removing the only remaining breaching item clears the curfew error along with the item itself.

### Out of scope
- The summary panel's timeline-at-a-glance, venue-overflow indicator, per-kind counts, and the cake-after-dinner / no-leading-break convention warnings (ST-03 extends `RunOfShowSummary.vue`, created here with only the curfew banner).
- Narrative prose, the metadata walkthrough, cross-links, and nav/sidebar discoverability (ST-04).
- Any change to the branch field shapes, add/remove behavior, or non-curfew validation ST-01 already built.

### Architecture-reference gap found while planning (read before the AC mapping)

Before mapping acceptance criteria to tests, two things the task brief asked me to check for granularity turned out to be real gaps, not just caution. Both are filed as findings below (findings 1 and 2) because they affect whether AC1 and AC9's inherited clock-cascade math can be correct as architected, but I record the evidence here since it shapes every test in the AC1/AC9 rows.

- **`displayOrder` is never mentioned in this story's Architecture reference.** It says only "flips the `program` choice's `preserveOrder` to `true`." Verified against the engine (`packages/core/src/components/DynamicFormItemChoice.vue:348`): `renderedChoiceOccurrences` does `if (!displayOrder.value) return occurrences` before any sort; `displayOrder.value` is `field.value?.displayOrder === 'added'`. So `preserveOrder: true` alone, with `displayOrder` left at ST-01's `'grouped'`, writes a persisted `order` child but the engine never reads it to re-sort the render. AC1's claim "the engine's `renderedChoiceOccurrences` re-sorts with no remount" is false unless `displayOrder: 'added'` is also set. The task brief's framing (ST-02 "owns the switch to `displayOrder: 'added'` + `preserveOrder: true`") is correct per the engine source and per ADR-1/seam 2, but the story's own Architecture reference does not say it. See Finding 1.
- **`collectProgramOccurrences`'s ordering key is never restated in this story.** ST-01's Architecture reference explicitly says it orders by "branch declaration order, then per-branch array index" in that story, and that "ST-02 swaps the ordering key to the persisted `order` child." This story's Architecture reference extends `runOfShowMath.ts` for `findCurfewBreaches` but never states the `collectProgramOccurrences` key swap. Per the engine (`DynamicFormItemChoice.vue:352-354`), once `displayOrder: 'added'` and `preserveOrder` are both on, the engine sorts by the persisted `order` field. If `collectProgramOccurrences` keeps ST-01's branch-order+index key, the row clock chips and the curfew math would disagree with the displayed order the instant two branches interleave post-reorder, the identical bug class ST-01's review finding 1 already caught and resolved once. See Finding 2.
