Plan the reception: a run-of-show builder

One typed metadata tree, one template. The planner builds the evening as an ordered list of program items: speeches, dinner courses, a band set, open dancing, cake, breaks. Nobody types a clock time. Each row carries only a duration, and the engine computes every row's start and end from the event's start plus the sum of every duration above it. The same running-fold cascade the split-payment ledger proves on the Checkout page, with time instead of money.

The payoff is the amplified-music curfew. Whether a band set or the dance floor ends before the curfew depends only on what sits above it, so dragging it earlier can fix a violation and pushing a long dinner course above it can create one. Order changes the clock, and the clock decides what is valid.

What you are looking at

Everything in the live form below is rendered from one metadata tree through one neutrally styled template. Clock times are computed, never entered.

Reordering is UI-level, not XSD

The display order and the per-row order value it writes are library behavior layered on the repeatable choice; they have no equivalent in <xs:choice> occurrence semantics. See the Choices page for the generic mechanics this page specializes, and the Inbox Rules Builder for the other order-as-the-subject showcase.

Metadata walkthrough (below the live form)

One metadata tree, one template

Everything above is declarative. The engine walks the tree, classifies each node by its shape, and renders it through the neutral template. The page then walks the metadata the way the other advanced examples do: VitePress <<< region excerpts, "What It Demonstrates", "How It Works", "Related Source".

The repeatable ordered choice

// one occurrence per program item; six branches, genuinely different fields
program: {
  maxOccurs: 20,                      // Open question 7
  minOccurs: 0,                       // empty program is valid
  explicitChoiceSelection: true,
  displayOrder: 'added',
  preserveOrder: true,                // every branch declares children (Q2)
  choice: {
    speech:  { children: { speaker, duration, onMic } },
    dinner:  { children: { course, duration } },
    band:    { children: { act, duration } },        // amplified by definition
    dance:   { children: { duration, musicStyle } }, // amplified by definition
    cake:    { children: { duration, note } },        // note added so preserveOrder applies
    break:   { children: { duration } },
  },
}

Exact field names / option increments are architecture's to finalize (Open question 3). preserveOrder requires every branch to have children (Open question 2).

What It Demonstrates

  • A repeatable ordered choice (maxOccurs > 1 + choice) as the page's whole subject, with six branch flavours
  • Template-driven reordering: up/down buttons writing two order values through useFormContext().setFieldValue
  • A computed clock cascade: durations in, clock times out, read live off form values
  • A hard-blocking, order-sensitive curfew rule reusing the hidden-vehicle-leaf + validateField pattern
  • A live summary panel: timeline, end vs venue close, curfew status by position, counts per kind
