# Component & API inventory

Living inventory of the library's public surface. The spec-workflow agents consult this before proposing anything new; the developer updates it whenever a change touches the public surface (a new export, prop, slot, setting, or validation rule, or a behavioral change to one). Keep entries to one or two lines; the source and `CLAUDE.md`'s Architecture section carry the detail.

Everything listed as exported comes from `packages/core/src/index.ts` and ships in `@bach.software/vue-dynamic-form`. Changing any of it needs a changeset (see CLAUDE.md).

## Components (exported)

| Component | Role |
| --- | --- |
| `DynamicForm` | The runtime engine. Accepts `metadata` + a `template` component, normalises paths and defaults (`correctMetadataAndSetDefaults`), provides settings via provide/inject, renders the `DynamicFormItem` tree. |
| `DynamicFormItem` | The core recursive item. Registers with vee-validate (`useField`), evaluates `computedProps`, detects its shape (array / choice / parent / input) and delegates or renders into the template. The most complex file in the codebase. |
| `DynamicFormItemArray` | Renders repeatable nodes (`maxOccurs > 1`), one sub-tree per occurrence. |
| `DynamicFormItemChoice` | Renders mutually exclusive branches (`choice` non-empty). `explicitChoiceSelection: true` switches to selection-first rendering: no branch mounts until the `-choice` slot's `addChoiceOccurrence(branchKey)` is called (`removeChoiceOccurrence`/`canAddChoiceOccurrence`/`activeChoiceOccurrences` complete the set). Flag absent/`false` keeps today's value-driven behaviour unchanged. For `maxOccurs: 1`, selecting a branch marks it active and switching clears the deselected branch's data; `preserveOnSwitch: true` (opt-in, `maxOccurs: 1` only) stashes the deselected branch's values in an ephemeral, instance-local ref before clearing, and restores them on switch-back with fresh touched/validation state — the stash never enters form `values`. A form reset (`resetForm`, or `resetField` aimed at the choice's anchor path; detected via vee-validate's `pendingReset` flag) re-derives the explicit selection purely from the freshly reset values, exactly like a fresh mount (a branch holding restored data reads as selected, an empty one deselects), and drops the preserve-on-switch stash, so a stale pre-reset selection can never combine with restored initial values into two active branches on a `maxOccurs: 1` choice, and data the reset discarded can never resurface from the stash on a later switch-back. For `maxOccurs > 1`, `addChoiceOccurrence(branchKey)` pushes a real occurrence into that branch's own field array (via `useFieldArrayExtended`, over a reactive per-branch path so it stays correct when nested inside a reindexing array), `removeChoiceOccurrence(branchKey, index)` removes a specific occurrence, and `activeChoiceOccurrences` lists every active occurrence across branches grouped by branch declaration order then index within branch, derived purely from the value tree. Occurrence math follows XSD batching: a branch's own `maxOccurs` is the slot size, not an independent cap, so `canAddChoiceOccurrence` is governed by the shared choice-level budget alone (in raw-item units at that batch size), optionally tightened by the branch's opt-in non-XSD `maxOccursTotal`. A budget shortfall caused by siblings (e.g. data loaded over the choice's `maxOccurs`) may disable an empty branch but never drops a branch's headroom below its filled item count, so branches holding loaded data stay editable and never show a shifting budget-relative (or negative) cap error; over-budget states surface through the choice-level rules instead. `usedChoiceOccurrences` reports consumption in choice-occurrence units (`sum of ceil(branch item count / branch maxOccurs)`), the same unit `xsd_choiceMinOccurs` validates in. A single (`maxOccurs: 1`) choice renders its container through the `*-choice`/`default-choice` slot, a repeatable (`maxOccurs > 1`) choice through `*-choice-array`/`default-choice-array`, and each repeatable occurrence through the `*-choice-array-item`/`default-choice-array-item` slot, iterating an internal `renderedChoiceOccurrences` computed rather than `activeChoiceOccurrences` directly. `renderedChoiceOccurrences` equals `activeChoiceOccurrences` unless the branch's `displayOrder` metadata is `'added'`, in which case it is a deterministic two-key sort: occurrences added this session sort ascending by an add-order key, after every occurrence with no such key (loaded saved data), which keeps its grouped position. The sort key is tier-dependent: an ephemeral, instance-local `insertionOrders` map keyed by the stable occurrence key (assigned at add-press time, never in `values`) when `preserveOrder` is off, or the occurrence's own persisted `order` value (see below) when it is on. `globalIndex` is the loop index over `renderedChoiceOccurrences`, so it reflects the displayed sequence, not always the grouped one. `preserveOrder: true` (opt-in, `maxOccurs > 1` only, requires every branch to declare `children`) writes a numeric `order` field into each occurrence's own values on add (`push({ order })`, counted across every branch of the choice) and keeps the values contiguous 1..N through a shared `normalizeOrder()` pass (stable sort by each occurrence's current `order`, a missing value slotting in at its grouped position, only ranks that actually changed written via `setFieldValue(path.order, n, false)`) that runs at mount, after every removal, and when the flag flips on, so gapped or missing loaded values self-heal while keeping their relative order. One scalar-leaf branch (no `children`) disables `preserveOrder` for the whole choice, with a dev-mode `console.warn` at mount naming the branches (a branch declaring its own child named `order` also warns); the ephemeral tier keeps covering every branch shape. The three ordering flags (`preserveOnSwitch`/`displayOrder`/`preserveOrder`) are read reactively from the metadata, so they flip live without a remount; flipping `preserveOrder` off strips `order` from every occurrence, while mounting with the flag absent never touches loaded data. `order` is real submitted data (kept by `removeNullValues`, changes no `xsd_choiceMinOccurs` or occurrence-budget outcome) and has no slot prop of its own; a template reads it like any other declared child field. |
| `DynamicFormItemWizard` | Renders a `wizard: true` node (see `FieldMetadata.wizard` below), checked before choice/array/parent detection in `DynamicFormItem`. Owns `currentStepIndex` (local state), `pages` (`field.children ?? []` — a co-declared `choice` or `maxOccurs > 1` is inert and triggers a one-time `console.warn` per ignored property), `isFirst`/`isLast`/`isValidating`, and navigation: `next()` (linear wizard: validates the current page via `validateSection` and advances only on success; non-linear wizard with `allowForwardJump`: surfaces the page's errors but always advances), `prev()` (unconditional, no validation), `gotoStep(index, options?)` (backward jumps always free and silent; forward jumps require `allowForwardJump`, then surface the current page's errors without blocking; `validateOnJump` defaults on and can be set `false` for a silent jump; both configurable at config or call-time-option level, call-time wins). Page paths are read from the corrected metadata tree (`overridePath(page.path, pathOverride)`), never re-derived. Renders the container through the `-wizard`/`default-wizard` slot (receives `WizardAttributes`: `fieldContext: LimitedFieldContext`, `currentStepIndex`, `pages` (the engine's resolved page list), `pageCount`, `isFirst`, `isLast`, `isValidating`, `wizardConfig: Required<WizardConfig>` (the resolved navigation config, defaults applied, so a stepper reflects the mode without re-reading raw `fieldMetadata.wizard`), `next`, `prev`, `gotoStep`) and each page through the `-wizard-page`/`default-wizard-page` slot (receives `WizardPageAttributes`: `isCurrent`, `pageIndex`, `currentStepIndex`, `isFirst`, `isLast`, `wizardConfig: Required<WizardConfig>`, `next`, `prev`, `gotoStep`), rendered for every page (not only the current one). A page's own content renders through its own shape (parent/array/choice) via a plain `DynamicFormItem`; there is no `-wizard-page-array`/`-wizard-page-choice` combinatorial family. All pages stay mounted; the template gates visibility with `v-show` on `isCurrent` (never `v-if`, or the page's fields are cleared and deregistered on navigation away). A choice of wizards or a repeated wizard falls out of the existing choice/array mechanics with no bespoke code (nest `wizard: true` inside a choice branch or an array item's children). No public composable, no provide/inject: all state travels only as slot props. |
| `DynamicFormTemplate` | The rendering bridge for user templates. Dispatches to named slots with priority fallback (per-type slot → `default-input`/`default-array`/`default-array-item`/`default-choice`/`default-choice-array`/`default-choice-array-item`/`default-wizard`/`default-wizard-page` → `default`; the `-choice-array` families are checked before the plain `-array` families because their type strings also end in `-array`/`-array-item`). Slot props typed via `defineMetadata`. The `-choice`/`default-choice` (single, `maxOccurs: 1`) and `-choice-array`/`default-choice-array` (repeatable, `maxOccurs > 1`) slots both receive `ChoiceAttributes` (extends `ArrayChoiceAttributes` with `addChoiceOccurrence`, `removeChoiceOccurrence`, `canAddChoiceOccurrence`, `activeChoiceOccurrences: ChoiceOccurrence[]`, `usedChoiceOccurrences: number`). The `*-choice-array-item`/`default-choice-array-item` slots (one per rendered occurrence of a `maxOccurs > 1` explicit choice) receive `ChoiceArrayItemAttributes` (extends `ItemAttributes` with `branchKey: string`, `globalIndex: number`, the occurrence's zero-based position across every branch's rendered occurrences (renumbers live on add/removal, never stored), and `insertionOrder?: number`, its ephemeral add-order position this session, `undefined` for an occurrence loaded rather than added; also carries `removeItem`), mirroring `*-array-item`. The `-wizard`/`default-wizard` (container) and `-wizard-page`/`default-wizard-page` (per-page visibility wrapper) slots are described under `DynamicFormItemWizard` above. |

## Composables & core (exported)

| Export | Role |
| --- | --- |
| `defineMetadata` | Pure type-level configuration carrier (`<FieldValueTypes, ExtendedFieldProperties, SlotProperties, ExtendedSettingsProperties>`); runtime values are empty stubs. |
| `useDynamicForm` | Wraps vee-validate's `useForm()`; adds `useFieldValue(path)` (typed path accessor) and `validateSection(sectionPath)` (wizard-step validation). Its `keepValuesOnUnmount` option (and the per-field `fieldOptions.keepValueOnUnmount`) now works as documented for every field rendered through `DynamicFormItem`: when the effective flag is `true`, unmounting a field no longer overwrites vee-validate's own preserved value. Attribute fields (a field's `attributes` entries) clear on unmount when the owning field's own value is gone (an empty complex value keeps no stale attributes); when the owning field still has a value, its attributes follow the same keep flags as any other field. The returned `meta.valid` aggregate (vee-validate's own `useForm()` value, no new accessor) is now live for a group, choice-anchor, or array node: `DynamicFormItem` runs a silent revalidation on every descendant change for non-input shapes, and `DynamicFormItemArray` does the same beside its own gated visible validation. A leaf's own `meta.valid` was already live on every value change independent of `validateOnValueUpdate` (vee-validate's own `setValue` always validates, silently when not asked to surface an error); only the visible error was ever deferred by that setting. Both new silent revalidations skip while a reset or a `shouldValidate: false` write is suppressing validation, matching every other validate call site. |
| `useValidatePartialForm` | Partial-form validation. Quirk: when called in the same component as `useDynamicForm` it reads the form context from the instance's own `provides` instead of `inject`. |

## Types (exported)

`DynamicFormItemProps`, `DynamicFormSettings`, `DynamicFormTemplateComponent`, `FieldMetadata`, `GetDynamicFormSettingsType`, `GetMetadataType`, `MetadataConfiguration`, `RequireOnly`, `ValidationMessage`.

`DynamicFormTemplateComponent` is the type of `DynamicForm`'s `template` prop: `Component | ((...args: any[]) => any) | object`. Deliberately wider than Vue's `Component` so a generic template SFC (script setup with `generic="..."`, which compiles to a generic call signature neither `Component` nor `DefineComponent` accepts) can be passed directly without a cast; the `object` member keeps the compiler-generated runtime prop check accepting object-based components. The engine widens the slot types internally, so the prop type carries no slot information.

`FieldMetadata` gained `explicitChoiceSelection?: boolean` (additive, default off; see `DynamicFormItemChoice` above). It is excluded from `ComputedPropsFieldType`: `computedProps` cannot change it at runtime, so a choice's render mode can never flip mid-form.

`FieldMetadata` also gained `preserveOnSwitch?: boolean` (additive, default off; ST-05), a per-choice flag sitting next to `explicitChoiceSelection` that opts a `maxOccurs: 1` explicit choice into preserve-on-switch (see `DynamicFormItemChoice` above). Read reactively from the metadata (switches from the flip onward follow the new setting), but excluded from `ComputedPropsFieldType` so the metadata prop stays its one sanctioned channel.

`ChoiceOccurrence` (`{ branchKey: string, index: number }`), `ChoiceAttributes`, and `ChoiceArrayItemAttributes` are declared in `DynamicFormTemplate.vue` next to `ArrayChoiceAttributes`/`ItemAttributes` and surface through the `-choice`/`-choice-array`/`-choice-array-item` slot typing; not (yet) re-exported from `index.ts`.

`FieldMetadata` also gained `wizard?: boolean | WizardConfig` (additive, default off), marking a node as a wizard (see `DynamicFormItemWizard` above). `WizardConfig` (`{ allowForwardJump?: boolean, validateOnJump?: boolean }`) and `WizardGotoStepOptions` (the same shape, for call-time `gotoStep` overrides) are declared in `FieldMetadata.ts` and re-exported through the existing `export *` in `index.ts`. `wizard` is excluded from `ComputedPropsFieldType`, alongside `explicitChoiceSelection`/`preserveOnSwitch`/`maxOccursTotal`, for the same static-metadata-only reason: `computedProps` cannot flip which component renders a node mid-form. `WizardAttributes`/`WizardPageAttributes` are declared in `DynamicFormTemplate.vue`, matching the `ChoiceAttributes` convention (declared in-file, not re-exported from `index.ts`).

`FieldMetadata` also gained `maxOccursTotal?: number` (additive, default off), meaningful on a `choice` branch: an opt-in, non-XSD hard cap on that branch's total raw occurrence count across the whole choice, independent of the XSD batching `maxOccurs` drives (no `<xs:choice>` equivalent). Applies in both explicit mode (`canAddChoiceOccurrence` disables the branch's add once reached) and auto mode (clamps the branch's rendered array headroom). Excluded from `ComputedPropsFieldType` alongside `maxOccurs`, for the same static-metadata-only reason: occurrence capacity must not flip mid-form via `computedProps`.

`FieldMetadata` also gained `displayOrder?: 'grouped' | 'added'` (additive, default `'grouped'`), meaningful on a `maxOccurs > 1` explicit choice: selects whether `DynamicFormItemChoice` renders occurrences grouped (today's behaviour) or in this session's add-order (see `DynamicFormItemChoice` above). Read reactively from the metadata: flipping it re-sorts the keyed occurrence list in place with no remount, and the session's add history survives the flip. Excluded from `ComputedPropsFieldType` alongside `explicitChoiceSelection`/`preserveOnSwitch`, so the metadata prop stays its one sanctioned channel.

`FieldMetadata` also gained `preserveOrder?: boolean` (additive, default off), meaningful on a `maxOccurs > 1` explicit choice whose branches all declare `children`: opts into writing a persisted `order` field into each occurrence's own values, surviving reload and loaded saved data, at the price of `order` becoming part of the submitted shape (see `DynamicFormItemChoice` above). Read reactively from the metadata: flipping it on seeds `order` into existing occurrences, flipping it off strips it. Excluded from `ComputedPropsFieldType` alongside `displayOrder`/`explicitChoiceSelection`/`preserveOnSwitch`, so the metadata prop stays its one sanctioned channel.

`FieldMetadata` also gained `presenceValue?: unknown` (additive, default `undefined`), meaningful only on a childless branch of an `explicitChoiceSelection: true`, `maxOccurs: 1` choice. On `addChoiceOccurrence(branchKey)` selecting that branch, the engine writes the marker into the branch's own value (via `setFieldValue`, `shouldValidate: false`), mirroring `clearBranch`'s `undefined` write on deselection, and never overwriting a value the branch already holds. A branch declaring `presenceValue` reads as selected (even on reload, with no click) whenever its own value is not `undefined`, bypassing the usual `checkTreeHasValue` emptiness check, and this reading also feeds `effectiveValuesCount` (sourced from `activeChoiceOccurrences` for the explicit single case), so a reloaded marker counts toward `xsd_choiceMinOccurs` too. No-op on a `maxOccurs > 1` branch (a pushed occurrence already represents presence there); inert on a branch that also declares `children`, with a one-time development warning naming the branch. Must be JSON-serializable; hashed as a constant in `hashField`'s mutable properties (not on its exclusion list). Excluded from `ComputedPropsFieldType`: it is static branch metadata, not a `computedProps` channel. `removeNullValues` strips an empty-object/empty-array marker back to `undefined`, documented at both ends.

`DynamicFormItemProps` gained `branchKey?: string`: set on the `DynamicFormItem` rendering a single occurrence of a repeatable explicit choice branch, it drives the `-choice-array-item` slot type suffix (mirroring `partOfArrayField`'s `-array-item` suffix) and is forwarded to the slot as `branchKey`.

`DynamicFormItemProps` also gained `globalIndex?: number` (additive, engine-internal wiring, mirroring `branchKey`): set alongside `branchKey` on a repeatable explicit choice occurrence's `DynamicFormItem`, it is the render-loop index over `renderedChoiceOccurrences` and is forwarded to the slot as `globalIndex`. `undefined` everywhere else (plain array items, non-explicit choices, `maxOccurs: 1` explicit choices, and any other field).

`DynamicFormItemProps` also gained `insertionOrder?: number` (additive, engine-internal wiring, mirroring `globalIndex`): set alongside `globalIndex` on a repeatable explicit choice occurrence's `DynamicFormItem`, it is that occurrence's ephemeral add-order position this session (1-based, in add-press order across every branch), `undefined` for an occurrence that existed before this session or was never added via `addChoiceOccurrence`. Forwarded to the slot as `insertionOrder`; never written to form `values`.

`DynamicFormItemProps` also gained `partOfAttributeField?: boolean`: set on each `DynamicFormItem` rendered through a parent's `#attributes` slot, marking it as an attribute item for unmount-cleanup purposes (the attribute is conditionally mounted based on whether the parent has a value).

`DynamicFormItemProps` also gained `attributeOwnerHasValue?: () => boolean`: bound alongside `partOfAttributeField`, a getter the attribute item calls on unmount to check whether its owner still has a main value. No owner value → the attribute clears regardless of `keepValuesOnUnmount`/`keepValueOnUnmount` (unchanged guarantee: an empty complex value keeps no stale attributes). Owner still has a value → the attribute follows the same keep flags as any other field.

## Validation rules (globally registered, `packages/core/src/core/validation.ts`)

`xsd_required`, `xsd_minOccurs`, `xsd_maxOccurs`, `xsd_choiceMinOccurs`, `xsd_choiceMaxOccurs`, `vdf_maxOccursTotal`, `xsd_minLength`, `xsd_maxLength`, `xsd_length`, `xsd_pattern`, `xsd_minInclusive`, `xsd_maxInclusive`, `xsd_minExclusive`, `xsd_maxExclusive`, `xsd_enumeration`, `xsd_whiteSpace`, `xsd_fractionDigits`, `xsd_totalDigits`.

`xsd_maxOccurs` (additive) validates an array field's (`DynamicFormItemArray`) raw item count against its `maxOccurs`, mirroring `xsd_minOccurs`'s wiring and timing exactly: pushed into `combinedValidation` whenever the array is not disabled (`maxOccurs !== 0`) and the metadata is well-formed (`maxOccurs >= minOccurs`; malformed metadata stays silently tolerated as it always was, since auto-add fills to `minOccurs` and removal is blocked below it, which would make the rule permanently unsatisfiable), placed after the existing `xsd_minOccurs` push so a co-occurring failure keeps the min message as the displayed error. Counts raw items including empty placeholders (the same quantity the "Add" affordance's cap governs), not filled values. Adds `messages.maxOccurs?: ValidationMessage` to `DynamicFormSettings` (additive, optional; placeholders `{field}`, `{0}`/`{max}`).

`xsd_choiceMaxOccurs` (additive) validates a choice field's (`DynamicFormItemChoice`) `usedChoiceOccurrences` against its `maxOccurs`, in choice-occurrence units (not raw item count), the same unit `xsd_choiceMinOccurs` and `canAddChoiceOccurrence` already use. `combinedValidation` was restructured from an early-return into a list so both the min and max choice rules can coexist if `minOccurs > maxOccurs` is ever declared (an unenforced invariant); under well-formed metadata the two are mutually exclusive. Adds `messages.choiceMaxOccurs?: ValidationMessage` (additive, optional; placeholders `{field}`, `{0}`/`{max}`).

`vdf_maxOccursTotal` (additive, `vdf_`-prefixed rather than `xsd_`: a non-XSD library extension with no `<xs:choice>` equivalent, namespaced because vee-validate's `defineRule` registry is global and last-write-wins, so an unprefixed name could silently collide with a consumer-defined rule) is a choice-level aggregate that fires when any branch's raw occurrence count exceeds that branch's own opt-in `maxOccursTotal` cap (`FieldMetadata.maxOccursTotal`, from FEAT-001). Pushed last into the same `combinedValidation` list as the two choice rules above, so a co-occurring `xsd_choiceMinOccurs`/`xsd_choiceMaxOccurs` failure wins the displayed `errorMessage`. Reports the first offending branch's cap in declaration order and never names the offending branch (`{field}` resolves to the choice's own anchor label). A single-branch choice (no `explicitChoiceSelection`) skips choice-level validation; there the cap clamps the branch's own rendered headroom (`min(maxOccurs, maxOccursTotal)`) so an over-limit load fails the branch's `xsd_maxOccurs` instead. `maxOccursTotal` can only tighten a branch's declared `maxOccurs`, never widen it, in every mode. Adds `messages.maxOccursTotal?: ValidationMessage` (additive, optional; placeholders `{field}`, `{0}`/`{max}`).

Message resolution priority: `settings.messages` → vee-validate `generateMessage` → rule default. Positional (`{0}`) and named (`{min}`, `{max}`, `{field}`) placeholders supported.

## Starter package (published separately)

`packages/starter/` ships as its own published package, `@bach.software/vue-dynamic-form-starter` (`publishConfig.access: public`, released through the same changeset pipeline as `packages/core/`). It is not the core engine's public surface (`packages/core/src/index.ts`), so it gets its own entry rather than sitting in the exported-components table above, but it is not private either: a change to its exports, `StarterValueTypes`, or `StarterFieldProperties` needs a changeset exactly like a `packages/core/` change does.

Any wrapper slot outside that handled set (a dedicated per-type slot for a built-in type such as `text-input`, or one for an `extendMetadata`-added type such as `richText-input`) is forwarded verbatim to the inner dispatcher (resolved at render time, so a slot the consumer adds after mounting is picked up too), so the engine's per-type-first slot priority applies to consumer-supplied type slots too; without this passthrough such a slot would be silently ignored and the field would fall back to the built-in markup. Choice chrome is now in place, still internal, no new export: an automatic-mode choice (`default-choice`) renders through `ChoiceField` (`sft-choice-group`, `-title`, `-desc`, `-body`; the engine renders every branch's fields unconditionally in automatic mode, letting the user fill in whichever one applies), while an explicit single-select choice (`heading-choice`) renders through `ChoiceSectionCard` (built on `SectionCard`) as an `sft-choice-grid` of `sft-choice-card` buttons, each with the radio dot, title, description, and an optional `StarterIcon` driven by the branch's `iconName` (now typed `StarterIconName`, migrated off the old docs `AppIconName`); `ChoiceSectionCard` forwards the section-wide `disabled` combined with each card's own `option.disabled` (`disabled || option.disabled`) to every `ChoiceCard` it renders; its `role="radiogroup"` wrapper also carries `aria-invalid="true"` when the choice has a validation error (read via `useAttrs()`, since `errorMessage` reaches it through attrs fallthrough to its `SectionCard` root rather than through its own declared props), giving the group an invalid target a screen reader or `focusFirstInvalid` can find even though the error text itself lives in the card's header. `ChoiceSectionCard` also accepts a `removeChoiceOccurrence` prop, used by a `watch` that deselects any active occurrence as soon as `disabled` turns true (so a disabled choice never keeps a value the user can no longer see or change). `StarterFormTemplate` wires both from the `-choice` slot: `:disabled="fieldMetadata.disabled || disabled"` and `:removeChoiceOccurrence="s.removeChoiceOccurrence"`. `ChoiceSectionCard`'s `ChoiceOption` type carries an additional `disabled?: boolean` field, forwarded by `StarterFormTemplate` from each branch's own `fieldMetadata.disabled` in the `heading-choice` option-mapping (`x.disabled`); the sibling mapping feeding `ChoiceArraySectionCard` carries the same field on the shared type but leaves it unused there, since that component already derives its own per-branch disabled state from `canAddChoiceOccurrence`. `ChoiceSectionCard` implements the full ARIA APG radio-group keyboard pattern on top of its existing `role="radiogroup"`/`role="radio"` markup: exactly one card is a Tab stop at a time (the selected enabled card, or the first enabled card when none is selected, every other card at `tabindex="-1"`), and `ArrowRight`/`ArrowDown` and `ArrowLeft`/`ArrowUp` move that Tab stop and the active selection among enabled cards, wrapping at both ends and skipping any card whose own `option.disabled` (or the section-wide `disabled`) excludes it. The move calls the same `addChoiceOccurrence` a click already uses, so it is indistinguishable from a click to the rest of the engine. `Space`/`Enter` activation on `ChoiceCard` is implemented with explicit `@keydown.space.prevent`/`@keydown.enter.prevent` handlers (the same pattern `ToggleSwitch` already uses), not left to the browser's native button activation, so it behaves identically across browsers and under test. A repeatable explicit choice (`heading-choice-array`) renders through `ChoiceArraySectionCard`, one Add button per branch inside `sft-choice-addbar`, reusing `sft-pill` for the used-of-max count and disabling (plus a visible `sft-choice-addbar-reason`, tied to the button through `aria-describedby`) only the branches whose own `canAddChoiceOccurrence` is false; each active occurrence (`default-choice-array-item`) renders through the same `RepeaterCard` the array shape uses. The choice option list passed to both card components is `fieldMetadata.choice.map(x => ({ value: x.name, title, description: x.choicePicker?.description ?? x.description, icon: x.iconName }))`, gated by `fieldMetadata.choicePicker?.show`, mirroring the ported `AdvancedFormTemplate` wiring exactly except for the `choicePicker?.description` fallback, which lets a branch show different text on its picker card than inside its own body once selected. `ChoiceArraySectionCard` is exported standalone; `ChoiceField`, `ChoiceCard`, `ChoiceSectionCard` stay internal (only `ChoiceSectionCard`'s `ChoiceOption` type is exported, for typing a consumer's own option list). Wizard, review, and success chrome completes the package: a wizard (`default-wizard`) renders through `FormWizard` (internal: `sft-wizard-head`/`-eyebrow`/`-title`, a `Stepper`, and an `sft-wizard-footer` with Back/Continue/Submit `AppButton`s, Back always rendered but visually `is-hidden` on the first page so the footer layout never jumps, Continue swapping for Submit on the last page), and each page (`default-wizard-page`) renders through a `v-show="isCurrent"` wrapper (never `v-if`, matching the engine's own page-registration contract) carrying `data-page="<pageIndex>"` and `data-testid="<pagePath>-page"`. `Stepper` (internal) marks a completed step `is-done` (a `StarterIcon` `check` glyph) and the active step `is-current`; upcoming steps are plain numbered and non-clickable unless `wizardConfig.allowForwardJump` is set. A step whose `Step.hasError` is true renders `is-error` instead: a red circle with an aria-hidden "!" glyph in place of the check/number, red step-title text, `aria-invalid` on the step button, and `" (contains errors)"` appended to its aria-label; the current step with an error gets a red ring instead of the usual sky one. Each step's title span carries a deterministic `${stepLabelIdPrefix}-step-label-${index}` id, so the wizard page container can point its `aria-labelledby` at it; `stepLabelIdPrefix` is a `useId()`-generated value `FormWizard` creates once per instance and passes to `Stepper` as a prop (`Stepper` falls back to its own `useId()` when mounted without that prop), independent of the optional `dataTestid` test-selector prop, so the accessible name exists even for a wizard whose root metadata sets `path: ''` (the pattern both `docs/examples/wizard.md` and `docs/examples/advanced` use). `FormWizard` holds a template ref on its `<main>` and watches the engine's `currentStepIndex` prop (pages never unmount, so there is no mount/unmount hook to react to instead): after a successful step change it focuses the new `[data-page]` container via the shared `focusWithTemporaryTabindex` helper (`tabindex="-1"` added at focus time, removed on the container's next blur) and sets that `aria-labelledby`; a counter guards against a stale focus call landing after a newer one when steps change rapidly. A blocked `next()` (the page being left fails validation) instead focuses the first invalid field on the current page via `firstInvalidWithin`, leaving `[data-page]` itself untouched. A failed final submit is outside `FormWizard`'s reach (it renders no `<form>`; the last-step button is a bare `type="submit"` left to the consumer's own form), so that case, and any non-wizard form's failed submit, is covered by the exported `focusFirstInvalid(containerEl)` helper, which a consumer calls from their own `onInvalidSubmit`. All three helpers live in the new internal `focus.ts` module (`focusWithTemporaryTabindex`, `firstFocusableWithin`, `firstInvalidWithin`, plus `focusFirstInvalid` itself, which `index.ts` re-exports; the first three stay internal). `firstInvalidWithin` matches the first `[aria-invalid="true"]` descendant that is not a `<button>` and is not hidden by `display: none` on itself or an ancestor (such as a `v-show`-hidden wizard page), so it skips the stepper's own error-flagged step buttons and a hidden page's field in favor of an actual, visible invalid field. The matched element is not guaranteed to itself be focusable (a `ChoiceSectionCard`'s `role="radiogroup"` wrapper carries `aria-invalid`, not any one card), so `focusFirstInvalid` and `FormWizard`'s own blocked-`next()` path both focus the nearest focusable descendant (`firstFocusableWithin`) when the match itself cannot take focus, landing on the group's roving tab stop instead of nowhere. `StarterFormTemplate` derives each page's `hasError` with a `pageHasErrors(pagePath)` helper (region-marked `wizard-step-errors`) that checks vee-validate's `useFormErrors()` against the page's path via the core package's `isPathInSection`. `FormWizard` exposes a `hasStepErrors` computed (`steps.some(step => step.hasError)`); on the last step, while it is true, it shows a `role="alert"` paragraph above the footer (`sft-wizard-alert`, `data-testid="<dataTestid>-step-errors-message"` when `dataTestid` is set, text from the overridable `stepErrorsText` prop) and disables the submit `AppButton`; the footer's top margin shrinks (`is-tight`) while the alert is shown. The final page of a wizard typically carries a single `wizardSummaryPage`-typed leaf field, dispatched through the `wizardSummaryPage` slot: it renders an `SectionCard` wrapping one `ReviewGroup` per entry in the field's `wizardSummary.groups` (typed `ReviewGroupProps[]`, so a group is `{ title, rows: [label, value][], dataTestid? }`) plus an `sft-confirm` banner when `wizardSummary.confirmation` is set, each `ReviewGroup`'s `edit` event calling `slotProps.gotoStep(i)` (the group's own index) to jump back. `ReviewGroup` and `SubmissionSuccess` are the two chrome pieces exported standalone (per ADR 4 of the feature): the docs' wizard demo pages compose them directly outside a `StarterFormTemplate` tree. `ReviewGroup` renders `sft-review-group`/`-header`/`-title`/`-list`/`-row`/`-key`/`-val`, an `Edit` button (`StarterIcon` `pencil`), and falls an empty row value back to a literal em dash placeholder glyph (`v || '—'`, a faithful port of the source table convention, not prose, so it does not fall under the project's em-dash writing rule). `SubmissionSuccess` wraps `SectionCard` too (`sft-success-hero`/`-badge`/`-title`/`-ref`, an `sft-timeline` list of `TimelineItem`s each `done` (static `checkCircle`) or `pending` (`loader` plus `sft-spin`, the one loading state in the whole package), and `sft-success-actions` with a JSON-toggle `AppButton` (local `showJson` ref) and a `reset`-emitting `AppButton`). Both standalone exports read their colours from the same document-root `--sft-*` variables as the rest of the package, so they are themed correctly with no wrapper class needed even mounted with no `StarterFormTemplate` ancestor; with no such ancestor they also never see an icon override, so they always render the Lucide default. A `grid`-typed parent node renders through its own `grid` slot as a bare `sft-grid-plain` div (no card chrome, full-row by default via `sft-span-full`, which spans the full row of any column count via `grid-column: 1 / -1`), laying its children out in a CSS grid. Grid layout is driven by three flat field properties: `columns` (the field's own children grid, `1`-`6` equal columns), and `colSpan` (`1`-`6` or `'full'`) plus `colStart` (`1`-`6`) for the field's placement in its parent's grid. Every value is `Responsive<T> = T | { base?, md?, lg? }` with mobile-first tiers (base from 0, md from 768px, lg from 1024px, each holding until a larger tier overrides it); a bare value means md-and-up (one column below). Every value maps to a static utility class shipped in the stylesheet, Tailwind-style: `sft-cols-{n}` (with `-base-`/`-lg-` tier infixes) on the grid body element, `sft-span-{n|full}` and `sft-col-start-{n}` (same infixes) on the chrome root. No inline styles and no custom properties are involved (the repo rule is: no `:style` bindings without Jeroen's approval), and classes do not inherit, so a parent's settings can never leak into a nested grid. The chrome components (`SectionCard`, `GroupField`, `FormField`, `CheckboxField`, `ChoiceField`, `ArrayField`, `RepeaterCard`) take `columns`/`colSpan`/`colStart` as props and bind the classes on their own elements; the `SectionCard`-wrapped cards (`ArraySectionCard`, `ChoiceSectionCard`, `ChoiceArraySectionCard`) receive them via attrs fallthrough onto their root `SectionCard`. Every chrome component that is not a plain input wrapper (`SectionCard` and its card wrappers, `GroupField`, `ArrayField`, `RepeaterCard`, `ChoiceField`) carries `sft-span-full` on its own root as a built-in full-row default, so only input fields flow per column; `FormField` is per-column by nature, and its leaf-heading usage opts into the full row at the template usage site instead. The class mapping lives in the internal `gridClasses.ts` helpers (`gridColumnsClasses`, `gridItemClasses`), not exported. In the stylesheet the `sft-col-start-*` group is declared after the `sft-span-*` group so an explicit start line always beats the start a span shorthand sets, and within each span tier `sft-span-full` is declared before the numeric spans so an explicit numeric `colSpan` beats the components' built-in full-row default; all utilities sit at the end of the file so they beat the component defaults (every grid-affecting selector is single-class on purpose, including `.sft-array-items`). The prototype's `sft-col-span` default-span class is superseded by `sft-span-full` and no longer ships. Gaps, auto-flow, and alignment are deliberately not metadata: they are design-system concerns, set centrally in consumer CSS on the grid containers (`.sft-grid`, `.sft-choice-group-body`, `.sft-grid-plain`). The tier widths are fixed in the stylesheet; the starter-template guide documents the CSS override for projects that need different widths. The old `fullWidth` boolean is replaced by `colSpan: 2`. `packages/starter/README.md` is the consumer documentation (install, stylesheet import, bare and wrapped usage, supported slots, icon usage and the wrapper-only `#icon` reachability caveat, customization guidance, extension, and the reserved-name and consumer-wins caveats), states explicitly that the package is an installable dependency and not a cloneable scaffold, and ships in the tarball. `StarterValueTypes` also gained seven HTML5 text-mode entries, all stored as `string`, rendered through the existing `TextInput`/`default-input` with no new component or slot: `number`, `email`, `tel`, `url`, `date`, `time`, `'datetime-local'` (quoted for the hyphen). `number` additionally gained an optional `number?: { min?, max?, step? }` group property on `StarterFieldProperties`, forwarded as plain `min`/`max`/`step` attributes onto `TextInput` (native spinner/stepping hints only, not a substitute for the `restriction`-driven `xsd_minInclusive`/`xsd_maxInclusive` validation). `StarterValueTypes` also gained `textarea: string`, rendered through the new `Textarea` component and `textarea-input` slot: a multi-line counterpart to `text`, adds no `StarterFieldProperties` group (`placeholder` and the shared root props are reused unchanged), and joins the `showValidState` opt-in the same way `text`/`select`/`password` already do. Does not join the `showValidState` opt-in. `StarterValueTypes` also gained `file: File | undefined`, rendered through the new internal `FileInput` component and `file-input` slot: the package's one uncontrolled control, since a native `<input type="file">` cannot take a `:value`.
